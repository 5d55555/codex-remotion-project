审计结论：**优先修复每帧分配、全屏动画调度和短窗口布局适配。** 当前代码规模小、布局浅，没有重型资源解码或启动 I/O；主要风险集中在持续运行的自绘背景。

本报告基于源码只读审计，未修改文件、未运行构建或真机测试。“可能掉帧”是代码风险判断，不代表已经测得掉帧。下列位置均相对当前项目目录，按优先级排序。

**1. P1：每帧创建 9 个 Shader 和至少 6 个数组，存在持续 GC 压力**

位置：`app/src/main/java/com/shinjuku/showdown/ShinjukuView.java:149、160、161、170`。

每帧执行两次 `beam()`：

| 分配 | 每帧数量 |
|---|---:|
| `LinearGradient` | 8 |
| `RadialGradient` | 1 |
| `widths`、`alphas` 数组 | 4 |
| 径向渐变颜色、位置数组 | 2 |

这是源码直接可见的分配，未计实现内部开销。120fps 下每秒创建 1,080 个渐变对象、720 个数组，并反复触及 Shader 底层资源。对象数量本身不能证明一定卡顿，但这是应首先消除的热点。官方明确建议避免在 `onDraw()` 分配对象，以免 GC 引起停顿。[官方：优化自定义 View](https://developer.android.com/develop/ui/views/layout/custom-views/optimizing-view)

具体改法：

- 将宽度、透明度数组改成 `private static final`。
- 在 `onSizeChanged()` 中创建两侧共 8 个光束渐变；它们的起止坐标、颜色都不随 `pulse` 改变。
- 径向渐变以固定半径创建，通过预分配的 `Matrix` 改变缩放，或围绕中心缩放 Canvas 后绘制固定圆。
- `Paint`、`Path` 已经是成员变量，并没有每帧 `new Path()`；无需重复优化成“复用 Path”。

径向渐变可按以下思路处理：

```java
// onSizeChanged：创建固定半径的 clashShader，保存 baseRadius。
// clashMatrix 为预先创建的成员变量。
clashMatrix.setScale(pulse, pulse, cx, cy);
clashShader.setLocalMatrix(clashMatrix);
glow.setShader(clashShader);
c.drawCircle(cx, cy, baseRadius * pulse, glow);
```

`onSizeChanged()` 的星星、楼群和窗口数组分配属于尺寸变化时的初始化；优先级低于每帧分配。

**2. P1：整个背景每个 VSync 重录、重绘，静态和低频部分没有分离**

位置：`ShinjukuView.java:104、110、120、121、125、138、176`。

每帧都重新提交全屏天空、90 颗星、8 层光束、交锋光晕、楼群、窗户、雾和28颗火星。窗口开关实际上约每4秒才发生一次判断结果变化，楼体与雾完全静态。

代价包括：

- UI 线程逐帧执行循环、三角函数与绘制命令录制。
- RenderThread/GPU 持续处理绘制与透明混合。
- 光束4层叠加、光晕、底部雾、半透明按钮形成局部过度绘制。
- 窗口数量随屏幕面积增长；平板、折叠屏和高分辨率设备成本更高。

`postInvalidateOnAnimation()` 能对齐帧节奏，但不保证设备只以60fps运行。若实际采用90/120fps，单帧预算分别约11.11/8.33ms，工作频率也随之上升。[官方：慢速渲染](https://developer.android.com/topic/performance/issues/render)

具体改法：

1. 保持原有前后遮挡顺序，拆出天空、楼群、雾等静态层；星星、光束、航空灯、火星独立更新。
2. 优先考虑拆成独立 View，让框架保留未失效 View 的 display list。
3. 窗灯使用独立层，只在状态切换时更新；不要每帧重录整片楼群。
4. 背景装饰可提供静态模式或较低更新率；先测60fps是否已足够，勿默认追求120fps。

缓存方式应按瓶颈选择：

| 方案 | 适用性与限制 |
|---|---|
| `RenderNode` | API29起可用，缓存绘制命令，减少UI侧重录；不等于消除GPU重放成本，API26–28需要分支。 |
| `Picture` | 缓存命令，不是预渲染像素；`drawPicture()` 在本项目最低版本已支持硬件加速，但仍需测量重放成本。 |
| `Bitmap` | 静态复杂楼群可预栅格化，逐帧画一次纹理；增加内存、首次生成和纹理上传成本。 |

ARGB_8888 的1080×2400全屏 Bitmap 约9.9MiB，1440×3200约17.6MiB，尚未计GPU侧资源。宜只缓存楼群所占区域，并在尺寸变化后重建。[官方：RenderNode](https://developer.android.com/reference/android/graphics/RenderNode)、[硬件加速](https://developer.android.com/develop/ui/views/graphics/hardware-accel)

**不能只把 `invalidate()` 换成局部矩形，就认为实现了局部渲染。** 星星和火星遍布大范围，硬件渲染也不保证严格按请求矩形执行绘制。分层保留命令更可靠。给整个动态背景强制开启硬件层同样无法缓存不断变化的内容，反而可能增加离屏纹理成本。

**3. P1：没有显式动画生命周期控制，耗电策略不完整**

位置：`ShinjukuView.java:138`；`MainActivity.java:15` 起，无对应暂停/恢复逻辑。

当前只有 `onDraw()` 尾部无条件请求下一帧，没有 Activity 状态、窗口可见性或用户静态模式控制。

需要准确区分：**这不等于已经证明后台无限绘制。** 窗口不可见时，框架通常停止实际绘制；这里也没有独立线程或永久运行的定时器。但代码未明确表达“何时允许持续动画”，分屏仍可见、页面被局部覆盖等场景也需要产品策略。

具体改法：

- 将帧调度移出 `onDraw()`，使用一个可移除的成员 `Runnable` 配合 `postOnAnimation()`。
- Activity 在 `onResume()/onPause()` 设置运行状态。
- View 同时检查 attached、window visibility、`isShown()`。
- 暂停、detach 时 `removeCallbacks()`；恢复时确保只启动一个回调链。
- 用户选择静态模式时绘制一帧后停止。

这能减少无意义的UI/GPU活动，降低长期驻留主页时的电量消耗和热降频风险。不要只按 `hasWindowFocus()` 停止：分屏中失焦的窗口可能仍然可见。

**4. P1：直接把系统 uptime 转成 float，设备运行较久后动画会出现时间量化**

位置：`ShinjukuView.java:106`。

```java
float t = SystemClock.uptimeMillis() / 1000f;
```

这里先将不断增长的毫秒值转换成 float。随着设备累计 uptime 增长，float 无法保留逐毫秒精度；大约7天时，毫秒输入的表示粒度已达到64ms量级。即使帧按时提交，火星和脉冲也可能看起来一跳一跳。

具体改法：先做 long 差值，再转换为 double，并让后续时间计算保持 double。

```java
private final long startMs = SystemClock.uptimeMillis();

// onDraw
double t = (SystemClock.uptimeMillis() - startMs) / 1000.0;
float pulse = 0.85f + 0.15f * (float) Math.sin(t * 2.2);
```

若暂停后不希望动画跳到新相位，维护累计“有效动画时长”，暂停期间不累计。

**5. P1：固定竖屏布局无法保证适应 Android16 大屏和短窗口**

位置：`app/src/main/AndroidManifest.xml:14`；`activity_main.xml:20、25、58、79`；`themes.xml:12、13`。

当前标题62sp、按钮固定260×58dp、两段18dp间隔，再加副标题和底部版本信息。加权 `Space` 只能分配剩余高度，无法在空间不足时把固定内容变成可滚动内容。横屏短窗口、大字体、分屏下可能溢出或被裁剪。

Android16上，target36应用在 `sw600dp` 及以上显示设备会默认被忽略方向等限制。官方列出的游戏例外依据 `appCategory`；本项目没有声明，不能仅凭应用名是游戏就假定例外生效。[官方：Android16目标版本行为变化](https://developer.android.com/about/versions/16/behavior-changes-16)

具体改法：

- 按**当前窗口可用宽高**适配，而不是依赖 `portrait`。
- 横向宽窗口采用左右布局；短窗口缩小标题和间距，并提供滚动兜底。
- 按钮使用可约束宽度、`minHeight="58dp"` 和内容 padding，允许大字体增高。
- 为标题设置最大宽度、换行或受控自适应字号。
- 折叠屏若有遮挡铰链，进一步按显示特征避让。

背景尺寸变化会自动重建场景，这是现有优点；但 `onSizeChanged()` 的随机生成和分配在连续窗口缩放时应额外检查。

**6. P2：`fitsSystemWindows` 可以生效，但建议明确处理 system bars 与 cutout**

位置：`MainActivity.java:38`；`activity_main.xml:16`；`themes.xml:5`。

不能把这里定性为“LinearLayout 不支持 `fitsSystemWindows`”。它继承 View 的默认处理：接收到相应 insets 时，应用为 padding 并消费。当前背景和内容互为兄弟，内容避让、背景铺满的结构也合理。[官方：View 默认 insets 行为](https://developer.android.com/reference/android/view/View.html)

风险在于它使用旧式默认策略，缺少明确的 cutout、横屏侧边安全区和导航模式处理意图。Android15对target35及以上强制边到边；Android16上target36不能再退出。透明系统栏颜色设置不能代替 insets 处理。

具体改法：移除该 XML 属性，显式对**内容层**应用 `systemBars | displayCutout`，保留原始 padding，避免重复分发时累加。例如引入 AndroidX Core 后：

```java
View content = findViewById(R.id.content);
int l = content.getPaddingLeft(), t = content.getPaddingTop();
int r = content.getPaddingRight(), b = content.getPaddingBottom();

ViewCompat.setOnApplyWindowInsetsListener(content, (v, insets) -> {
    Insets safe = insets.getInsets(
            WindowInsetsCompat.Type.systemBars()
            | WindowInsetsCompat.Type.displayCutout());
    v.setPadding(l + safe.left, t + safe.top,
                 r + safe.right, b + safe.bottom);
    return insets;
});
ViewCompat.requestApplyInsets(content);
```

本项目目前没有运行时 AndroidX Core 依赖，采用此方案需补依赖；也可使用按API分支的原生实现。不要给根布局和内容重复加同一份 inset。三键导航可能保留系统对比度遮罩，不应承诺设置透明色后所有模式完全透明。[官方：Views边到边适配](https://developer.android.com/develop/ui/views/layout/edge-to-edge)

**7. P2：Toast 连点会反复撤销和重建，提示可能闪烁、被截断**

位置：`MainActivity.java:21`。

当前 `cancel()` 的确可以撤销正在显示或尚未显示的 Toast，因此“防止堆积”的方向合理。但快速点击时，新提示可能刚出现就被撤销，也可能来不及出现；反复创建和系统服务交互没有必要，还可能打断辅助功能反馈。

具体改法：

- 相同“未开放”提示采用共享节流，例如1秒内重复点击直接忽略。
- 可使用常驻的行内状态文字，避免高频瞬时消息。
- `onPause()` 取消并清空当前 Toast，避免离开主页后继续显示。
- 若复用同一个 Toast，不要假定 `show()` 每次都能跨版本精确重置时长。

官方明确说明 `cancel()` 的撤销行为，以及**后台 Toast**存在限流；不能把后台限流规则直接当成前台连点的固定行为保证。Android12起，当前target版本的文本 Toast 最多两行，本项目短文案不受影响。[官方：Toast](https://developer.android.com/reference/android/widget/Toast)

**8. P2：TextView 有点击动作，但缺少标准按钮角色；“开始游戏”没有反馈**

位置：`activity_main.xml:58、65、72`；`themes.xml:18、19`；`MainActivity.java:31`。

这些控件已经 `clickable`、`focusable`，又设置了点击监听，**并非完全不能被 TalkBack 操作**。问题是其默认类型仍是 TextView，无法稳定提供标准 Button 的角色表达。“开始游戏”点击后无任何反馈，也无法让用户判断是否生效。

具体改法：

- 优先换成原生 `Button`，继续使用现有背景和样式，并调整默认最小尺寸、padding和大小写设置。
- 两个“空置”使用可区分的名称，例如“空置位置一，未开放”。
- 开始游戏尚未实现时明确显示“开发中”，或提供同样的未开放反馈。
- 装饰背景设置 `importantForAccessibility="no"`；按钮文字本身已可朗读，无需再添加重复的 `contentDescription`。

58dp高度满足常用触控目标要求，但仍需验证大字体不会裁字。[官方：应用无障碍](https://developer.android.com/guide/topics/ui/accessibility/apps)

**9. P2：release 关闭 R8，也没有资源压缩**

位置：`app/build.gradle.kts:20`；`gradle.properties:1`。

`isMinifyEnabled=false` 意味着发布包没有使用 R8 优化；`isShrinkResources` 未开启。当前应用很小，收益可能有限，但这是合理的发布配置改进，**不能指望它修复每帧 Shader 创建或GPU过绘**。

针对当前AGP8.13.2，可改成：

```kotlin
release {
    isDebuggable = false
    isMinifyEnabled = true
    isShrinkResources = true
    proguardFiles(
        getDefaultProguardFile("proguard-android-optimize.txt")
    )
}
```

并在 `gradle.properties` 设置：

```properties
android.r8.optimizedResourceShrinking=true
```

新增自定义规则应以真实需求为依据；启用后验证XML中的自定义 View 能正常 inflate，并保存 mapping。[官方：启用R8与资源优化](https://developer.android.com/topic/performance/app-optimization/enable-app-optimization)

还应明确区分：

- 当前未显式将release设为debuggable；AGP默认release不可调试。
- debug包默认可调试，本身带性能成本；连接调试器、录制完整分配又会增加干扰。
- 正式帧率结论应来自release或基于release的profileable变体。[官方：性能分析构建类型](https://developer.android.com/studio/profile)
- `org.gradle.jvmargs=-Xmx3g` 只影响构建进程，不会给手机应用配置3GB堆。
- `android.useAndroidX`、非传递R类、Kotlin工具链不是此处运行时卡顿原因。
- 所示 `testImplementation` 依赖不会作为正式应用运行时依赖打包。

**10. P3：首帧基础良好，但进场动画刻意延迟“主页完整可见”**

位置：`MainActivity.java:33、50`；`themes.xml:3、4`；`activity_main.xml:30`。

未发现深层嵌套、主线程磁盘/网络操作、大图解码。`FrameLayout + LinearLayout` 足够浅；权重有额外测量成本，但不值得优先重构。纯色深色 `windowBackground` 有助于启动过渡。

具体改法：

**硬件加速与 minSdk26 的核查结论**

位置：`ShinjukuView.java:109–220`；`MainActivity.java:39`；`AndroidManifest.xml:4`。

当前没有关闭硬件加速。矩形、圆、简单填充 Path、线性与径向渐变均属于常见支持路径；**没有依据声称这些操作必然导致整个 View 自动退回软件渲染**。

需要区分：

- 不断修改 Path 可能增加几何处理成本；本项目只有少量简单多边形，优先级低于分配与全屏持续更新。
- 当前没有 `BlurMaskFilter`、复杂混合模式或显式软件层；文字阴影也不能等同于不受支持的非文字阴影。
- 不支持的绘制操作不保证自动得到正确的软件回退；应逐项核查，必要时只对局部显式使用软件层。
- API26–27上，大比例缩放 Path/阴影的质量限制需实测，不能把官方表格中的API28误读成“API28前不支持drawPath”。[官方：硬件加速支持与缩放限制](https://developer.android.com/develop/ui/views/graphics/hardware-accel)

现有 `setDecorFitsSystemWindows()` 已由API30条件保护；其他所示调用未发现明确的API26不兼容点。后续引入 `RenderNode`、新式 insets API时必须加版本保护。Java21语言级别也不代表可以直接使用所有Java21运行库API；当前源码未见这类使用。

**改完后的真机验证清单**

以下是建议执行的验证步骤，本次审计没有执行。

1. **用真实发布配置建立基线。** 安装签名release；需要分析时用release派生的profileable变体。保持亮度、温度、电量模式一致，关闭录屏、调试器和性能叠加层后再做最终采样。覆盖一台API26/27设备、Android15/16设备，以及一台90/120Hz设备。

2. **先测冷启动，再单独测进场与稳态动画。**

```bash
adb shell am start -S -W -n com.shinjuku.showdown/.MainActivity
adb shell dumpsys gfxinfo com.shinjuku.showdown reset
```

   重复冷启动至少10次，比较中位数和尾部耗时；`-S` 是结束进程后启动，不等于清空系统缓存。首页运行一段固定时间后执行：

```bash
adb shell dumpsys gfxinfo com.shinjuku.showdown framestats > gfxinfo.txt
```

   分别采集进场、稳态和连续点击，不要只看平均fps。记录帧耗时P50/P95/P99和掉帧比例；`gfxinfo`明细有容量限制，长期测试需分段采集。[官方：dumpsys](https://developer.android.com/tools/dumpsys)

3. **确认实际刷新率和实际应用帧节奏。** 在系统设置中选择60/90/120Hz，开发者选项打开“显示刷新率”。面板显示120Hz不代表应用正在稳定输出120fps；以System Trace/Perfetto的FrameTimeline与呈现时间为准。预算分别是16.67/11.11/8.33ms。

4. **定位UI、GPU与GC各自的问题。** 开发者选项→“系统跟踪”，或Android Studio→Profiler→System Trace，录制10–20秒。查看主线程绘制、RenderThread、调度等待、GC和FrameTimeline。Shader优化后应看到逐帧分配显著减少；GC是否造成错过截止时间需要在时间线上关联确认。[官方：FrameTimeline](https://github.com/google/perfetto/blob/main/docs/data-sources/frametimeline.md)

5. **检查过绘与无效更新。** 开发者选项打开“调试GPU过度绘制”“GPU呈现模式分析”；检查雾、光束交汇和半透明按钮区域。传统16ms参考线不足以判定120Hz是否合格。诊断后关闭这些选项再做最终测量。[官方：检查渲染速度](https://developer.android.com/topic/performance/rendering/inspect-gpu-rendering)

6. **检查生命周期与热稳定性。** 前台运行10–15分钟，再测试Home后台、锁屏、返回、分屏失焦和恢复：

```bash
adb shell input keyevent KEYCODE_HOME
adb shell dumpsys cpuinfo com.shinjuku.showdown
adb shell dumpsys meminfo com.shinjuku.showdown
adb shell dumpsys thermalservice
```

   用trace确认隐藏后没有应用持续帧循环，恢复后只有一条调度链；内存不持续增长。比较冷机与热机的帧时间，不能只测刚启动的30秒。

7. **验证边到边与自适应。** Android15/16分别测试手势导航、三键导航、横屏刘海、平板横屏、折叠展开、分屏最小高度；字体与显示大小调到最大。检查标题、三个按钮、版本文字均可见且可操作，内容不被系统栏或铰链遮挡。

8. **验证交互与无障碍。** 开启TalkBack，用触摸探索及键盘/D-pad依次操作按钮；确认角色、名称和反馈正确。快速点击空置按钮20次后立即离开页面，检查提示是否闪烁、堆积或残留。

验收应同时满足：目标刷新率下帧截止时间稳定、没有周期性GC尖峰、热机后无明显恶化、不可见时无持续动画负载，以及所有目标窗口尺寸下菜单可用。仅“肉眼看着顺”或“平均60fps”不足以证明问题已解决。
