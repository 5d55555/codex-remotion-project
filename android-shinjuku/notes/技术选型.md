建议《新宿决战》采用 **Java 主页 + 独立 GameActivity + C++ 游戏核心 + OpenGL ES 3 + Swappy + ADPF**。先做 GLES 后端；只有实测证明存在明显收益，或发行渠道提出要求，再增加 Vulkan。

这是基于你把**持续性能、帧节奏、输入延迟和包体**放在首位的工程判断。若团队主要熟悉 Java、希望更快完成游戏，**libGDX 是更务实的第二选择**；不能因为它使用 Java 就认为无法稳定运行 120fps。

以下基于截至 **2026-10-29** 查到的官方文档和官方仓库；其中 Swappy 文档更新于 2026-02，AGP 8.13 文档始于 2025-09。性能等级和开发成本是选型判断，并非同场景实测结果。任何路线都不能脱离场景复杂度、设备驱动和温度条件承诺“永不掉帧”。[Swappy 官方文档](https://developer.android.com/games/sdk/frame-pacing)、[AGP 8.13 文档](https://developer.android.com/build/releases/agp-8-13-0-release-notes)

**先明确几个会影响选型的事实。**

- 60/90/120fps 的单帧预算分别是 **16.67/11.11/8.33ms**。平均 FPS 达标，也可能因帧间隔不均、队列积压而卡顿或延迟高。
- `Choreographer` 提供显示同步时机，`Surface.setFrameRate()` 提供刷新率意向，Swappy 管理提交节奏；三者解决的问题不同。Swappy 同时支持 GLES 和 Vulkan，并通过时间戳、同步栅栏等机制减少过早呈现与缓冲队列积压。[官方机制说明](https://developer.android.com/games/sdk/frame-pacing)
- Android 官方指出，**Android 15 游戏默认采用 60Hz；更高帧率应显式通过 Frame Rate API 或 Swappy 请求**。请求仍受温度、电量、用户设置和系统策略影响。[高刷优化指南](https://developer.android.com/games/optimize/display-refresh-rate-change)
- **APT 与 ADPF 不同**：Android Performance Tuner 用于收集性能数据并在 Google Play 分析；ADPF 用于运行时向系统提供工作负载提示、感知热状态。APT 不负责给游戏“加速”。[APT](https://developer.android.com/games/sdk/performance-tuner)、[ADPF](https://developer.android.com/games/optimize/adpf)

**各路线的性能与实现代价，可按下面比较。**

“多线程”需区分独立渲染线程、资源工作线程和并行生成 GPU 命令；有独立线程并不等于渲染可任意并行。

| 路线 | 性能上限与帧节奏 | GC／卡顿风险 | 多线程能力 |
|---|---|---|---|
| **1. View/Canvas + Choreographer** | 适合主页和较轻的 2D。60、90、120fps 都可能达到，但大量动态精灵、复杂混合与特效的控制空间较小；呈现由 HWUI 管理 | Java 分配、主线程阻塞、布局、首次图片上传、文字排版都可能产生尖峰 | `onDraw()` 在 UI 线程记录命令，框架 RenderThread 执行；逻辑可后台计算，但须安全发布快照 |
| **2. SurfaceView + lockHardwareCanvas** | 简单至中等复杂度 2D 可很好运行；独立线程减少主页/UI 工作干扰。仍需自行做显示同步，没有 Swappy 的直接提交控制 | Java GC 仍存在；Canvas 锁定、提交及首次资源使用可能阻塞 | 一个线程持有 Canvas 绘制；逻辑、解码可分线程，不能多个线程同时画同一 Canvas |
| **3. Java/Kotlin GLES 3** | 高。批处理、图集、实例化、离屏效果均可控制。GLSurfaceView 的连续渲染不自动等于完善的 pacing；自管 EGL 控制更完整 | 可做到热循环近零分配；仍需控制 GC、驱动调用、shader 编译、纹理上传 | GLSurfaceView 已有独立 GL 线程；单 EGLContext 通常只由一个线程持有。多 context 上传更复杂 |
| **4. C++ + GameActivity + GLES/Vulkan + Swappy** | 控制最完整。GLES 足以承载大多数 2D 对战；Vulkan 提供更强的显式调度能力，但不会自动更快 | 游戏核心没有托管 GC；仍有 malloc、锁、缺页、I/O、shader/pipeline 创建和驱动卡顿 | GLES 通常单提交线程；Vulkan 更适合并行录制命令。两者都可并行处理资源、AI 等 |
| **5. libGDX** | 高，SpriteBatch 等适合 2D；Android 底层是 GLES。默认后端的 swap/pacing 控制弱于自管 EGL | 热循环可近零分配；注意临时集合、字符串、对象、同步加载和字形生成 | 有独立渲染线程；资源准备可后台做，GL 操作回渲染线程 |
| **6. Godot 4** | 2D 能力成熟，足以实现目标，但节点、脚本、透明叠加和复杂 shader 会影响低端机。已内置 Swappy | GDScript 主要采用引用计数，不是 JVM 式追踪 GC；对象创建释放、脚本、资源加载仍会卡顿 | 有渲染线程配置与工作线程；场景树和渲染资源操作受线程安全约束 |
| **7a. raylib Android** | 轻量 C 框架，2D 上限高；默认目标 FPS/VSync 不应当成完整 Android pacing，需要补平台集成 | 无 JVM 核心 GC；仍需管理分配、资源与驱动尖峰 | 以单渲染线程为主；后台任务自建 |
| **7b. SDL3** | 高；可用 SDL Renderer，或自管 GLES/Vulkan。VSync 本身不等于 Swappy | 同 C/C++；外接运行时则另算 | 资源/逻辑可后台；需遵守各 SDL 渲染 API 的线程要求 |

View 硬件加速采用显示列表机制，不能将 `onDraw()` 理解为直接、立即执行 GPU 绘制；GLSurfaceView 则明确提供独立渲染线程。[View 硬件加速模型](https://developer.android.com/topic/performance/views/hardware-accel-views)、[GLSurfaceView](https://developer.android.com/reference/android/opengl/GLSurfaceView)

第 2 条还有两个容易混淆的点：`SurfaceHolder.lockHardwareCanvas()` 从 **API 26** 提供；普通 `lockCanvas()` 得到的是软件 Canvas。硬件 Canvas 每帧应完整覆盖 Surface，不能依赖上一帧内容保留。[SurfaceHolder](https://developer.android.com/reference/android/view/SurfaceHolder)、[Surface/Canvas 架构说明](https://source.android.com/docs/core/graphics/arch-sh)

| 路线 | 包体趋势¹ | Linux 纯命令行构建 | 开发成本 | 中文文字办法 |
|---|---|---|---|---|
| **1. View/Canvas** | 最小一档 | SDK + Gradle 即可 | 最低 | `TextView`、`Canvas.drawText()`、`StaticLayout`，使用系统字体回退或自带字体 |
| **2. Hardware Canvas** | 最小一档 | 同上 | 低至中；增加线程和 Surface 生命周期管理 | 同上；缓存排版结果 |
| **3. Java/Kotlin GLES** | 小 | SDK + Gradle；加 Swappy 时引入 NDK | 中高，自建批处理、资源、文字系统 | 用 Android Canvas 将文字绘制到 Bitmap 后上传并缓存；或预制字形图集 |
| **4. NDK 自研** | 可控，通常小于完整通用引擎 | Gradle + NDK + CMake，完全可行 | 最高 | 固定 UI 可用预制图集；动态文本用 FreeType + 排版/回退方案，或 JNI 调 Android 排版栅格化 |
| **5. libGDX** | 小至中；native 扩展和 ABI 会增加体积 | 完全可行，可接入现有 Gradle 项目 | 中，显著低于自研引擎 | `BitmapFont` 或 `gdx-freetype` + 包含中文的字体；不能只生成默认拉丁字符集 |
| **6. Godot 4** | 通常最大；可自编裁剪模板 | **headless 导出可行** | 游戏功能开发较低；Android 深度定制另计 | `FontFile`/主题字体 + 中文字体与 fallback；预热字形 |
| **7a. raylib** | 小，取决于裁剪与资源 | 可行；核对 Android 构建模板 | 中高，需补平台能力 | 中文 TTF/OTF + `LoadFontEx()` 指定 Unicode codepoints |
| **7b. SDL3** | 小至中，取决于附加库 | 官方支持 Android AAR/Prefab、CMake/Gradle | 中高，仍需游戏框架 | SDL_ttf + 中文字体与 fallback，缓存文本/字形 |

¹ 这里比较的是框架增量；不报未经同配置构建的 MB 数。完整中文字体、音乐、图集及同时打包多个 ABI，可能比代码框架更影响最终包体。

libGDX 官方支持 Android GLES 2/3，其 FreeType 扩展可以指定生成字符集。raylib 官方示例展示了 UTF-8 → codepoints → 去重 → `LoadFontEx()` 的流程。SDL3 官方提供 AAR/Prefab 接入方式。[libGDX GLES](https://libgdx.com/wiki/graphics/opengl-es-support)、[gdx-freetype](https://libgdx.com/wiki/extensions/gdx-freetype)、[raylib 字形示例](https://github.com/raysan5/raylib/blob/master/examples/text/text_codepoints_loading.c)、[SDL3 Android](https://wiki.libsdl.org/SDL3/README-android)、[SDL_ttf](https://github.com/libsdl-org/SDL_ttf)

**高刷和 ADPF 并非 NDK 专属，各路线都能接入，但难度不同。**

| 路线 | 高刷／帧节奏接入 | ADPF 性能提示 |
|---|---|---|
| **1. View** | Choreographer 跟随系统回调；API 35+ 可用 `View.setRequestedFrameRate()`。旧系统结合窗口刷新率偏好；不应假设普通 View 有可直接控制的独立 Surface | 可用 Java `PerformanceHintManager`；只关联自己掌握的线程，别依赖框架私有 RenderThread |
| **2. Hardware Canvas** | 对有效 `holder.getSurface()` 调 `setFrameRate()`；游戏线程 Looper 上使用 Choreographer；Canvas API 不直接提供 Swappy swap 接入点 | 可提示游戏线程 |
| **3. GLES Java/Kotlin** | Surface 请求高刷；自管 EGL 可经 JNI 接 Swappy。原生 GLSurfaceView 的自动 swap 不便直接替换 | 可提示 GL/逻辑线程 |
| **4. NDK** | Swappy + `ANativeWindow`；或自行使用原生帧率 API。GLES/Vulkan 都支持 | 原生 API 或 Java 桥接，最容易统一管理 |
| **5. libGDX** | Android 层请求 Surface 高刷；需要更强 pacing 时修改后端。不要依赖桌面限帧接口 | 在 Android 模块封装，取得实际渲染线程 TID |
| **6. Godot** | 内置 Swappy；配置目标 FPS 和 pacing 模式，并验证具体渲染后端 | 可通过 Android 插件/GDExtension 集成；不能假设已有完整 PerformanceHint session |
| **7. raylib / SDL3** | Android 桥接请求高刷；Swappy 需接到实际呈现路径，不能叠加两套限帧器 | 可原生接入，需掌握线程与帧工作范围 |

特别注意：当前 libGDX Android 后端源码中的 `setForegroundFPS()`、`setVSync()` 是空实现。因此，**桌面设置成功不代表 Android 生效**；应检查所固定版本的后端。[AndroidGraphics 源码](https://github.com/libgdx/libgdx/blob/master/backends/gdx-backend-android/src/com/badlogic/gdx/backends/android/AndroidGraphics.java)

Godot 的 `enable_frame_pacing` 默认开启；自动模式可能把无法持续满足的 60fps 降到稳定 30fps。因此它能帮助节奏稳定，但不能弥补场景本身超预算。[Godot ProjectSettings](https://docs.godotengine.org/en/stable/classes/class_projectsettings.html#class-projectsettings-property-display-window-frame-pacing-android-enable-frame-pacing)

**为什么主推路线 4，并暂不把 Vulkan 作为首发必选。**

你的游戏本体还没开始，可以从一开始就控制内存分配、输入队列、资源预热和呈现节奏。C++ 核心、GLES 批处理与 Swappy 的组合能提供这些控制，同时保留 Android 原生主页。

对典型 2D 对战，先优化图集切换、透明 overdraw、全屏后处理、纹理带宽，通常比直接更换图形 API 更值得做。Vulkan 增加同步、资源生命周期、pipeline 和驱动适配成本；在尚无实测瓶颈时，这笔成本不一定带来相应收益。这个结论是针对本项目的工程取舍。

建议最初采用：

- **一个游戏/渲染线程**：输入消费 → 固定步长模拟 → 绘制 → Swappy 提交。
- **少量资源工作线程**：文件读取、解压、图片解码；GPU 上传集中调度。
- 只有测出模拟明显抢占绘制预算，再拆逻辑与渲染线程。过早拆分会增加同步成本和快照延迟。
- APT 放到需要线上设备分布分析时接入；首版先做本地帧监视、Perfetto 和 ADPF。

如果不愿承担自研文字、音频、资源管理和生命周期的成本，就选 **libGDX + Android 高刷/ADPF 桥接**。路线 3 自研 Java GLES 相比 libGDX，主要适合明确想保留自定义渲染架构的团队。路线 1、2 可以完成轻量游戏，但不作为本项目长期首选。

**现有 Java 主页可以原样保留，通过独立 Activity 进入游戏。**

```text
MainActivity（现有 android.app.Activity）
    │ Intent：关卡、角色、模式、存档标识
    ▼
BattleActivity extends GameActivity
    │
    ├─ Surface / 输入 / 生命周期
    ├─ C++ 模拟与 GLES 渲染
    ├─ Swappy
    └─ ADPF / Thermal
```

GameActivity 官方支持 Java 子类并加载 native 库；它本身继承 AppCompatActivity，不要求把现有主页一起改造成 GameActivity。[接入指南](https://developer.android.com/games/agdk/game-activity/get-started)、[GameActivity 官方说明](https://android.googlesource.com/platform/frameworks/opt/gamesdk/+/refs/heads/android-games-sdk-game-activity-release/game-activity/README.md)

衔接时应落实：

- 进入游戏后停止主页背景动画及无用回调；返回时恢复。
- `onPause()`、焦点丢失、Surface 销毁分别处理，允许 Surface 重建。
- 不长期阻塞 UI 线程等待游戏线程退出；Surface 销毁后禁止继续提交。
- 跨 Activity 传配置和标识，大资源由游戏资源系统读取。
- 若采用 GameActivity native glue，使用 **GameActivity 配套版本**，不要误接 NDK NativeActivity 的同名 glue。

换用 libGDX、SDL3 或 Godot 时，也可采用独立游戏 Activity；Godot 保留原生主页需要 Android 库/插件集成，不能只导出一个独立 Godot APK 就完成衔接。

**建议固定模拟步长，并把“玩法帧率”和“显示帧率”分开。**

对战逻辑可固定 **60 tick/s**，渲染根据能力选择 60/90/120fps；碰撞、出招、硬直、随机数不能随渲染帧率改变。累计时间推进模拟，限制单次追赶步数，避免长暂停后陷入追帧循环。

90/120fps 渲染可使用状态插值，但传统“上一状态与当前状态插值”通常增加约一个模拟 tick 的视觉延迟。对战角色的输入反馈，应评估有限预测、独立表现层或提高模拟频率，而非无条件插值全部状态。

触控路径尽量短：保留事件时间戳和 pointer ID，尽早入队，在本帧模拟前消费；暂停、失焦时清除按压状态。60Hz 模拟也意味着输入到模拟生效存在量化等待，120Hz 显示不会自动消除它。

**关键 API 建议清单如下。**

| 功能 | API / 库 | 使用要点 |
|---|---|---|
| Java 显示同步 | `Choreographer.postFrameCallback()`，API 16+ | 在对应 Looper 线程获取实例，回调需重新注册 |
| 更完整时间线 | `postVsyncCallback()`，API 33+ | 提供 deadline、预期呈现时间等 |
| 原生显示同步 | `AChoreographer` | 自管循环的备选，不和 Swappy 重复等待 |
| Surface 高刷 | `Surface.setFrameRate()`，API 30+ | 游戏使用 `FRAME_RATE_COMPATIBILITY_DEFAULT` |
| 帧率切换策略 | 三参数 `setFrameRate()`，API 31+ | 优先无缝切换；生命周期或目标变化时设置 |
| View 帧率意向 | `View.setRequestedFrameRate()`，API 35+ | 用于 View/HWUI 路线 |
| 原生高刷 | `ANativeWindow_setFrameRate()` | 低版本进行运行时保护 |
| 显示变化 | `DisplayManager.DisplayListener`、`Display.getSupportedModes()` | 处理实际模式变化 |
| GLES pacing | `SwappyGL_init/setWindow/setSwapIntervalNS/swap` | 用 `SwappyGL_swap()` 替换实际 swap |
| Java ADPF | `PerformanceHintManager`，API 31+ | session 创建、目标更新、实际耗时报告、关闭 |
| 原生 ADPF | `APerformanceHint_*`，API 33+ | 低版本可走 Java 桥接或跳过 |
| 新版工作报告 | `WorkDuration`，API 35+ | 支持 CPU/GPU 工作信息 |
| 热状态 | `PowerManager` thermal API | 提前降画质/帧率，恢复加迟滞 |
| 自定义追踪 | `Trace.beginSection()`、`ATrace_*` | 标记输入、模拟、渲染、上传、提交 |

官方说明强调：`setFrameRate()` 是意向，**不保证得到请求值，也不负责调用渲染循环**；游戏应使用 DEFAULT 兼容模式。[Frame Rate API](https://developer.android.com/media/optimize/performance/frame-rate)、[Choreographer](https://developer.android.com/reference/android/view/Choreographer.html)、[View API](https://developer.android.com/reference/android/view/View)

Swappy 初始化后，在 Surface 变化时更新 `ANativeWindow`，并检查是否启用；初始化失败仍须有备用同步策略。[Swappy 接入函数](https://developer.android.com/games/sdk/frame-pacing/opengl/add-functions)

ADPF session 中必须传 **Linux TID**，Java 使用 `Process.myTid()`，不能使用 `Thread.getId()`。目标耗时表示工作截止预算；实际报告应反映工作区间，避免把人为限帧休眠当作计算需求。换帧率后更新目标，暂停时停止报告或关闭 session。它是调度提示，不是强制锁频。[Performance Hint 说明](https://source.android.com/docs/core/perf/performance-hint-api)、[Session API](https://developer.android.com/reference/android/os/PerformanceHintManager.Session)

**中文建议采用“主页用系统排版，战斗内用缓存文字”。**

固定菜单、技能名、提示文字，可从全部本地化文本提取字符，制作字体子集和字形图集；比分、血量数字单独缓存。动态昵称/聊天则需要更完整的字体覆盖、缺字回退和排版。

GLES/C++ 路线可以调用 Android `Paint`/`StaticLayout` 将完整文本栅格化为 Bitmap，再上传缓存，减少自研排版负担；不要每帧重新生成或上传文字。直接使用 FreeType 时，它主要解决字形栅格化，完整排版、换行和 fallback 仍需另行处理。

Godot 能使用系统字体回退，但官方指出 **Android 系统字体加载依赖厂商配置，可靠性有限**。需要确定显示效果时，应随包带有授权的中文字体子集。[Godot 字体说明](https://docs.godotengine.org/en/stable/tutorials/ui/gui_using_fonts.html)

**你的容器足以完成构建；缺少的是设备验证。**

AGP 8.13 的最低 Gradle 为 8.13、最低 JDK 为 17；现有 Gradle 8.14.3/JDK 21 可承载这套构建。构建 JVM 版本不等于 Android Java API 版本，建议明确设置 Java/Kotlin 字节码目标，例如 17，并按需要配置 desugaring。[AGP 兼容表](https://developer.android.com/build/releases/agp-8-13-0-release-notes)、[Gradle 8.14.3 兼容说明](https://docs.gradle.org/8.14.3/userguide/compatibility.html)

对于主推路线，固定 SDK、NDK、CMake 和依赖版本，通过 `externalNativeBuild` 接 CMake，再运行：

```bash
./gradlew :app:assembleDebug :app:assembleRelease :app:bundleRelease
```

release 签名需要单独配置。无 Android Studio、无模拟器、无 KVM，都不妨碍编译和打包。

所有含 native 库的路线，包括 libGDX 扩展和 Godot 模板，都应检查 **16KB 页面兼容性**。AGP 8.5.1+ 处理对应打包对齐，NDK r28+ 默认生成 16KB 对齐库，但旧预编译依赖仍须检查。[官方页面大小指南](https://developer.android.com/guide/practices/page-sizes)

Godot 的纯命令行导出也明确可行：

```bash
godot --headless --path ./game --editor --import
godot --headless --path ./game --export-release "Android" ./build/shinjuku.apk
```

前提是使用 **Godot editor 二进制**、安装与其精确匹配的 export templates、准备 `export_presets.cfg`、SDK/JDK 路径和签名设置。无 GPU 环境使用 `--headless`；导出模板自身不能代替编辑器执行导出。自定义 Gradle 构建应服从固定 Godot 版本的模板要求，不能默认直接套用现有 AGP。[命令行导出](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html#exporting)、[Android 导出配置](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html)

**主推方案的项目结构可以保持精简。**

```text
android-shinjuku/
├─ app/
│  └─ src/main/
│     ├─ java/.../
│     │  ├─ MainActivity.java
│     │  ├─ BattleActivity.java
│     │  └─ platform/         # 字体、设置、Java API 桥接
│     ├─ cpp/
│     │  ├─ CMakeLists.txt
│     │  ├─ platform/         # GameActivity、输入、生命周期
│     │  ├─ core/             # 固定步长、战斗、碰撞、回放
│     │  ├─ render/gles/      # 图集、批处理、shader
│     │  ├─ assets/           # 异步加载、缓存
│     │  └─ perf/             # Swappy、ADPF、帧监视、trace
│     ├─ assets/              # 游戏资源
│     └─ res/                 # Android UI 资源
├─ native-tests/              # 主机可运行的 C++ 逻辑测试
├─ benchmark/                 # 有设备后运行的 instrumentation
└─ tools/                     # 图集、字体子集、包体与对齐检查
```

优先让 `core/` 不依赖 Android、JNI 或 GLES，便于 Linux 上测试与回放验证。不要一开始同时实现多个渲染后端。

**没有真机时，可以验证正确性、构建和潜在风险，不能证明 Android 流畅度。**

| 检查 | 能验证什么 | 不能推出什么 |
|---|---|---|
| Gradle `lint`、单元测试、release 构建 | API 级别保护、资源/Manifest、编译打包 | 真实帧节奏、驱动兼容 |
| Java/Kotlin 核心 JUnit、JMH/JFR | 算法复杂度、分配、相对性能回归 | HotSpot 结果不等于 ARM ART 性能 |
| C++ 主机测试、clang-tidy、ASan/UBSan | 战斗逻辑、越界、生命周期等错误 | Android GPU/调度性能 |
| 确定性回放 | 同输入下状态/hash 是否一致 | 画面是否按时呈现 |
| 字体/资源检查 | 本地化字符覆盖、图集尺寸、缺失资源 | 厂商字体回退与 GPU 上传表现 |
| APK/AAB 静态检查 | ABI、依赖、包体、ELF/ZIP 对齐、签名 | 安装后稳定性 |

可建立基础 CI：

```bash
./gradlew :app:lintRelease :app:testReleaseUnitTest :app:assembleRelease
```

含 C++ 时增加主机测试、静态分析和所有交付 ABI 的交叉编译；用 `llvm-readelf`、`zipalign`、`apkanalyzer`、`bundletool` 检查产物。若主机有软件图形环境，可做渲染正确性冒烟测试，但其 FPS 不作为手机性能指标。

**有真机后，按工具覆盖范围分别验证。**

| 工具 | 建议用途与限制 |
|---|---|
| **Perfetto** | 首选：看游戏线程调度、CPU 频率、GC、锁、I/O、BufferQueue、SurfaceFlinger，结合自定义 trace 定位尖峰 |
| **AGI** | 检查 draw call、shader、纹理、GPU 工作。GLES 帧分析通过 ANGLE 转译到 Vulkan，结果需回原始驱动确认 |
| **APA** | 2026-05 官方推出的 Android Performance Analyzer，可作为新的系统性能分析工具评估 |
| **`dumpsys gfxinfo ... framestats`** | 适合主页和 View/HWUI；不能完整代表独立 GL/Vulkan Surface 游戏帧 |
| **Macrobenchmark / FrameTimingMetric** | 自动化启动、主页动画、切换流程；独立游戏 Surface 要验证指标覆盖，并搭配游戏 trace/自定义统计 |
| **GPU 呈现模式分析条形图** | 查看 View/HWUI；不能当作整个 GLES/Vulkan 游戏的 GPU 时间 |
| **显示刷新率选项** | 确认面板刷新率；显示 120Hz 不代表游戏提交或实际显示 120 个新帧 |

AGI 的 GLES/ANGLE 限制、View 指标的覆盖边界，以及 FrameTimingMetric 的 CPU/overrun 定义都有官方说明；`frameOverrunMs` 需 API 31+。Perfetto FrameTimeline 对 SurfaceView 的覆盖也有局限，应结合系统版本及实际 trace 检查，不能只看一条总览曲线。[AGI](https://developer.android.com/agi/troubleshooting)、[渲染指标限制](https://developer.android.com/topic/performance/vitals/render)、[Macrobenchmark 指标](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-metrics)、[Perfetto FrameTimeline](https://github.com/google/perfetto/blob/main/docs/data-sources/frametimeline.md)、[2026 APA 公告](https://android-developers.googleblog.com/2026/05/introducing-android-performance-analyzer.html)

常用命令：

```bash
adb shell dumpsys gfxinfo your.package.name reset
# 执行主页动画或切换场景
adb shell dumpsys gfxinfo your.package.name framestats

./gradlew :benchmark:connectedCheck
```

测试至少覆盖低端 60Hz、中端 90/120Hz，以及不同 GPU 厂商；使用 release/profileable 构建、固定回放，分别测首次运行、预热后和持续运行 20–30 分钟。主动测试暂停恢复、Surface 重建、刷新率变化、首次技能特效和温控降档。

除平均 FPS，记录 **帧间隔 P50/P95/P99、超时比例、连续重复帧、最长停顿和输入年龄**。端到端触控延迟还需要高速摄影或外部测量；软件时间戳只能覆盖链路的一部分。

**游戏内置监视器应显示帧时间曲线，并区分“工作耗时”和“真正显示”。**

使用预分配环形缓冲区保存最近约 1,000–2,000 帧，记录：

```text
输入事件时间 → 消费时间
模拟开始/结束
CPU 渲染开始/结束
GPU 时间（支持时异步查询）
提交开始/结束
实际呈现时间（可获得时）
```

叠层每 250–500ms 更新一次：

- 目标 FPS、实际显示刷新率、提交 FPS；
- 帧间隔 P50/P95/P99、超预算次数和连续超时次数；
- 模拟、CPU 绘制、GPU、提交等待各自耗时；
- 最近输入的消费延迟、热状态、当前画质档；
- 最近数秒曲线，并标出 16.67/11.11/8.33ms 预算线。

不要每帧排序全部样本、拼字符串或写磁盘；GPU query 延迟读取，避免同步等待。`eglSwapBuffers()`/`SwappyGL_swap()` 返回时间**不等于屏幕呈现时间**，应明确标注统计口径；需要更可靠的呈现分析时，结合 Swappy 统计和系统追踪。[Swappy 帧统计](https://developer.android.com/games/sdk/frame-pacing)

最终把首个里程碑定为：**一个可重复的双角色战斗压力场景，在低端机持续稳定 60fps；在具备余量的设备上请求并验证 90/120fps。** 先完成这条完整链路，再扩充美术与特效，技术路线的选择才有可验证的依据。
