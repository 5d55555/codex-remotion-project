# 战斗审计（Sol）

两轮只读审计：先审新写的战斗代码，修完再复核。下面是原文，最后是处理结果。

## 第一轮

确认有 5 项问题，主要是输入丢失、最大输出苍的吸力语义和局部插值缺失；未确认正常生命周期下存在崩溃或 Activity 泄漏路径。

以下按严重程度排序。审计全程只读；未运行会写入构建产物的 Gradle，也未做真机性能测量。

1. **P2：黑闪停顿期间，按键被消费后直接丢弃**

   **位置：** [BattleLoop.java:128](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/BattleLoop.java:128)、[World.java:53](/home/user/codex-remotion-project/android-shinjuku/core/src/main/java/com/shinjuku/showdown/core/World.java:53)。

   **触发条件：** 黑闪的 8 tick 停顿期间按下跳跃、体术、赫或苍。

   **后果：** `controls.sample()` 已推进 `seen`，但 `World.step()` 在 `controlGojo()` 前返回，随后边沿被清除。体术、赫、跳跃连输入缓冲都进不去；苍即使继续按住，也可能因丢掉 `blueDown` 而无法起手。

   **最小改法：** 在停顿判断前接收并缓存输入；动作执行仍等停顿结束。苍的按下、松开也需要保留，不能只保留最终 `held`。

2. **P2：Controls 计数器只能保证“至少发生过一次”，不能保证不丢键或保持苍的事件顺序**

   **位置：** [Controls.java:100](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/Controls.java:100)、[Controls.java:112](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/Controls.java:112)、[World.java:95](/home/user/codex-remotion-project/android-shinjuku/core/src/main/java/com/shinjuku/showdown/core/World.java:95)。

   **触发条件：**
   - 两次采样之间，同一按钮按下多次，例如战斗线程阻塞、主线程仍处理触摸时。
   - 苍在同一采样间隔内经历“按下→松开→再次按住”。

   **后果：**
   - `seen[i] = n` 一次吞掉全部增量，多个按下合并为一个。
   - 第二种序列得到 `blueDown=true、blueUp=true、blueHeld=true`，世界立即启动普通苍，当前仍按住的第二次操作失去长按机会。
   - 各项原子读取不是整体快照，采样还可能读到跨越不同触摸事件的组合。这是事件一致性问题，不是原子变量缺少可见性。

   **最小改法：** 使用有序输入队列传递按钮边沿，预分配即可避免分配；按住状态与事件保持一致。单纯给计数器加锁，仍无法恢复已经合并掉的事件顺序。

3. **P2：最大输出苍只将加速度上限翻倍，实际吸力并未普遍翻倍**

   **位置：** [World.java:219](/home/user/codex-remotion-project/android-shinjuku/core/src/main/java/com/shinjuku/showdown/core/World.java:219)、[World.java:325](/home/user/codex-remotion-project/android-shinjuku/core/src/main/java/com/shinjuku/showdown/core/World.java:325)、[Tuning.java:42](/home/user/codex-remotion-project/android-shinjuku/core/src/main/java/com/shinjuku/showdown/core/Tuning.java:42)。

   **触发条件：** 最大输出苍吸引目标，且速度跟随计算出的加速度没有触及普通苍的上限。

   **后果：** 实际加速度仍是相同的 `BLUE_FOLLOW × 速度差`。例如目标距中心水平 20、速度为零时，两种苍算出的水平加速度都是 `1600`，均未被限幅。最大速度也仍是 `480`。因此“范围翻倍”成立，“吸力翻倍”只落实为上限参数翻倍。

   **最小改法：** 如果需求指实际吸引加速度翻倍，对未限幅的吸引向量也应用倍率，再做相应限幅。如果需求仅指最大加速度上限，则当前实现可接受，但需要明确这一解释。

4. **P2：苍的飞行位置没有插值，90Hz 下移动步幅不均匀**

   **位置：** [World.java:301](/home/user/codex-remotion-project/android-shinjuku/core/src/main/java/com/shinjuku/showdown/core/World.java:301)、[BattleRenderer.java:229](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/BattleRenderer.java:229)、[BattleRenderer.java:420](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/BattleRenderer.java:420)。

   **触发条件：** 苍飞行期间，显示帧与逻辑 tick 不整齐对齐，尤其是 90Hz。

   **后果：** 人物位置使用 `alpha` 插值，苍却直接画最新的 `b.x/b.y`。90Hz 对应正常的 `1、1、2` tick 循环，苍因此按不均匀步幅移动；超过 120Hz 时还会重复位置。可以确认位置采样不均匀，实际肉眼明显程度未做真机验证。

   **最小改法：** 为苍保存上一 tick 的位置，用同一个 `alpha` 插值；生成、落地时同步初始化前后位置。

5. **P3：Bgm.release() 不退出 bgm HandlerThread**

   **位置：** [Bgm.java:55](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/Bgm.java:55)、[Bgm.java:111](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/Bgm.java:111)、[MainActivity.java:96](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/MainActivity.java:96)。

   **触发条件：** 主页结束并调用 `bgm.release()`，应用进程继续存活。

   **后果：** 播放器被释放，但线程仍在等待消息，且线程引用未保存，无法退出。这是固定一个线程的残留，**不会随进入战斗次数增长，也未形成 Activity 泄漏**。

   **最小改法：** 若 `release()` 表示最终销毁，保存线程引用，在清理完成后 `quitSafely()`，同时处理 singleton 的后续重建；若刻意让线程伴随整个进程存活，应将该方法明确为“释放播放器”。

**确认没有问题的点**

- **Surface 销毁同步：** `surfaceLock` 覆盖 `lockHardwareCanvas→draw→unlockCanvasAndPost`；`surfaceGone()` 在同一锁内清空 holder。销毁返回后，旧 Surface 不会再被这条绘制路径访问。
- **退出顺序：** battle 线程先移除帧回调，再 `renderer.release()`、`quitSafely()`；正常生命周期下未见释放位图后继续绘制的路径。角色位图最终可随对象被 GC 回收，未确认永久泄漏。
- **发布与可见性：** `Layout` 构造完成后通过 `volatile` 发布，数组也在发布前填好；摇杆逻辑向量打包为一个 `volatile long`，不会读到混合的两个分量。World 与渲染在同一线程。
- **固定步长：** 理想 60/120Hz 分别稳定为每帧 2/1 tick；90Hz 的 `1、1、2` 属于正常比例。人物的前后位置插值公式正确；恢复时不会补算暂停时间。
- **机制：** 无限会保留阻挡表现并屏蔽伤害、冲量、硬直，三种绕过均要求标志和世界状态同时成立；体术 50、黑闪 350、PRD 长期概率 15% 且第 32 次必出；苍有投距限制、向中心吸引、距离伤害最高 100/s、长按范围翻倍和额外前摇；赫直接 150 并击飞；宿傩没有技能或 AI。
- **稳态性能：** 未发现应用代码逐帧的装箱、字符串拼接、迭代器或 lambda 分配。渐变和滤镜预建、线段批量绘制，battle 设置了 DISPLAY 优先级。首帧及布局变化会烘焙位图并分配对象；是否造成掉帧，以及 Canvas 锁、文字阴影、渐变、圆弧的实际成本，静态审计无法确认。

## 第二轮（复核修改）

结论：修改尚未完全正确，确认仍有 4 处问题；普通事件环的内存发布顺序、时间基准和苍插值未发现问题。

1. **[Controls.java:115](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/Controls.java:115)：overflow 重同步不是一致快照。**  
   **触发：**战斗线程执行 `evRead = evWrite` 后，主线程可以继续更新 `held` 并入队；随后读取的 `held` 可能已包含仍留在队列里的新事件。`overflow = false` 也可能覆盖主线程新写入的溢出通知。  
   **后果：**按住状态与待消费边沿不对应，可能提前松开苍、重复解释状态；丢失的新溢出通知还会使后续重同步缺席。每个字段使用 volatile/原子访问不能让整个恢复过程原子化。  
   **最小改法：**溢出恢复使用与生产者互斥的短临界区，同步取得写指针和按住状态并清除通知；若坚持无锁，则需要带版本号、由生产者发布的一致恢复快照及确认协议。

2. **[World.java:83](/home/user/codex-remotion-project/android-shinjuku/core/src/main/java/com/shinjuku/showdown/core/World.java:83)：停顿里锁存的苍按下仍会被提前清掉。**  
   **触发：**真实黑闪发生时五条悟处于 `MELEE`；停顿期间按苍，恢复后的第一次 `controlGojo()` 先清空锁存，再进入 `MELEE` 分支。  
   **后果：**这次按下永久丢失，即使一直按住，回到 `FREE` 也不会开始蓄力。现有测试人工设置停顿且保持 `FREE`，没有覆盖真实场景。  
   **最小改法：**为苍按下设置有期限的输入缓冲，在可消费或明确取消时清除；不要在检查动作状态之前无条件清空。

3. **[World.java:76](/home/user/codex-remotion-project/android-shinjuku/core/src/main/java/com/shinjuku/showdown/core/World.java:76)：苍的布尔锁存再次合并了事件顺序。**  
   **触发：**已有 `BLUE_HOLD`，停顿期间先松开，再重新按住；恢复时两个 latch 都为 true，`blueHeld` 也为 true。  
   **后果：**第 122 行仍因旧 `blueUp` 进入普通苍前摇，新按下被一起清掉。Controls 保留的顺序到了 World 又丢失。  
   **最小改法：**停顿期间保存苍的有序边沿，恢复后按序消费；两个布尔值不足以表达“松开→再按下”和“按下→松开”的区别。

4. **[World.java:120](/home/user/codex-remotion-project/android-shinjuku/core/src/main/java/com/shinjuku/showdown/core/World.java:120)：停顿期间的取消输入没有参与恢复后的取消判断。**  
   **触发：**处于 `BLUE_HOLD` 时停顿，期间按跳、体术或赫，恢复前该输入边沿已清除。  
   **后果：**虽然 `latch()` 保存了对应缓冲，取消分支仍只检查 `in.jump/melee/red`，苍继续蓄力甚至进入最大输出，其他攻击缓冲随后过期。  
   **最小改法：**取消判断使用已锁存的输入意图，并明确处理取消后对应缓冲的消费，避免重复执行。

其余重点的核对结果：

- **普通 SPSC 路径正确：**数组写入先于 `evWrite` 的 volatile 发布；消费者读取 `evWrite` 后读槽位，并在读取完成后发布 `evRead`，正常满环不会覆盖未读槽位。
- **时钟基准一致：**Android 的触摸事件时间和 Choreographer 帧时间使用同一 uptime/单调时钟体系，毫秒转纳秒只损失精度。[MotionEvent 文档](https://developer.android.com/reference/android/view/MotionEvent)、[AOSP Choreographer](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/view/Choreographer.java)
- **`limitNs` 未发现永久饿死或队列乱序：**最后一个 tick 的 `Long.MAX_VALUE` 会放行时间限制；重复边沿造成的是队头顺延。`FAR_AHEAD_NS` 会提前消费超前至少 250ms 的事件，但正常同源时钟下无需这个兜底。
- **最大输出吸引、苍位置插值和 HUD 描边未发现新增问题。Bgm 线程仍不退出，但已是进程级单例复用，不再随反复进入页面累积线程。**

## 处理结果

第一轮：
1. 停顿期间丢键 → World 在停顿判断之前先接收输入（体术、赫、跳的缓冲照常记；苍的按下/松开进有序队列）。
2. 计数器合并按键 → 改成按时间排序的预分配事件环（单写单读），每个 tick 同一个键最多一次按下加一次松开，其余顺延；帧内最后一个 tick 取完已到的事件，不加延迟。
3. 出力最大吸力只翻倍上限 → 整个吸引 ×2（加速度上限、跟随强度、目标速度），测试确认同样相对位置的实际加速度正好 2 倍。
4. 苍飞行没插值 → 保存上一 tick 位置，和人物一样按 alpha 插值。
5. Bgm 线程不退出 → 有意为之（进程级单例，只有一个线程，下次进来复用），改了注释说明。
另外把 HUD 文字的 setShadowLayer（每帧模糊字形）换成了描边。

第二轮：
1. 溢出重同步不一致 → 主线程“改按住状态 + 入队”放在同一把锁里，战斗线程只在溢出恢复时拿锁（平时无锁）。
2、3. 苍的布尔锁存被提前清掉、合并顺序 → 换成有序小队列，每个按下有 0.12 秒有效期（和其他缓冲一样，停顿期间不计时），只有能用上的状态才取。
4. 停顿期间的取消没参与判断 → 蓄苍时看缓冲（体术/赫/跳），进入蓄力时清掉更早的缓冲（最新的意图是苍）。
第二轮的 2–4 目前触发不了（命中停顿只出现在体术里，蓄苍时不会停顿），为以后宿傩的攻击也带停顿先修好，有对应的单元测试。
