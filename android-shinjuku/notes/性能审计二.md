1. **P1：RenderNode 对象存在，不代表显示列表仍然有效**

   **位置：** `ShinjukuView.java:154–161、263–264、374`

   当前只判断 `staticNode != null`。系统可以在节点不再被绘制时自动丢弃显示列表；这种情况下节点仍存在，但 `drawRenderNode()` 不产生内容。当前 attach 检查也无法覆盖“未 detach、显示列表已失效”的情况，可能出现楼群和天空消失、动态元素继续绘制。

   官方要求通过 `hasDisplayList()` 判断是否需要重新录制。[RenderNode 文档](https://developer.android.com/reference/android/graphics/RenderNode#hasDisplayList())

   **具体改法：** 在硬件重放前检查有效性；录制使用 `try/finally`。建议把“创建节点”和“录制已有节点”分开，恢复时无需重建星星、火星等数据。

   ```java
   // API 29+；在硬件重放分支中执行
   if (!staticNode.hasDisplayList()) {
       RecordingCanvas rc = staticNode.beginRecording(w, h);
       try {
           drawStatic(rc, w, h);
       } finally {
           staticNode.endRecording();
       }
   }
   c.drawRenderNode(staticNode);
   ```

   现有 `drawStatic()` 会重新生成 `windows/offPts`，因此恢复录制属于允许分配的慢路径。进一步可将场景数据生成与绘制分离，避免恢复时重复生成。

2. **P1：FrameStatsView 没有完整的暂停、可见性和重新 attach 管理**

   **位置：** `FrameStatsView.java:40–47、56–81、97–99`；`MainActivity.java:57–67`

   打开监视后：

   - `onPause()` 只停止背景，面板仍不断请求 Choreographer 回调，增加无意义唤醒。
   - 隐藏窗口不会主动移除其回调。
   - detach 移除回调后，`on` 仍为 `true`，重新 attach 不会恢复测量。
   - 停顿后的首个间隔可能把后台时间计入“最差帧”。
   - `toggle()` 未清零 `frames/janky/worst`，再次打开会混入上一轮未完成的统计窗口。

   **具体改法：** 将用户开关、Activity resumed、聚合可见性共同作为运行条件；所有入口调用同一个同步方法。

   ```java
   private boolean resumed, aggregatedVisible;

   private void resetWindow() {
       last = windowStart = worst = 0;
       frames = janky = 0;
   }

   private void syncSampling() {
       Choreographer ch = Choreographer.getInstance();
       ch.removeFrameCallback(this);
       resetWindow();
       if (on && resumed && aggregatedVisible && isAttachedToWindow()) {
           ch.postFrameCallback(this);
       }
   }
   ```

   `toggle()`、`onVisibilityAggregated()`、attach/detach 和新增的 `setResumed()` 都调用它；Activity 在 resume/pause 传入状态。`doFrame()` 开头也检查相同条件，避免停止后收到的尾回调继续挂链。

3. **P1：面板显示的是回调频率，不是实际渲染 FPS；“最差耗时”和“掉帧”命名不准确**

   **位置：** `FrameStatsView.java:58–74`

   `now - last` 是相邻 Choreographer 帧时间戳的间隔，并不是这一帧的执行耗时。即使背景停止绘制，面板自身仍可以获得接近刷新节奏的回调；GPU 或 SurfaceFlinger 未按时呈现，也未必被这个算法识别。

   `janky++` 统计的是**超阈值间隔次数**。一次间隔跨过多个刷新周期也只加一，不能称为丢失帧数。`1.5 × period` 作为固定节奏下识别跨周期的启发式可以使用，但刷新率切换、主动降帧时会失真。

   **具体改法有两个层级：**

   ```java
   // 保留现有实现时，首先修正读数名称
   line1 = String.format(Locale.ROOT,
           "回调 %.0f Hz / Display %.0f Hz", fps, refreshHz());
   line2 = String.format(Locale.ROOT,
           "最大间隔 %.1f ms  超阈值 %d", worst / 1e6f, janky);
   ```

   若要测窗口实际产出的帧，使用 `Window.OnFrameMetricsAvailableListener`；API 31+ 可比较有效的 `TOTAL_DURATION` 与 `DEADLINE`：

   ```java
   long duration = metrics.getMetric(FrameMetrics.TOTAL_DURATION);
   if (Build.VERSION.SDK_INT >= 31) {
       long deadline = metrics.getMetric(FrameMetrics.DEADLINE);
       if (duration >= 0 && deadline > 0 && duration > deadline) {
           // 记录应用帧超时；不等同于最终呈现掉帧
       }
   }
   ```

   回调中只聚合数值，注意报告对象会复用、统计投递也可能丢失。最终呈现是否错过预期时间，用 Perfetto FrameTimeline 判定。[FrameMetrics](https://developer.android.com/reference/android/view/FrameMetrics)、[FrameTimeline](https://github.com/google/perfetto/blob/main/docs/data-sources/frametimeline.md)

   `refreshHz()` 每帧读取一次、统计更新时再读一次没有必要；可以监听显示变化并缓存。但 `Display.getRefreshRate()` 仍不能直接作为“背景应当每秒绘制多少帧”的依据。

4. **P2：全尺寸 Bitmap 回退缺少内存上限，软件截图还会留下长期缓存**

   **位置：** `ShinjukuView.java:163–164、249–251、266–270`

   ARGB_8888 像素内存约为 `w × h × 4`：

   | 尺寸 | 单张像素内存 |
   |---|---:|
   | 1080 × 2400 | 9.9 MiB |
   | 1440 × 3200 | 17.6 MiB |
   | 3840 × 2160 | 31.6 MiB |

   API 26–28 还可能有 GPU 上传纹理占用；首次软件绘制和上传都可能造成卡顿。API 29+ 一次软件 `View.draw()` 后，位图会与 RenderNode 一直共存到尺寸变化或 detach。尺寸连续变化时会反复创建大对象，存在低内存设备 OOM 风险。

   此外，`recycle()` 没有证明旧位图已经退出 View 的缓存绘制命令。**不能据此断言当前必崩**，但官方明确建议避免主动回收仍可能被 View 引用的位图。[Bitmap.recycle](https://developer.android.com/reference/android/graphics/Bitmap#recycle())

   **具体改法：**

   ```java
   // releaseStatic()：API 26+ 优先交给引用生命周期回收
   staticBitmap = null;
   ```

   同时给缓存设像素预算，超出预算时降采样，不能只移除 `recycle()` 而继续无上限分配：

   ```java
   long pixels = (long) w * h;
   double scale = Math.min(1.0,
           Math.sqrt(2_000_000.0 / pixels)); // 示例预算，按画质验证调整
   int bw = Math.max(1, (int) Math.ceil(w * scale));
   int bh = Math.max(1, (int) Math.ceil(h * scale));

   Bitmap bitmap = Bitmap.createBitmap(bw, bh, Bitmap.Config.ARGB_8888);
   Canvas bc = new Canvas(bitmap);
   bc.scale((float) scale, (float) scale);
   drawStatic(bc, w, h);
   ```

   重放时用预建的目标 `Rect` 和开启过滤的 `Paint` 拉伸回 View 尺寸。软件截图若很少发生，可直接绘制静态内容，避免持有另一张全屏缓存；相应初始化分配属于截图慢路径。

5. **P2：RenderNode 省了 UI 线程录制，不代表静态背景在 GPU 上只画一次**

   **位置：** `ShinjukuView.java:169–241、263–340`

   当前每次背景 `onDraw()` 的绘制调用上限为：

   | 内容 | Canvas 绘制调用 |
   |---|---:|
   | 静态节点或 Bitmap | 1 |
   | 星星 | 6 |
   | 光束 | 8 |
   | 交锋光晕 | 1 |
   | 航空灯 | 2 |
   | 灭窗覆盖 | 0–1 |
   | 红雾 | 1 |
   | 火星 | 1–4 |
   | **合计上限** | **24** |

   这是 Java 层绘制调用数，**不是 GPU draw call 数**。静态节点内部仍包含 `10 + 远楼数 + 近楼数 + 亮窗数` 条绘制操作；显示列表重放会继续处理这些内容，并非自动变成一张缓存纹理。

   最大的面积成本是全屏天空重绘；最大的宽幅透明覆盖是底部 **28% 高度的红雾**。光束附近存在四层嵌套混合，光晕与其重叠；按钮透明背景也会继续混合。HWUI 可能合批或剔除部分操作，最终成本须用真机确认。

   **具体改法：** 这个慢速主页动画值得优先尝试 60fps。API 35+ 可以表达偏好：

   ```java
   if (Build.VERSION.SDK_INT >= 35) {
       scene.setRequestedFrameRate(60f);
   }
   ```

   但这是刷新率偏好，**不是绘制限速器**；ARR 还取决于设备支持。若要控制自身重录频率，用一个 Choreographer 调度器按绝对时间决定是否 `invalidate()`，同时移除 `onDraw()` 末尾的自调度：

   ```java
   private long nextDrawNs;

   // 在唯一的 FrameCallback 中；生命周期入口负责挂起和移除回调
   long period = 1_000_000_000L / 60;
   if (nextDrawNs == 0 || frameTimeNanos >= nextDrawNs - 500_000L) {
       invalidate();
       if (nextDrawNs == 0) nextDrawNs = frameTimeNanos;
       do {
           nextDrawNs += period;
       } while (nextDrawNs <= frameTimeNanos);
   }
   // 仅运行条件成立时 postFrameCallback(this)
   ```

   停止或恢复时清零 `nextDrawNs`。这种方法仍有每次 VSync 的轻量回调，但减少背景录制；不要在 `onDraw()` 中直接提前返回来“保留上一帧”，硬件显示列表重新录制时可能把内容清掉。90Hz 显示下固定 60fps 还存在不均匀节奏，需要请求合适的显示刷新率。[ARR 文档](https://developer.android.com/develop/ui/views/animations/adaptive-refresh-rate)、[AOSP 多刷新率机制](https://source.android.com/docs/core/graphics/multiple-refresh-rate)

   **关于 `appCategory=game`：** Android 15 官方策略是游戏默认 60Hz，需要显式请求更高帧率。Android 16 上也不能仅凭设备支持 120Hz 就假设当前窗口运行在 120Hz；用户设置、厂商策略、温控和省电都会影响结果。当前主页无需为测试而主动申请 120Hz。[游戏刷新率官方说明](https://developer.android.com/games/optimize/display-refresh-rate-change)

6. **P2：动画开关只在 resume 读取，前台动态关闭动画时背景可能继续运行**

   **位置：** `MainActivity.java:53、60`；`ShinjukuView.java:261、349–353`

   `areAnimatorsEnabled()` 的 API 和调用条件正确，minSdk 26 足够。但它只是查询，不会让自定义绘制循环自动跟随设置变化。前台打开省电模式等情况下，背景可能继续耗电到下一次 resume。

   **具体改法：** API 33+ 在 resumed 期间注册缩放变化监听，pause 时解除；旧版本如要求即时响应，可在运行期间低频重新检查。

   ```java
   // API 33+，保存为字段；onResume 注册、onPause 解除
   private final ValueAnimator.DurationScaleChangeListener scaleListener =
           scale -> scene.setAnimating(ValueAnimator.areAnimatorsEnabled());
   ```

   官方说明监听在主线程执行；`areAnimatorsEnabled()` 也可能受省电模式影响。[ValueAnimator 文档](https://developer.android.com/reference/android/animation/ValueAnimator)

   另一个语义问题：停止调度并没有冻结动画时间。外部触发重绘时，`t` 仍继续增长；恢复后会跳到当前墙钟位置。如果确实要求“停在当前帧、恢复后接着播放”，应累计活动时长：

   ```java
   double t = (accumulatedMs
           + (running ? SystemClock.uptimeMillis() - runStartMs : 0L))
           / 1000.0;
   ```

   `running` 应统一由 resumed、可见和动画许可决定。

7. **P3：Toast 节流仍可能排队，pause 只取消最近一个实例**

   **位置：** `MainActivity.java:18、33–38、66`

   `LENGTH_SHORT` 的持续时间不是 1500ms 的契约；每隔 1.5 秒创建一个新 Toast，仍可能让前一个尚未结束时又提交一个。字段只保留最近实例，pause 不能可靠覆盖先前已提交的实例。

   **具体改法：** 采用更保守的节流间隔，并在允许下一次展示时先取消旧实例：

   ```java
   if (now - toastAt < 2500L) return;
   toastAt = now;
   if (toast != null) toast.cancel();
   toast = Toast.makeText(this, R.string.not_open, Toast.LENGTH_SHORT);
   toast.show();
   ```

   pause 后同时 `toast = null`。当前 `uptimeMillis()` 做节流、首击负初值和 pause 主动取消的方向均正确。

8. **P3：短窗口适配仍有下限，面板也没有遵守父布局测量约束**

   **位置：** `res/layout/activity_main.xml:12–94、103`；`res/values/dimens.xml:4–9`；`FrameStatsView.java:85–86`

   三个固定高度按钮、标题、间距加起来仍存在最小内容高度。分屏窗口足够矮或字体放大时，权重 Space 缩到零也无法容纳内容；固定按钮宽度也可能超过极窄窗口。`h600dp` 资源不能覆盖所有情况。

   面板固定顶部 44dp 也未使用安全 inset，部分刘海窗口会遮挡；其 `onMeasure()` 直接返回 230×44dp，忽略 `AT_MOST/EXACTLY`。

   **具体改法：**

   ```java
   setMeasuredDimension(
           resolveSize(Math.round(230 * dp), wSpec),
           resolveSize(Math.round(44 * dp), hSpec));
   ```

   内容改为可滚动容器，并给内部内容保留正常高度时的居中布局；按钮宽度限制在可用窗口内。面板边距依据实际顶部安全 inset 设置，避免固定猜测状态栏高度。

已确认没问题的部分：

- **RenderNode 尺寸、软件画布判断和常规重建：** `ShinjukuView.java:158–159` 同时设置节点位置与 recording viewport，正确；`263` 检查实际 Canvas 的硬件加速状态，软件画布不会误调用 `drawRenderNode()`。尺寸变化会重建，detach 会清理，同尺寸重新 attach 也有恢复入口；剩余缺口是第 1 条的显示列表有效性检查。
- **背景热路径 Java 分配：** `276–340` 没有装箱、字符串格式化、新 lambda 或集合迭代器；`for (float[] e : embers)` 是数组遍历，不产生 Iterator。`drawPoints()` 确实合并了应用层调用，但底层仍会复制或记录点数据，不能扩展成“整个图形栈零分配”。首次软件回退明确属于分配慢路径。
- **double 时间：** `261` 先用 long 相减再除以 `1000.0`；三角函数参数与火星取模使用 double，最后才转换到 float，已解决原先长期运行的 float 时间精度问题。
- **背景调度链：** `343–361` 不会因多次 invalidation 形成指数增长的独立循环；最终由 ViewRoot 合并遍历。pause 后可能还有一次已提交的尾重绘，但不会继续挂链；可见性变化和 resume 两种顺序均有启动入口。注释可改成“重复失效请求最终合并为绘制”，更准确。
- **RadialGradient 缩放：** `295–298` 的 `save/scale/restore` 只是坐标变换，没有使用 `saveLayer()`，不会因此额外创建离屏纹理。主要代价仍是光晕覆盖像素的着色与混合。
- **Insets 两条路径：** `MainActivity.java:85–114` 的 API 26–29 system-window inset、API 28+ cutout 取最大值，以及 API 30+ `systemBars | displayCutout` 均合理；保存原始 padding 避免重复累加，返回原 insets 也正确。旧系统若希望背景真正延伸到刘海区域，还需配置相应 cutout mode；当前属于视觉覆盖差异。
- **进场 `withLayer()`：** 仅用于五个较小的静态内容 View，没有给持续变化的全屏背景建硬件层；临时层会恢复原状态。初始化数组、插值器和 lambda 是一次性分配，可以接受。[ViewPropertyAnimator 文档](https://developer.android.com/reference/android/view/ViewPropertyAnimator#withLayer()) 当前 pause 未取消进场动画，最多继续短暂运行；可在 pause 中 `cancel()` 后显式恢复 `alpha=1、translationY=0`，不要仅取消而留下半透明控件。
- **面板格式化：** 每 500ms 两次 `String.format()` 会产生 varargs、装箱和字符串，但作为手动开启的调试面板可以接受；它不在 `onDraw()` 中，也没有触发布局。优先修正统计口径与生命周期。
- **Android 16 方向限制：** `AndroidManifest.xml:6、16` 的 `game` 分类属于官方列出的例外；不能认定 `targetSdk=36` 会让这里的 portrait 必然失效。仍须适配用户或设备强制调整窗口的情况。[Android 16 行为变更](https://developer.android.com/about/versions/16/behavior-changes-16#large-screens)
- **资源与构建配置：** 原生 Button、最小 50dp 高度、关闭按压抬升、release R8 和资源压缩均合理。当前没有反射或 JNI 入口需要额外 keep；XML 自定义 View 的引用属于标准构建工具处理范围。`gradle.properties` 中这些开关没有引入运行时性能问题。启动图标、颜色和字符串未发现相关崩溃或持续绘制风险。
