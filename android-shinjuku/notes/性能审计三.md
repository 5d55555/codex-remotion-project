1. **P1：`prepared` 不能覆盖原生 Error 状态，运行期调用缺少异常保护**

   位置：[Bgm.java:129](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/Bgm.java:129)、137、143、147、166、173、191。

   **触发条件：**播放器原生端已经出错，但 Java `onError` 尚未处理，此时点击、切后台或收到焦点回调。

   **问题与后果：**

   - Java 的 `prepared` 仍可能为 `true`，继续调用 `seekTo/start/pause/isPlaying/setVolume`。
   - 非法状态可能报告异步错误，部分调用也可能抛 `IllegalStateException`；当前没有兜底，工作线程上的未捕获异常可能导致应用崩溃。
   - 重建进入 Preparing 后，GAIN／CAN_DUCK 只检查 `player != null` 就调用 `setVolume`。官方明确指出 Preparing 期间调用有副作用的方法，其行为未定义。
   - `onError` 缺少 `mp == player` 校验；无条件立即重建还会在持续解码错误时形成重试循环。
   - `new MediaPlayer()` 在 `try` 外；创建失败也无法进入现有恢复路径。

   **具体改法：**显式维护 `PREPARING/READY/STARTED/PAUSED/ERROR`；正常路径靠状态判断，异常路径统一处理。不要用 `isPlaying()` 充当状态机。

   ```java
   private void applyVolume() {
       if (player == null || !prepared) return;
       try {
           player.setVolume(ducked ? DUCK_VOLUME : VOLUME,
                            ducked ? DUCK_VOLUME : VOLUME);
       } catch (IllegalStateException e) {
           failCurrentPlayer(e);
       }
   }

   @Override public boolean onError(MediaPlayer mp, int what, int extra) {
       if (mp != player) return true;
       failCurrentPlayer(null); // 清状态、release、记录 what/extra
       return true;
   }
   ```

   `seek/start/pause` 同样集中封装。`failCurrentPlayer` 应限制重试次数、延迟重试，且后台不自动反复创建；下次用户点击允许重新尝试。`create()` 的异常要记录，不能静默吞掉；将构造也放入 `try`，失败时清除所有就绪状态。

   这些合法状态与 Preparing 限制已核对[官方 MediaPlayer 状态表](https://developer.android.com/reference/android/media/MediaPlayer#Valid_and_invalid_states)。

2. **P1：重播意图会丢失，恢复逻辑也可能绕过未完成的 seek**

   位置：[Bgm.java:66](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/Bgm.java:66)、120、124、133、140。

   **触发条件一：**已播放过的播放器发生重建或临时丢焦点；用户点击后进入后台，等准备完成／命令执行时 `hostPaused == true`。

   `startFromZero()` 直接返回，没有保存“下次必须从零”的独立意图。回前台走 `resumeIfWanted()`，可能直接续播旧位置。

   **触发条件二：**点击发出 seek，随后快速切后台再返回，或 seek 期间经历 TRANSIENT→GAIN。

   `resumeIfWanted()` 不检查 `startAfterSeek`，可以在 seek 完成前 `start()`，与注释承诺相反。单个 `startAfterSeek` 也无法准确表达“正在 seek”和“还有更新的点击”。

   **具体改法：**独立保存 `restartPending` 与 `seeking`，让点击、准备完成、前台恢复、焦点恢复统一经过一个入口。为保证等待 seek 时不继续播旧内容，可先暂停：

   ```java
   // 均仅由 bgm 线程访问
   private boolean restartPending, seeking;

   // 点击命令中：
   wanted = true;
   restartPending = true;
   if (player == null) create();
   drivePlayback();

   private void drivePlayback() {
       if (!prepared || !wanted || hostPaused || !focusUsable || seeking) return;

       if (restartPending) {
           restartPending = false;
           pauseIfStarted();       // 使用自己维护的 STARTED 状态
           seeking = true;
           seekSafelyToZero();      // 内含异常恢复
       } else {
           startIfReadyOrPaused();
       }
   }

   @Override public void onSeekComplete(MediaPlayer mp) {
       if (mp != player || !seeking) return;
       seeking = false;
       drivePlayback(); // 有更新点击则再 seek；后台/无焦点则保持暂停
   }
   ```

   **当前播放中调用 seek 本身是合法的，且不会把 Started 改成 Paused，因此正常情况下会继续播放。**现有 `onSeekComplete` 的“不重复 start 已播放实例”在单次正常时序下成立。另需明确：MediaPlayer 会合并尚未处理的 seek，不能承诺连点次数与 seek 回调次数一一对应。[官方 seekTo 说明](https://developer.android.com/reference/android/media/MediaPlayer#seekTo(long,%20int))

3. **P1：临时失焦仍把 `hasFocus` 当作播放授权，点击和错误恢复可绕过暂停**

   位置：[Bgm.java:126](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/Bgm.java:126)、150、175、179、191。

   **触发条件：**播放→LOSS_TRANSIENT→点击，或 LOSS_TRANSIENT 后播放器出错并重建。

   `LOSS_TRANSIENT` 保留 `hasFocus = true`；随后 `requestFocus()` 直接返回成功，`startFromZero()` 又清除 `focusPaused`。因此并未重新取得可播放焦点，就可能恢复播放。错误重建后的 `onPrepared→startFromZero` 也存在同样问题。

   **具体改法：**区分“焦点请求仍登记着”和“当前允许播放”；临时失焦时保留登记，撤销播放授权，GAIN 才恢复。

   ```java
   case AudioManager.AUDIOFOCUS_LOSS_TRANSIENT:
       focusUsable = false;
       focusPaused = true;
       pauseIfStarted();
       break;

   case AudioManager.AUDIOFOCUS_GAIN:
       focusUsable = true;
       focusPaused = false;
       ducked = false;
       applyVolume();       // 仅在就绪状态实际调用 MediaPlayer
       drivePlayback();
       break;
   ```

   临时失焦期间点击可以保留 `restartPending`，等待 GAIN；如果选择主动重新申请，也必须真实调用 `requestAudioFocus` 并检查返回值。

   永久 LOSS 当前确实会暂停，但注释“回到前台再播”不成立：`focusPaused` 会让 `resumeIfWanted()` 提前返回。建议永久 LOSS 清除自动续播意图，等下一次明确点击。官方也要求永久失焦后由用户明确操作重新开始。[官方焦点指南](https://developer.android.com/media/optimize/audio-focus)

   当前把 `hasFocus` 先设为 `false`，之后 `abandonFocus()` 就不会实际 abandon。建议用独立的 `focusRegistered` 记录已成功登记的请求，永久 LOSS／release 时明确清理：

   ```java
   case AudioManager.AUDIOFOCUS_LOSS:
       pauseIfStarted();
       wanted = false;
       restartPending = false;
       focusUsable = false;
       focusPaused = false;
       abandonRegisteredFocus();
       break;
   ```

   CAN_DUCK 后保留播放、降至 0.25 倍是合理策略；Android 8+ 也可能由系统自动 duck，根本不发该回调。需要新增 `ducked` 状态，成功重新获取焦点时显式恢复音量，避免依赖一次未必到达的 GAIN。

4. **P2：FrameStats 的统计被面板自身污染，且忽略报告丢失**

   位置：[FrameStatsView.java:45](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/FrameStatsView.java:45)、140、149、173。

   **触发条件：**关闭系统动画、背景停止，或统计线程忙碌。

   **问题与后果：**

   - `tick` 每 500 ms `invalidate()`，自身持续制造窗口帧。`lastFrameAtMs` 因这些帧更新，“静止：没有新帧”通常无法可靠出现。
   - `dropped` 是**遗漏的统计报告数**，当前完全忽略，因此可能低报 FPS，也无法知道最慢帧／超时数是否完整。
   - 时间窗口由回调到达时间决定，线程积压会使短时 FPS 失真。
   - `shownFps/shownFrames/shownWorstMs/shownOverruns` 分别 volatile，不能保证 UI 读到同一批结果。

   **具体改法：**明确显示“窗口帧率，含面板刷新”；取消“没有新帧”的确定性断言。累计遗漏报告，FPS 用采样帧的 `INTENDED_VSYNC_TIMESTAMP` 时间跨度，结果通过一个不可变快照发布：

   ```java
   private volatile Snapshot shown;

   // stats 线程
   reportsLost += dropped;
   // 累计时间戳、样本数、worst、overruns
   shown = new Snapshot(fps, samples, worstMs, overruns, reportsLost);

   // onDraw 主线程
   Snapshot s = shown;
   ```

   遗漏的报告无法恢复其耗时，不能直接算成“掉帧”或补进超时数。官方明确说明报告可能丢失，且 `FrameMetrics` 对象会被复用；当前在回调内立即读取数值、不保存对象是正确的。[官方监听器说明](https://developer.android.com/reference/android/view/Window.OnFrameMetricsAvailableListener)

   `TOTAL_DURATION` 对比 API 31+ `DEADLINE` 的方向正确；旧版本用刷新周期只能标成近似预算。[官方 FrameMetrics 说明](https://developer.android.com/reference/android/view/FrameMetrics#DEADLINE)

5. **P2：刷新率只在启动统计／恢复动画时读取，运行中变频后分频和显示失准**

   位置：[ShinjukuView.java:413](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/ShinjukuView.java:413)、[FrameStatsView.java:104](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/FrameStatsView.java:104)。

   **触发条件：**同一次 resumed 期间，系统从 60 Hz 切换到 120 Hz，或反向切换。

   背景可能从目标 60 FPS 变成 120 FPS，或从 60 FPS 降为 30 FPS；面板 Hz 和旧系统超时预算也保持旧值。静态 60/90/120/144 Hz 下，当前分频计算符合注释。

   **具体改法：**前台注册 `DisplayManager.DisplayListener`，离开时移除；显示变化后在主线程更新分频，并向 stats 线程投递预算更新：

   ```java
   private void updateRefreshRate() {
       Display d = getDisplay();
       float hz = d == null ? 60f : d.getRefreshRate();
       vsyncDivisor = Math.max(1, (int) (hz / 60f + 0.25f));
       vsyncCount = 0;
   }

   // FrameStats：主线程保存 UI 用值，统计线程保存统计用值
   refreshHz = hz;
   statsHandler.post(() -> statsRefreshHz = hz);
   ```

7. **P3：命令线程使用 AUDIO 优先级过高；首次初始化并非完全不阻塞主线程**

   位置：[Bgm.java:38](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/Bgm.java:38)、[Bgm.java:43](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/Bgm.java:43)、45；[MainActivity.java:39](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/MainActivity.java:39)。

   音频解码和实时输出不由这个 HandlerThread 执行；它只处理控制命令及 Binder 调用，通常使用默认优先级即可：

   ```java
   HandlerThread thread = new HandlerThread("bgm");
   ```

   MediaPlayer 资源读取、准备、seek、start、pause、release 都没有直接堵塞 UI；但首次 `Bgm.get()` 在主线程启动线程，`getLooper()` 会等待 Looper 初始化，此外构造中还获取 AudioManager。因此“所有入口只投递、不阻塞”表述过强。

   `decorView.post()` 也不保证第一帧已经画完。若要尽早准备，直接 `bgm.prepare()` 即可；若确实要求首帧后开始，应使用帧提交回调并做版本兜底。

其他已确认的结论：

- **回调线程正确。**`new MediaPlayer()` 在 bgm HandlerThread 上，其已有 Looper；`onPrepared/onSeekComplete/onError` 会回到该 Looper，并非一律主线程。AOSP 构造优先使用 `Looper.myLooper()`，缺失时才回退主 Looper。焦点监听也显式指定了 bgm Handler。现有播放器及播放布尔字段没有发现跨线程直接读写。[AOSP MediaPlayer 源码](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/master/media/java/android/media/MediaPlayer.java)
- **提前点击正常路径成立。**准备前点击设置 `wanted`，完成后启动；准备期间连点不会反复创建播放器。但需按第 2 项补齐后台与恢复时序。
- **点击后进入后台，已执行 pause 后的 seek 完成本身不会自动重新播放。**现有 `onSeekComplete` 检查 `hostPaused/focusPaused`，这部分正确。异步投递意味着 `onPause` 到命令执行之间仍有短暂窗口。
- **Android 15+ 的前台限制与调用线程无关。**要求是应用处于 top app 或运行合适的前台服务；`onResume` 后在 bgm 线程请求可以合法成功。但 Runnable 执行时应用可能已离开前台，所以必须检查返回值，不能把曾经 onResume 当作保证。当前失败后不启动是正确的；不要在后台循环重试。[官方限制](https://developer.android.com/media/optimize/audio-focus#android_12)
- **Activity 配置重建和 finish 后重进，普通路径可用。**单例只持 Application Context；配置重建不 release，旧 Activity pause、新 Activity resume 会继续播放。finish 后 `player = null`、`prepared = false`，HandlerThread 保留，所以后续 prepare 能重新创建。建议 release 同时重置全部播放／焦点状态，避免残留语义。
- **RenderNode 修改正确。**绘制前检查 `hasDisplayList()`，失效重录，`endRecording()` 放 finally，并仅在硬件 Canvas 上绘制，符合[官方要求](https://developer.android.com/reference/android/graphics/RenderNode#hasDisplayList())。软件 Canvas 的直接绘制兜底也成立，但它每帧会分配，不能把“零分配”承诺扩展到软件路径。
- **Choreographer 单链调度成立。**`scheduled` 防止重复注册，暂停时移除；动画时钟停下后冻结。分频减少绘制次数，但仍每个 vsync 回调，属于轻量开销。
- **FrameMetrics 注册／移除主体正确。**主线程控制注册，统计回调在 stats Handler 上，onPause／隐藏会移除，tick 也移除。可再用每次注册独立的 session 标识隔离晚到回调；保留的 `window` 在移除后可置空。多个 volatile 结果的一致性问题见第 4 项。
- **内存没有整曲 PCM 常驻问题。**MediaPlayer 流式解码；197 秒不会直接变成等长 PCM 内存。旧系统位图约 8 MB 预算合理，不主动 recycle 可避免显示列表仍引用时出错；尺寸变化时旧位图与新位图可能短暂并存。两个静态 HandlerThread 是进程级保留开销，不会每次重建 Activity 就新增线程。
- **Toast 限频、替换旧 Toast、onPause 撤销均合理。**
