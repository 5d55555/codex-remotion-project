# 战斗架构（Astra 的方案，实现时的偏差见文末）

我的决定是：**这一版选 A：Java `SurfaceView + lockHardwareCanvas`，游戏逻辑与绘制共用一个独立线程；角色用预渲染部件图集，逻辑固定 120 tick/s。将来需要复杂着色器时，优先迁移到 B，保留 Java 战斗核心。**

这是针对“一个人开发、必须在容器里持续看见画面、当前只有两个角色”的取舍。笔记推荐的 C 仍有长期控制优势，但现在引入 C++、JNI、EGL 和主机渲染宿主，会明显推迟战斗玩法迭代。**没有设备实测，任何路线都不能保证中低端机稳 60fps；下面给的是可控制预算、可验证正确性的实现方案。**

已阅读四个 Java 类、技术选型笔记、Manifest、Gradle 配置和现有 Paparazzi 测试。本次只做设计，没有修改文件。

**1．路线决定与迁移边界**

| 路线 | 对本项目的判断 |
|---|---|
| A：独立线程 Hardware Canvas | **本版采用**。现有 Java、Canvas、Paparazzi 经验可直接复用；图集、变换、少量粒子足以表达当前技能 |
| B：Java 自管 EGL/GLES3 | **后续首选迁移方向**。保留逻辑，增加精灵批处理、shader、FBO；Swappy 可通过小型 JNI 桥接 |
| C：C++ GameActivity/GLES3/Swappy | 控制最完整，但不是两角色游戏达到高刷的必要条件；目前不承担整套原生基础设施成本 |
| libGDX | 如果现在就决定全面进入 GLES，它比自研 B 更省开发量；但 Paparazzi 不能直接验证其实际游戏渲染 |

A 使用的是硬件 Canvas，符合项目已有 `minSdk=26`。每帧完整覆盖 Surface，不依赖上一帧像素保留；用不透明背景开始绘制。[SurfaceHolder 官方说明](https://developer.android.com/reference/android/view/SurfaceHolder)

具体采用：

```text
原生主页 → 原生难度页 → 横屏 BattleActivity
                            │
                       BattleSurface
                            │
                    单游戏线程 + Canvas
```

当前 Manifest 把主页锁成竖屏。第一版可以保留竖屏主页和难度页，仅战斗页横屏；进场先完成尺寸确定与资源预热，再开始计时。

**A 的风险不是“Java 太慢”，而是绘制控制有限：**

- 无法直接控制 Canvas 内部的 GPU 批处理和呈现队列。
- 大面积透明叠加、动态复杂路径、逐帧模糊容易超预算。
- Paparazzi 能验证构图，却不能复现手机 HWUI、驱动与 Surface 呈现时序。
- `lockHardwareCanvas()`、提交和首次纹理使用仍可能出现等待。

本版先设以下**工程预算，不是平台极限**：

| 项目 | 初始预算 |
|---|---|
| 人物 | 2 人，每人约 12～18 个部件 |
| 同屏粒子 | 低档 128，高档 256 |
| 绘制命令 | 通常低于约 400 条/帧 |
| 全屏特效 | 最多一层简单透明色或纹理覆盖 |
| 发光 | 烘焙光晕图，禁止每帧动态模糊 |
| 图集 | 先控制在 2～3 张 2048² RGBA 内，另算背景 |

2048² RGBA 原始像素约 16MiB，不能按 PNG 文件大小估算运行内存。

满足以下任意条件就启动 GLES 迁移评估：

1. 领域效果需要屏幕空间扭曲、多个离屏合成或可控 bloom。
2. 常态超过约 500～1000 个独立精灵，并出现 CPU 绘制提交瓶颈。
3. 真机上，减粒子、减少透明覆盖、预热资源后，渲染仍持续占满帧预算。
4. 为绕开 Canvas 限制，开始不断增加特殊路径和中间 Bitmap。

**技能数量不是迁移标准。** “茈”和领域可以先用图集、缩放、旋转、遮罩式转场表现；需要什么视觉能力才是标准。

提前隔离三层：

```text
BattleWorld：玩法、碰撞、技能，无 android.* 依赖
SceneComposer：状态 → 图集编号、仿射变换、颜色、层次
CanvasRenderer：执行绘制命令
```

未来替换最后一层即可。不要在技能类里调用 `Canvas`，也不要让碰撞读取人物图片尺寸。

**2．线程、时钟、输入与生命周期**

**线程模型**

| 线程 | 职责 |
|---|---|
| UI 线程 | Activity、难度页、触摸解析、Surface 生命周期 |
| 游戏线程，带 Looper | 消费输入、固定模拟、人物姿态、生成绘制命令、锁 Canvas、绘制提交 |
| 资源线程 | 加载、解码；进入战斗前完成资源交接 |
| 已有 Bgm 线程 | 保留 MediaPlayer 串行控制 |

先不拆模拟与渲染线程。两个角色的逻辑远小于绘制开销，拆开反而增加快照、同步和延迟。

**固定 120 tick/s，渲染 60/90/120fps。**

相较笔记里的 60 tick/s，这里选 120，是为了降低动作输入量化延迟，并让吸力、击飞和碰撞更平顺。两个角色的计算量很小；仍需用测试验证。

- 所有技能时间保存为整数 tick。
- 60fps 通常每帧模拟 2 tick，120fps 通常 1 tick。
- 渲染插值仅影响显示，不参与碰撞。
- 前后状态插值约增加一个 tick，即 8.33ms 的视觉延迟。
- 按钮按下反馈可立即显示；伤害、位移、出招仍由模拟裁决。

用整数累积避免把 `1e9 / 120` 截断带来的时钟漂移：

```java
static final int HZ = 120;
static final long SECOND = 1_000_000_000L;
static final int MAX_STEPS = 8;

long accumulator; // 单位：纳秒 × HZ

void advance(long elapsedNs) {
    accumulator += Math.min(elapsedNs, 100_000_000L) * HZ;

    int steps = 0;
    while (accumulator >= SECOND && steps < MAX_STEPS) {
        previous.copyFrom(world);            // 复制到预分配状态
        input.applyForTick(world.tick + 1);   // 按已分配的 tick 消费
        world.step();                        // dt = 1 / 120
        accumulator -= SECOND;
        steps++;
    }

    if (accumulator >= SECOND) {
        stats.recordOverload();
        accumulator %= SECOND; // 单机版丢弃墙钟积压，不跳过玩法 tick
        input.rebasePendingTimeline();
    }

    float alpha = (float) accumulator / SECOND;
    composer.compose(previous, world, alpha, drawBuffer);
}
```

这里超载后会短暂“游戏时间落后于现实时间”，不会为了赶时间直接跳过伤害或碰撞。暂停恢复时清空 accumulator、重设时间基准、令 previous=current。

**输入：预分配 SPSC 环形队列。**

UI 是唯一生产者，游戏线程是唯一消费者。只复制原始值，不跨线程保留 `MotionEvent`。

```java
final class InputRing {
    static final int CAP = 256, MASK = CAP - 1;

    final int[] kind = new int[CAP];
    final int[] control = new int[CAP];
    final int[] value = new int[CAP];
    final long[] timeNs = new long[CAP];

    volatile long writeSeq;
    volatile long readSeq;

    // 仅 UI 线程调用
    boolean offer(int k, int id, int v, long t) {
        long w = writeSeq;
        if (w - readSeq >= CAP) return false;

        int i = (int) w & MASK;
        kind[i] = k;
        control[i] = id;
        value[i] = v;
        timeNs[i] = t;
        writeSeq = w + 1; // volatile 发布完整槽位
        return true;
    }

    // 仅游戏线程调用
    void drain(InputConsumer dst) {
        long r = readSeq;
        long end = writeSeq;
        while (r < end) {
            int i = (int) r & MASK;
            dst.accept(kind[i], control[i], value[i], timeNs[i]);
            r++;
        }
        readSeq = r; // 数据读取结束后才允许复用
    }
}
```

补全以下规则才能落地：

- 摇杆坐标量化为有符号整数；建议死区 0.12，死区外重新映射到 0～1。
- UI 用固定数组跟踪 `pointerId → 控件`，不能把 pointer index 当 ID。
- 手指按下时捕获控件，移出后仍由该控件接收抬起。
- `ACTION_CANCEL`、失焦、暂停均清除摇杆和所有按键。
- 不用每次触摸 `Handler.post(() -> ...)`。
- 队列满时不能静默丢掉 `UP`：增加独立的 `volatile cancelEpoch`，溢出就递增；游戏线程发现变化后丢弃旧输入并全部松键，记录异常。
- 正常输入按事件时间映射到尚未执行的 tick；迟到事件进入下一 tick。不要将刚收到的按键应用到所有历史追赶 tick。
- 回放记录**最终生效 tick、顺序、量化值**，不在回放时重新解释墙钟时间。

短促的 DOWN/UP 可能落在同一 tick，必须保留顺序，不能只存“本帧是否按住”。

**零分配的范围**

目标是“战斗稳定运行时，自己写的每 tick/每帧热路径不分配”，不是宣称 Android 框架完全没有分配。

预分配：

- 两个角色状态及上一 tick 状态。
- 技能实例、命中记录、粒子、音效/表现事件环。
- `Paint`、`Rect`、`RectF`、`Matrix`、绘制命令数组。
- HUD 数字字符缓冲和固定文字。

禁止热路径使用集合扩容、Stream、装箱、字符串拼接、Bitmap 创建、图片解码、JSON 解析和路径重建。

池满策略必须明确：

- 装饰粒子可以丢弃或替换最旧粒子。
- 伤害、命中和技能实例不能静默丢失。
- 本版苍最多同时存在一个，技能池按明确上限配置。
- 技能空间不足时拒绝施放，且不扣冷却。

**帧节奏**

游戏线程创建自己的 `Choreographer`，使用同一个回调对象，只维持一条回调链：

```text
vsync → 输入整理 → 模拟若干 tick → 插值 → 绘制提交 → 注册下一次回调
```

不用忙循环，也不叠加 `sleep(16)`。

- API 30+：对有效 Surface 请求目标帧率，兼容模式用 `DEFAULT`。
- API 31+：优先无缝切换。
- 监听实际显示模式变化，重新选择提交节奏。
- 120Hz 可以提交 120 或每两次 vsync 提交 60。
- 90Hz 若要稳定 60，应请求切到支持的 60Hz 模式；固定在 90Hz 上跳帧得到 60 会有不均匀间隔。
- 旧系统使用显示模式偏好作为尽力请求。

`setFrameRate()` 只是意向，不是限帧器，也不保证屏幕采用请求值。[Frame Rate API](https://developer.android.com/media/optimize/performance/frame-rate)

A 不接 Swappy，因为没有自己控制的 EGL swap 点。迁移 B 后，由 Swappy 接管实际提交节奏，不再叠加另一套等待器。[Swappy 官方说明](https://developer.android.com/games/sdk/frame-pacing)

**ADPF：首版留接口，暂不开 Performance Hint。**

先接 API 29+ 热状态监听和画质档位：先减粒子、光晕和背景动态，再降显示目标；模拟仍保持 120 tick/s。

原因是 Canvas 的工作分布在游戏线程、框架渲染线程和 GPU，仅报告 Java 绘制调用耗时可能误导调度。获得设备数据后再启用：

- session 使用 `Process.myTid()`；
- 只报告可解释的工作区间；
- 不把限帧等待当作 CPU 工作；
- 切目标后更新预算，暂停后停止报告或关闭 session。

这些 API 是性能提示，不是锁频。[PerformanceHintManager.Session](https://developer.android.com/reference/android/os/PerformanceHintManager.Session)

**生命周期：Surface 销毁必须有停止访问的确认。**

运行条件：

```text
resumed && focused && surfaceReady && resourcesReady && !userPaused
```

处理顺序：

1. `surfaceCreated/Changed`：发布新 generation、尺寸和 viewport。
2. 游戏线程采用新 generation，预热必要资源后开始。
3. `onPause/失焦`：关闭运行门、清输入、暂停模拟、停止回调。
4. `surfaceDestroyed`：撤销当前 generation，确保正在进行的 Surface 使用已经结束。
5. 重建后保留游戏世界，重建尺寸相关资源；不补算后台时间。

`surfaceDestroyed()` 返回前，渲染线程必须已经停止访问旧 Surface；仅投递异步停止消息不够。[Surface 生命周期要求](https://developer.android.com/reference/android/view/SurfaceHolder.Callback)

实现一个小型 `SurfaceGate`，管理“是否允许开始绘制”和“是否存在进行中的绘制”。销毁时禁止新绘制并等待已有绘制释放；等待时不持有游戏线程需要的锁，游戏线程也不得同步等待 UI。生命周期协调要与资源加载、线程退出分开，不能在销毁回调里等待解码或整个工作队列。

锁定成功的 Canvas 必须在 `finally` 中提交释放。正常 `onPause` 提前停绘，减少销毁阶段需要等待的概率；驱动卡死的风险无法靠 Java 超时安全消除。

**音乐衔接**

现有 `Bgm` 的专用线程、异步准备和焦点处理可以保留，但要改两点：

- `MainActivity.onPause()` 不能再直接代表“整个应用进入后台”。
- `MainActivity.onDestroy()` 不能因主页结束而释放战斗正在使用的音乐。

改为应用级音频协调器，统一管理前台状态与当前音乐场景，区分内部 Activity 切换和离开应用。

建议“开始游戏”进入难度页；选难度并开始战斗时调用一次 `playFromStart()`。暂停恢复只续播。短音效用预加载 `SoundPool`，通过有界事件队列触发，不为每次攻击创建 MediaPlayer。

现有 `ShinjukuView` 在主页暂停后停止即可。**系统“移除动画”只能影响装饰，不应让战斗模拟停下。**

**3．角色：代码制作部件，运行时画图集**

推荐：**SVG/Canvas 代码作为角色制作源，构建时栅格化成部件图集；运行时做骨骼式二维变换。**

HTML 可以作为离线制作或预览工具，但不进入游戏运行时。对几何风格 Q 版人物，SVG 的尺寸、颜色和锚点通常更容易管理。

每个角色先拆成：

```text
后侧手臂、后侧腿、躯干、前侧腿、前侧手臂、
头、头发、眼罩/面部、手掌、衣摆
```

拳头、张手、受击脸做少量替换部件。避免第一版就实现复杂网格蒙皮。

```java
// 加载阶段生成；之后只读
final class RigDef {
    int boneCount;
    short[] parent;        // 父骨骼必须先于子骨骼
    short[] regionId;      // 图集区域
    float[] bindX, bindY;
    float[] pivotX, pivotY;
    short[] drawOrder;
}

// 每个角色一份，全部预分配
final class RigPose {
    float[] x, y, angle, scaleX, scaleY;
    float[] worldAffine;   // 每根骨骼 6 个值
}
```

变换约定：

```text
Mworld = Mparent × Translate(x,y) × Rotate(angle) × Scale(sx,sy)
Mdraw  = Mworld × Translate(-pivotX,-pivotY)
```

朝向翻转放在角色根变换上。动画用 tick 时间轴、关键帧数组；角色动作不用 `ValueAnimator`。

绘制命令只包含：

```text
regionId
m00 m01 m02 m10 m11 m12
颜色/透明度
混合模式
顺序
```

首版支持普通透明混合和少量加亮效果即可。透明精灵必须保持层次顺序，不能为了按图集排序打乱前后关系。

图集制作注意：

- 边缘扩色和留边，防止采样到邻接部件。
- PNG 放 assets 或 drawable-nodpi，避免密度自动缩放。
- 身体关节处留重叠，旋转时不露缝。
- 图集坐标、锚点、逻辑身高和碰撞盒各自定义。
- 碰撞盒随动作状态变化，但不跟着头发和衣摆摇摆。

动态矢量只用于少量简单线段、圆环和调试碰撞框。复杂角色轮廓、光晕、烟雾都预渲染。

**4．战斗规则、公式与默认参数**

先明确一个设计假设：**本版按侧视横向对战实现**，世界坐标 x 向右、y 向上；摇杆水平分量移动，竖直分量用于技能瞄准，跳跃控制高度。如果你要的是可向场景纵深走动的清版动作，应改为地面 `(x,z)` 加跳跃高度 `h`，不能混用两种模型。

参考战场宽度 `W=1280` 世界单位，人物高约 100。显示缩放和宽高比不改变 W，因此不同手机的苍最大距离一致。

普通攻击流程：

```text
输入 → 动作状态机 → 前摇 → 激活命中区 → 命中裁决
     → 伤害/控制 → 表现事件 → 后摇
```

统一使用 `attackInstanceId`，同一次体术或赫只能命中同一目标一次。宿傩无 AI，但保留受伤、硬直、击飞、倒地和死亡状态。

**难度入口**

```java
void selectDifficulty(int id) {
    switch (id) {
        case STANDARD: onMiwaSelected(); break;
        case HARD:     onUraumeSelected(); break;
        case CRAZY:    onYorozuSelected(); break;
        case NIGHTMARE:onStrongestSelected(); break;
        default: throw new IllegalArgumentException();
    }
    startBattle(id);
}
```

四个函数分别对应“三轮、里梅、万、史上最强”。这一版函数可为空，保存 difficultyId；不擅自引入隐藏伤害倍率。以后返回不同 `BattleConfig`。

**体术与 15% PRD**

明确数值：普通体术 **50 总伤害**，黑闪 **350 总伤害**，不是 50+350。

采用线性递增 PRD：

\[
P(\text{本次触发})=\min(1,Cn)
\]

其中 n 为上次触发后第几次有效判定。通过期望周期求解：

\[
E[N]=\sum_{k=0}^{\infty}\prod_{i=1}^{k}(1-\min(1,Ci)),
\qquad 1/E[N]=0.15
\]

我实际数值求解得到：

```java
static final double BLACK_FLASH_C = 0.03222091437308769;

int attempt = 1;

boolean rollBlackFlash(CombatRng rng) {
    double p = Math.min(1.0, BLACK_FLASH_C * attempt);
    boolean hit = rng.nextUnitDouble() < p;
    attempt = hit ? 1 : attempt + 1;
    return hit;
}
```

规则建议：

- 只在一次体术**有效命中并通过防御裁决**时抽一次。
- 挥空不抽、重复重叠不抽、攻击按钮按下不抽。
- 成功重置，失败累加；同一场战斗中不会因移动、暂停或切技能重置。
- 从 n=1 开始，首次概率约 3.22%；15% 是长期频率。
- 最迟第 32 次有效判定必出，即最多连续 31 次失败。
- 战斗 RNG 与粒子 RNG 分开；回放保存 RNG 状态和 attempt。

手感占位：体术前摇 10 tick、有效 6 tick、后摇 20 tick；输入缓存 10 tick。黑闪可增加约 6 tick 的命中停顿；停顿必须由逻辑计数实现，不能 `sleep`，同时冻结相关动作与技能计时。

**苍的落点与投掷距离**

释放时锁定施法原点与瞄准方向：

\[
L=\min(L_{\text{请求}},0.3W)
\]
\[
c=o+\hat dL
\]

- 有摇杆方向时使用摇杆方向。
- 无方向时，朝面向一侧的宿傩位置辅助瞄准；否则沿面向。
- 将落点限制在战场合法区域；矩形战场中对合法原点做 clamp 不会增加距离。
- 以释放瞬间的原点计算，投出后不追随玩家。
- 飞行约 18 tick，到达后开始吸引；飞行过程不造成持续伤害。
- 最大输出扩大的是作用半径，**不扩大投掷距离**。

**苍的吸力**

不使用 \(1/r^2\)：中心容易数值爆炸，也不好调手感。

令目标相对苍中心距离为 r，影响半径为 R：

\[
q=\operatorname{clamp}(1-r/R,0,1)
\]

吸引加速度上限采用：

\[
a_{\max}(r)=A(0.25+0.75q^2), \quad r<R
\]

范围外为零。边缘仍有一定吸力，越靠近越强。中心附近使用有阻尼的弹簧而非持续最大拉力：

\[
\mathbf a_s =
\operatorname{clampMagnitude}
\left(k(\mathbf c-\mathbf p), a_{\max}(r)\right)
\]

以隐式阻尼更新技能作用后的速度：

\[
\mathbf v_{t+1}
=
\frac{\mathbf v_t+\Delta t(\mathbf a_s+\mathbf a_{\rm other})}
{1+b\Delta t}
\]

初值建议：

```text
R = 0.18W ≈ 230
A = 2400 单位/s²
k = 64 /s²
b = 16 /s
最大吸引速度 = 480 单位/s
核心捕获半径 rc = 10
```

`b=2√k` 对应中心未限幅区域的临界阻尼参考值。这里把公式解释为单位质量目标；以后用抗拉系数调不同敌人。

最大输出：

```text
Rmax = 2R
Amax = 2A
```

不默认翻倍伤害，也不默认翻倍速度上限。弹簧核心保留相同稳定控制，这是避免“越强越抖”的设计处理。

防穿过和抖动：

1. 每 tick 只积分一次，所有外力先累计。
2. 用旧位置到新位置的线段检查是否进入核心圆，不能只检查终点。
3. 进入核心且无优先级更高的击退时，将位置收敛到中心，清除速度并进入 `BLUE_CAPTURED`。
4. 捕获期间不反复归一化零向量；本版允许悬浮，因此暂停重力。
5. 苍消失后解除捕获、恢复重力。
6. 被赫命中时立即解除捕获，并给 24 tick 吸引抗性，避免刚击飞又瞬间被吸回。

这是游戏控制器，不是严格物理模拟。边界碰撞在积分后处理；苍中心必须落在目标身体可达的合法区域，避免持续把人往墙内吸。

**苍的持续伤害**

使用核心平顶、外围平滑衰减：

\[
q_d=\operatorname{clamp}
\left(\frac{R-r}{R-r_c},0,1\right)
\]
\[
DPS(r)=100q_d^2
\]

因此核心最高 100/s，边缘趋近 0。最大输出仍最高 100/s，只扩大覆盖和控制。

HP 推荐存“毫血”，并保留除法余数：

```java
// 每个“苍实例 × 目标”独立保存 remainder
long dpsMilli = Math.round(100_000.0 * q * q);

remainder += dpsMilli;
int damageMilli = (int) (remainder / 120);
remainder %= 120;

target.hpMilli -= damageMilli;
```

目标始终处于核心时，120 tick 恰好扣 100 血，不会因每 tick 截断造成偏差。持续伤害不每 tick 播音效或制造命中停顿；伤害数字可每 12 tick 合并显示。

**长按苍：明确状态机**

以下均为可调占位：

```text
按下 → BLUE_HOLD
短于 42 tick 松手 → 普通前摇 12 tick → 投出
保持到 42 tick（350ms）→ 最大输出前摇 36 tick（300ms）→ 自动投出
```

完整最大输出最早约 650ms 出手。

取消规则：

- 长按确认前：松手是普通施放；移动允许；跳跃或其他攻击可取消。
- 长按确认后：进入承诺前摇，移动速度降到 30%；松手不降级。
- 前摇最后 12 tick 锁定方向，之前允许瞄准。
- 有效受击硬直可打断；无限成功阻挡的攻击不打断。
- 系统 `ACTION_CANCEL`、暂停、失焦取消未释放动作，避免恢复后自动发招。
- 技能真正生成时开始完整冷却；被打断可设 0.5 秒失败锁，避免反复白嫖前摇。
- 普通苍/最大苍共享冷却。

**赫：150 伤害与击飞**

建议首版为短程前向爆发，而非再增加一套弹丸：

```text
前摇 14 tick
命中区持续 4 tick
后摇 24 tick
有效距离约 0.16W
总伤害 150
```

命中时给质量归一化冲量：

```java
target.vx += facing * 650f;
target.vy += 420f;

target.vx = clamp(target.vx, -800f, 800f);
target.vy = Math.min(target.vy, 600f);
target.hitstunTicks = Math.max(target.hitstunTicks, 42);
```

重力先取 `1800 单位/s²`，向下。上述 420 上抛速度在无其他作用时约抬高 49 单位，空中时间约 0.47 秒。

- 硬直期间禁止主动移动和出招，物理继续。
- 横向撞墙夹到 `角色半宽～W-角色半宽`，清除朝墙外速度。
- 首版不做墙反弹和墙伤害。
- 落地清除向下速度，可进入 12 tick 落地恢复。
- 所有高速移动用扫掠碰撞或连续区间判定，避免穿过薄命中区。
- 赫与苍同 tick 命中时先解除捕获并赋予抗拉，再积分，顺序固定。

**“无限”的接口**

不要写成“Gojo 受伤函数直接 return”。将攻击接触、伤害和表现分开：

```java
final class AttackContext {
    int sourceId, targetId, attackInstanceId;
    int damageMilli;
    int flags;
    int hitstunTicks;
    float impulseX, impulseY;
    int domainId;
}

interface DefenseRules {
    // 返回位掩码，不创建结果对象
    int resolve(World world, AttackContext attack);
}

// 示例结果位
static final int ALLOW_DAMAGE  = 1;
static final int ALLOW_IMPULSE = 2;
static final int ALLOW_STUN    = 4;
static final int SHOW_INFINITY = 8;
```

顺序：

```text
检测接触
→ 校验是否重复命中
→ 校验攻击上下文与领域规则
→ 防御裁决
→ 应用允许的伤害/冲量/硬直
→ 发出普通命中或无限阻挡表现
```

建议本版无限同时阻止掉血、击退和硬直，攻击自身特效照常完成，五条附近显示阻挡波纹。这比“血没扣但被无限连击飞”更符合被动预期；如果只要求免伤，位掩码可以单独调整。

未来绕过条件分别接：

- **领域必中**：目标确实处于生效领域中，而且必中未被抵消。
- **领域展延**：攻击者当前展延状态有效，且该接触符合规则。
- **特殊手段**：攻击具有被规则系统认可的特殊绕过能力。

不能只因“存在领域”就让所有攻击绕过无限；攻击方也不能自行设置一个无条件信任的 bypass 位。

| 项目 | 默认值 |

**5．容器验证方法**

**逻辑单元测试与确定性回放**

把 `core` 做成独立纯 Java 模块，用 JUnit 测试，不加载 Android。

回放头至少保存：

```text
规则版本、配置 hash、初始 RNG 状态、初始世界
每条输入：生效 tick、顺序、控件、量化值
```

每隔固定 tick 对完整逻辑状态计算 hash，包括：

- 位置、速度、HP、动作阶段；
- 技能存活时间、冷却、伤害余数；
- PRD attempt、RNG 状态；
- 命中去重表及捕获状态。

不要把粒子和渲染插值放进逻辑 hash。随机算法固定并版本化；不依赖容器遍历顺序。需要跨 JVM/ART 位级一致时，对逻辑使用定点数或显式量化，并对平方根等计算采用固定实现；仅“固定 dt”不足以保证跨平台完全一致。

必要测试：

| 测试 | 断言 |
|---|---|
| 60/90/120 渲染调度 | 同 tick 输入得到相同最终状态 |
| PRD | 固定种子序列可重现；长序列频率约 15%；无超过 31 次连续失败 |
| 挥空与重复命中 | 不增加抽奖次数，不重复扣血 |
| 苍核心伤害 | 120 有效 tick 恰好 100 血 |
| 苍距离 | 任何输入落点距施法原点不超过 0.3W |
| 苍控制 | 靠近中心收敛，无 NaN；最大输出范围、加速度上限翻倍 |
| 赫与苍同时作用 | 赫能解除捕获，抗拉时段有效 |
| 无限 | 普通攻击不扣血；合法绕过才生效 |
| 输入 | DOWN/UP 同 tick、多指、溢出、暂停均不残留按压 |
| 边界 | 高速击飞不出界，不穿过有效碰撞区 |

**Paparazzi 截图：复用真正的 CanvasRenderer**

不截图 `SurfaceView` 本身。提供普通 View 测试宿主：

final class BattlePreviewView extends View {

这样验证的是正式版同一套构图、图集与变换代码。Paparazzi 本身支持无设备和模拟器的 Android 画面渲染。[Paparazzi 官方仓库](https://github.com/cashapp/paparazzi)

建议固定截图：

**Mesa llvmpipe EGL：可以做，但不是直接运行 APK。**

将来进入 B/C 后，可以在 Linux 上：

```text
Mesa EGL surfaceless display
→ 创建 OpenGL ES 3 context
→ pbuffer 或 FBO
→ 执行相同 shader、图集和绘制命令
→ glReadPixels → PNG
```

Mesa 支持 surfaceless EGL，llvmpipe 是 CPU 软件光栅器，不需要 KVM。[Mesa EGL](https://docs.mesa3d.org/egl.html)、[llvmpipe](https://docs.mesa3d.org/drivers/llvmpipe.html)

主机测试程序可以按这样的环境启动：

```bash
LIBGL_ALWAYS_SOFTWARE=true \
GALLIUM_DRIVER=llvmpipe \
EGL_PLATFORM=surfaceless \
./render-smoke --scene blue-max --tick 180 --out blue.png
```

其中 `render-smoke` 需要自行实现；本次没有在容器中安装或运行它。实际能否创建 GLES3 context，要检查 Mesa 构建、扩展和 `GL_VERSION`。

尤其注意：

- Android 的 `android.opengl.GLES30` 不能原样当作桌面 JVM 驱动使用。
- B 需要一个 GL 调用适配层，主机端接 Linux EGL/GLES。
- C 可复用更多原生渲染代码，但仍需替换 Android 资源和窗口接口。
- 主机截图能检查 shader、UV、混合和构图，不能验证手机驱动、Swappy 或 Android 生命周期。
- llvmpipe 的 FPS 没有手机性能参考价值。

所以“GLES 在容器里看不到”并非绝对障碍，真正成本是多维护一个主机宿主。

## 实现时的偏差

- 苍的吸力：照上面“加速度限幅 + 隐式阻尼 b=16”实现后，远处的终端速度只有 A/b≈150 单位/秒，站在地上的目标还会被地面摩擦完全抵消，拉不动，算不上“巨大吸力”。改成“目标速度跟随”：目标速度指向中心，大小 min(480, 5×距离)；速度以 16/s 追目标速度，加速度不超过 A(0.25+0.75q²)。远处全速冲向中心，近处等价于 k=80、b=16 的弹簧（接近临界阻尼，不会冲过头）；被吸时不受地面摩擦。
- 苍的落点最高 360（原来 560），被吸上去的人头顶不出画面。
- 音乐：用户要求点“开始游戏”时就从头播放，保留这一点（没有改成进战斗才播）。
- 加了约 0.12 秒的输入缓冲（体术、赫、跳跃），连按不吞键。
