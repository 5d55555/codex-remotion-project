# 帧节奏资料（v0.14，Luna 联网查证）

问题：背景：一个纯 Java 的 Android 2D 格斗游戏（minSdk 26，targetSdk 36�……（完整问题见下面四点的标题）

## 结论先说

这套架构的主要风险不在每帧 0.1 ms 的 CPU 绘制成本，而在 **帧提交与显示节奏是否匹配**：应用可能准时完成绘制，却把缓冲区过早提交、排队，或让 `eglSwapBuffers()` 的阻塞和 Choreographer 的唤醒节奏相互作用，造成额外延迟和不均匀呈现。官方 Android Frame Pacing 资料把 buffer stuffing、节奏抖动和多刷新率下的 judder 都列为需要解决的问题；Swappy 正是围绕这些问题设计的。[Android Frame Pacing](https://developer.android.com/games/sdk/frame-pacing)

对你这个项目，我会优先做三件事：**真机测呈现时间和 swap 阻塞；按实际目标帧率正确设置 Surface 帧率；把 ADPF 的实际耗时定义和目标周期改正确。** FrameTimeline 在纯 Java 的 `SurfaceView` + EGL 路径中有诊断价值，但仅拿到 timeline 不会自动改变 SurfaceFlinger 的呈现目标。

## 1. 自己的 Choreographer 线程 + EGL 交换

### 常见问题、判断与修法

| 问题 | 怎么判断 | 低风险修法 |
|---|---|---|
| **Buffer stuffing / 多一帧延迟** | Perfetto 看 app 提交、SurfaceFlinger latch/present 时间；连续帧 present 间隔不均，即使 app 渲染很快；触控到画面响应比预期多一个刷新周期 | 每次只提交一帧；不要让渲染线程自由循环；避免 swap 返回后立即再排队。必要时研究 EGL fence/back-pressure。对 OpenGL 游戏，官方推荐用 Frame Pacing/Swappy 处理时间戳和同步 fence，但它是 native/NDK 方案，和当前限制不兼容。[官方说明](https://developer.android.com/games/sdk/frame-pacing) |
| **`eglSwapBuffers()` 阻塞** | 分段记录模拟、绘制、swap 的墙钟时间；若 swap 时间周期性接近一个刷新周期，通常是队列背压或等待 buffer 释放，不等于 GPU 绘制真的用了这么久 | 不要把 swap 等待当作逻辑或 GPU 工作时间报告给 ADPF；检查是否每次 Choreographer 回调只做一次 swap。swap 阻塞本身可能是限速/背压，强行消除可能让队列堆积 |
| **Frame callback 或帧间隔抖动** | 用 `frameTimeNanos` 记录相邻回调间隔，再与 `System.nanoTime()` 记录的回调开始、绘制完成和 swap 返回时间对照；在 Perfetto 检查线程调度和 SurfaceFlinger present | Choreographer 线程只负责一帧回调中的工作；不要另开无限渲染循环。若在 60Hz 屏每回调仍固定推进 1/120 秒，应用是在每次显示机会都画一帧，但每两帧逻辑状态才变一次；要按实测呈现节奏确认这是否是预期 |
| **刷新率切换、游戏模式或省电模式限制** | 注册 `DisplayManager.DisplayListener`，记录 mode/refresh rate 和 callback 间隔；用真机检查切换前后 swap、回调时序。`setFrameRate()` 是请求，系统可能因电量、热状态或其他 Surface 而不采纳 | 在 Surface 创建/游戏进入活跃状态时调用一次，不要每帧调用。Android 15 起游戏默认刷新率可能是 60Hz，需明确请求高帧率；系统仍可覆盖请求。[Android 游戏刷新率说明](https://developer.android.com/games/optimize/display-refresh-rate-change) |

`setFrameRate()` 只提供 Surface 的目标帧率提示，不会自己修复生产管线；Android 文档也明确提醒，帧率不匹配时应为每帧提供 presentation timestamp，避免过早呈现导致 judder。[Frame Rate API](https://developer.android.com/media/optimize/performance/frame-rate)

### `eglPresentationTimeANDROID` 和 FrameTimeline 值不值得用？

**`eglPresentationTimeANDROID`：值得做实验，尤其是应用帧率低于屏幕刷新率或两者比例不整除时。** 它可避免 buffer 被平台过早呈现，从而降低 judder。正确做法是为每个即将 swap 的 EGL 窗口帧设置**单调递增、与目标呈现时刻对应**的时间戳，再调用 `eglSwapBuffers()`；不能把一次逻辑 tick 的时间戳直接当作所有重复显示帧的时间戳。时间戳过期、跳回或按错误时钟域传入，都会令结果无效或产生不规则显示。若渲染帧率本来就是显示刷新率，收益可能有限。[Frame Rate API 对 presentation timestamp 的说明](https://developer.android.com/media/optimize/performance/frame-rate)

**API 33 的 Java `Choreographer.postVsyncCallback()` / `FrameData`：有诊断价值，直接控制 SurfaceView 呈现的价值有限。** `FrameData` 可以读取候选 timeline 的 deadline、expected presentation time 和 vsync ID。可以先记录 preferred timeline 的这些值，与实际 swap/present 数据对比，判断当前帧能否赶上 deadline。`FrameData.getFrameTimeNanos()` 是帧开始渲染时间，不宜拿来作为游戏动画时钟；API 文档建议动画时钟使用 animation time。[FrameData](https://developer.android.com/reference/android/view/Choreographer.FrameData) [FrameTimeline](https://developer.android.com/reference/android/view/Choreographer.FrameTimeline)

需要注意，Java `SurfaceView`/EGL 没有一个通用 Java API 能把所选 vsync ID 直接附到 EGL swap 上。API 35 的 `SurfaceControl.Transaction.setFrameTimeline(vsyncId)` 是为 SurfaceControl transaction 设置 timeline 的接口，不是给 `eglSwapBuffers()` 设置 timeline 的通用入口。因此在当前纯 Java 架构里，**先用 FrameData 做观测；不要以为读到 expected presentation time 就等于系统会按它呈现。**[SurfaceControl.Transaction.setFrameTimeline](https://developer.android.com/reference/android/view/SurfaceControl.Transaction#setFrameTimeline(long))

另外，FrameTimeline 在 API 33 才有；`eglPresentationTimeANDROID` 由 EGL 扩展提供，必须运行时检查扩展是否支持。

## 2. ADPF 用法核对

### 目标时长填什么？

填**这组会话线程每个工作周期的目标工作耗时**，不是显示刷新周期。周期预算可用作硬上限参考，但目标应来自设备上实测的 CPU 工作耗时及可接受的 deadline 预算。

- 如果逻辑 tick 每 8.33 ms 执行一次，但渲染每次显示回调才执行一次，ADPF 报告的工作周期应对应**实际被测量的工作**，而不是不加区分地总填 8.33 ms。
- 60/90/120 Hz 的刷新周期分别约为 **16.67/11.11/8.33 ms**。这些是显示间隔，不代表 CPU 每周期需要忙这么久。
- 刷新率变化时，只在真实工作周期目标随之变化时更新 target。不要为了追刷新周期，把 0.1 ms 的实际工作谎报成接近 8.33 ms；那会给调度器错误的负载信号。

### 实际时长包括什么？

API 31 的 `reportActualWorkDuration(long)` 表示会话线程上一周期工作所花的时长；Java 文档要求时间戳基于 `SystemClock.uptimeNanos()`。[Session API](https://developer.android.com/reference/android/os/PerformanceHintManager.Session)

你的“CPU 逻辑 + CPU 发出绘制命令”可以计入。不要把 **`eglSwapBuffers()` 阻塞等待**混进 CPU work duration；它可能包含等待 buffer/fence 的时间，并非 CPU 正在做工作。也不要把尚未完成的异步 GPU 时间算成 CPU 时间。

API 35 的 `reportActualWorkDuration(WorkDuration)` 支持报告工作周期起始时间、总耗时，以及 CPU/GPU 分量；只有在你能可靠计量各分量时才用。不要把 GPU 时间估成 CPU 时间，或重复计算总时间和分项。[WorkDuration API](https://developer.android.com/reference/android/os/PerformanceHintManager.Session#reportActualWorkDuration(android.os.PerformanceHintManager.WorkDuration))

### 多久报告一次？HandlerThread 能否作为会话线程？

官方对周期性 workload 的预期是**每个工作周期报告一次**；同时可以查询 `getPreferredUpdateRateNanos()`，设备可能不希望客户端过于频繁更新。[PerformanceHintManager](https://developer.android.com/reference/android/os/PerformanceHintManager)

HandlerThread 可以作为会话线程：在它上面取 `Process.myTid()`，创建 session，并在同一条线程上持续报告。线程要长期稳定存在。若线程分工变化，API 34 的 `Session.setThreads(int[])` 可以更新关联 TID。ADPF 会话只对该会话所包含的线程工作时间有意义。

### Android 12–16 的相关 API

| Android | API 级别 | 相关能力 |
|---|---:|---|
| Android 12 | 31 | Java `PerformanceHintManager`、创建 session、`reportActualWorkDuration(long)`、`updateTargetWorkDuration()`。需处理不支持时返回 `null` |
| Android 13 | 33 | `Choreographer.postVsyncCallback()` 和 FrameTimeline；Game State API 可告诉系统游戏正在加载或处于不可中断 gameplay 等状态。[Game State API](https://developer.android.com/games/optimize/adpf/gamemode/gamestate-api) |
| Android 14 | 34 | `Session.setThreads(int[])` |
| Android 15 | 35 | `setPreferPowerEfficiency()` 和 `reportActualWorkDuration(WorkDuration)`；可在确认性能余量足够、希望省电时试验 prefer-power-efficiency |
| Android 16 | 36 | 当前核对到的主要新增显示 API 是 `Display.getSuggestedFrameRate()`，用于读取系统给出的 NORMAL/HIGH 建议帧率；不是强制刷新率命令。[Display API](https://developer.android.com/reference/android/view/Display#getSuggestedFrameRate(int)) |

### 这个轻负载游戏中 ADPF 的预期收益

已知工作耗时不到 0.1 ms，通常远低于最慢的 8.33 ms 帧预算。此时 ADPF **大概率不会提升帧率或画面平滑度**；它不控制显示刷新、EGL 队列或 swap 呈现节奏。它可能帮助高负载突增时调度，也可能没有可见收益。错误 target、把 swap wait 当 CPU work、或频繁报告不匹配的工作周期，反而会给系统错误线索。建议先保留埋点，比较启用/关闭时的 deadline miss、耗电和温升，再决定是否常开。

## 3. Surface 帧率策略、兼容模式和新 API

### `changeFrameRateStrategy`

- **`CHANGE_FRAME_RATE_ONLY_IF_SEAMLESS`**：建议作为格斗游戏默认值，避免刷新率切换带来黑屏或明显中断。系统可能因此不切换到请求模式。
- **`CHANGE_FRAME_RATE_ALWAYS`**：官方重点场景是长时间视频播放，允许为匹配内容帧率接受非 seamless 切换。游戏通常不应主动接受这种可见中断；除非设备/产品设计明确接受，并且切换不会发生在对战中。[Surface.setFrameRate 文档](https://developer.android.com/reference/android/view/Surface#setFrameRate(float,int,int))

### `FRAME_RATE_COMPATIBILITY_FIXED_SOURCE` vs `DEFAULT`

游戏用 **`FRAME_RATE_COMPATIBILITY_DEFAULT`**。`FIXED_SOURCE` 是给固定帧率视频源使用的，暗示平台可以用 pulldown 适配帧率；Android 文档明确说非视频内容用 DEFAULT。[Frame Rate API](https://developer.android.com/media/optimize/performance/frame-rate)

### Android 15/16 值得用的 API

- **API 35 `Window.setFrameRateBoostOnTouchEnabled(true)`**：可试，用于系统在用户触摸窗口时提升帧率。它对菜单、触控 UI 或触摸后需要更快反馈的场景更直接；但不能代替游戏自己的输入到渲染路径，也不保证所有厂商都会产生可见效果。需在支持 API 35 的设备上对照测量。[Window API](https://developer.android.com/reference/android/view/Window#setFrameRateBoostOnTouchEnabled(boolean))
- **GameManager API 31**：正确标注 `android:isGame="true"`；resume 时查询用户选的 Game Mode，并按 STANDARD/PERFORMANCE/BATTERY 调整自己的质量/帧率策略。不能假定 Game Mode 一定可用或一定强制高刷新率；Android 15+ 某些设备可能没有 `GameManager` 实例，记得 null check。[GameManager](https://developer.android.com/reference/android/app/GameManager)
- **Game State API 33**：在加载、菜单、不可中断对局等状态变化时上报，帮助系统做资源/功耗决策。它不负责输入，也不是刷新率锁定 API。[Game State API](https://developer.android.com/games/optimize/adpf/gamemode/gamestate-api)
- **API 36 `Display.getSuggestedFrameRate(category)`**：适合读取系统建议的 NORMAL/HIGH 帧率，例如菜单用 NORMAL、活跃对战用 HIGH，再把合适值作为 Surface 帧率 hint。它是建议值；与“无条件请求最高支持刷新率”相比，可能更有利于省电和遵从系统策略。[Display API](https://developer.android.com/reference/android/view/Display#getSuggestedFrameRate(int))

建议策略：API 30+ 在对局 Surface 可见且渲染器启动时，选设备支持且产品实际能维持的目标（例如 60/90/120），调用 `surface.setFrameRate(fps, DEFAULT, ONLY_IF_SEAMLESS)`；不要单纯以设备最高值为目标。API 35+ 可单独 A/B 测 touch boost。API 36 可在菜单/对局状态切换时读取 suggested rate。

## 4. 像素风角色走路不匀

根因要先区分：**离散逻辑移动**与**显示帧率不均匀**不是同一问题。固定 120Hz 逻辑每步 1–2 个虚拟像素，若 60Hz 显示每两个逻辑 tick 才显示一次，就会看到位置跳跃；若移动速度不是刷新率的整数比例，还会出现不同长度的驻留间隔。

| 方法 | 效果与代价 |
|---|---|
| **位置插值** | 用固定 tick 的前后状态和余数插值绘制，可让低 tick 频率下运动更连续。你已经有插值，重点是确认位置值没有在最终绘制前被取整。它会引入接近一个逻辑 tick 的显示延迟；对碰撞/判定绝不能用插值位置 |
| **像素对齐** | 最终 sprite 坐标取整到虚拟像素，再最近邻放大，像素轮廓稳定、不会糊；但细小位移会形成“停几帧再跳一格”，这可能正是感知上的顿挫 |
| **子像素渲染** | 保留浮点位置、纹理采样用线性过滤或专门的亚像素覆盖，可获得较平滑运动；但像素边缘会抖/糊，与严格像素艺术风格冲突 |
| **相机平滑** | 平滑背景和镜头运动，能减少视口移动造成的顿挫；但不应平滑格斗角色本身的判定坐标。单独平滑相机可能造成角色相对舞台漂移，且增加视觉延迟 |

实用做法：**逻辑与碰撞保持固定 tick；绘制位置用插值；像素风角色先对插值结果取整到虚拟像素；相机只对背景/视口做小幅平滑并限制延迟。** 如果取整导致一格一格移动，需决定视觉风格优先级：可只对角色渲染使用有限的子像素位移，而保持纹理最近邻采样；务必在 60/90/120Hz 上分别看效果。你提供的插值方案方向正确，但“余数插值 + 最终像素对齐”仍不会保证每次移动都均匀。

## 优先级清单

| 优先级 | 改动 | 收益 | 风险 | 改动量 |
|---|---|---|---|---|
| 1 | 真机记录 callback interval、逻辑/绘制/swap 分段耗时、当前 refresh rate；用 Perfetto 对照 present 时间 | 找出节奏问题发生在哪一段 | 低 | 小 |
| 2 | 确保 `setFrameRate()` 用游戏实际目标帧率、`DEFAULT`、`ONLY_IF_SEAMLESS`；不要每帧调用 | Android 15+ 可避免游戏默认 60Hz 限制；降低不匹配概率 | 低 | 小 |
| 3 | 修正 ADPF：target 用工作 deadline/实测周期目标；报告真实 CPU 工作时长，排除 swap 等待；刷新率变化时同步更新 | 避免系统得到错误负载信号；重负载时可能有调度收益 | 低到中 | 小 |
| 4 | API 33+ 记录 preferred timeline 的 deadline/expected presentation time；必要时测试 EGL presentation timestamp | 定位过早呈现和错过 deadline | 低到中 | 中 |
| 5 | 比较 API 35 touch boost、API 36 suggested rate、Game Mode/Game State 的实际设备效果 | 改善触摸活跃时刷新策略或系统协作 | 设备相关 | 小到中 |
| 6 | A/B 测像素取整、浮点位置、有限子像素移动和背景相机平滑 | 针对像素级移动感知调优 | 风格取舍明显 | 中 |

## 落地情况（v0.14）

- ADPF：目标是显示器刷新周期，实际时长只算逻辑和绘制，不含 eglSwapBuffers / lockHardwareCanvas / unlockCanvasAndPost 的等待；Android 12+、设备支持才开。
- Surface.setFrameRate 原来就是 DEFAULT 兼容性、只在刷新率变化时调用（两参数版本默认 ONLY_IF_SEAMLESS），符合建议。
- eglPresentationTimeANDROID、FrameTimeline、touch boost、Game State：没有真机测量前不改（收益不确定）。
- 像素风角色一顿一顿：保留最近邻像素风格；这次改的是 AI 自己的起停（加减速、不碎步），见 README“走位的顺滑”。
