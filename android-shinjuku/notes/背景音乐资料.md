## 先说结论

对于这首约 197 秒的本地游戏背景音乐，建议用**预先编码好的 Ogg Vorbis 文件，通过一个长期持有的 `MediaPlayer` 异步准备并循环播放**。它能避免把整首曲目解码到内存，启动和维护也比较简单。

但要把“无缝”分成两件事：**编码文件的首尾是否适合循环**，以及**设备上的播放器是否在循环边界无缝衔接**。`MediaPlayer.setLooping(true)` 只保证循环播放，不承诺所有设备、所有编码文件都无缝。若循环点绝不能有空隙或咔哒声，必须把实际音频文件做好首尾衔接，并在目标设备上听测验证；单靠切换播放器 API 不能保证。

## 1. 格式与循环

- **MP3：**Android 的 AOSP MP3 extractor 会读取 Xing 信息中的 encoder delay/padding，也会读取 `iTunSMPB` gapless 元数据。[AOSP `MP3Extractor.cpp`](https://android.googlesource.com/platform/frameworks/av/%2B/master/media/module/extractors/mp3/MP3Extractor.cpp) 这说明 Android 的解码链路能识别这些信息，但不能据此断言所有设备的 `MediaPlayer` 循环边界都能无缝；`setLooping()` 的 API 文档没有这种保证。MP3 首尾若本身不匹配，或元数据缺失/处理不一致，仍可能听到空隙或突变。
- **Ogg Vorbis：**平台内置支持 `.ogg` 中的 Vorbis；官方格式表没有承诺 `MediaPlayer` 的 loop point 会做 gapless 衔接。[Android 支持的媒体格式](https://developer.android.com/media/platform/supported-formats) 用合适的 Vorbis 文件循环通常可行，但设备上的边界表现仍需实测。单从格式名不能保证无缝。
- **Opus：**官方格式表列出 Ogg 中 Opus 的支持从 **Android 10 / API 29** 起。minSdk 26 的应用若要覆盖 API 26–28，不能把 Ogg Opus 当作平台保证支持的格式。[Android 支持的媒体格式](https://developer.android.com/media/platform/supported-formats)
- **AAC/M4A：**AAC 与 MPEG‑4/M4A 是平台支持的组合，MP4 extractor 也处理 gapless edit list 中的 delay/padding。[Android 支持的媒体格式](https://developer.android.com/media/platform/supported-formats)；[AOSP `MPEG4Extractor.cpp`](https://android.googlesource.com/platform/frameworks/av/%2B/master/media/module/extractors/mp4/MPEG4Extractor.cpp) 但这同样不是 `MediaPlayer` 循环无缝的跨设备承诺。

**建议：**若资源可随 APK 一起发布，优先选**经过试听验证的 Ogg Vorbis**，兼顾体积与平台覆盖；若必须依赖 gapless 元数据，MP3/AAC 的 extractor 行为有 AOSP 依据，但具体循环表现仍要实测。制作资源时应检查波形首尾的相位、振幅和音乐内容是否能自然衔接，并在至少一台 API 26–28 设备和一台较新设备上听循环点。

## 2. 播放器取舍

| 方案 | 长音乐的适用性 | 主要权衡 |
|---|---|---|
| `MediaPlayer` | **推荐作为简单默认方案** | 平台解码，压缩文件播放时不必把整首 PCM 装进 Java 堆；异步准备可避免阻塞 UI。循环方便。循环边界质量不作 API 保证。 |
| Media3 ExoPlayer | 可用，但本地单曲循环未必值得引入 | 有更丰富的播放控制和媒体能力；需要增加 AndroidX Media3 依赖，具体 APK 增量取决于版本、R8 与打包配置，应以构建产物测量。官方将其列为推荐的媒体播放方案。[MediaPlayer 入门](https://developer.android.com/media/platform/mediaplayer/basics) |
| `SoundPool` | **不适合整首背景音乐** | 会预解码为 PCM；每个声音内部限制 1 MiB，44.1 kHz 立体声约 5.6 秒，197 秒会被截断。适合短音效。[SoundPool API](https://developer.android.com/reference/android/media/SoundPool) |
| AAudio / Oboe | 一般不值得只为循环 BGM 使用 | 面向低延迟原生音频；AAudio 不负责压缩格式解码或文件 I/O，需要自行接解码、缓冲和循环逻辑。Java 应用还要引入 JNI/C++。Oboe 在 API 27+ 使用 AAudio，较低版本回退 OpenSL ES。[AAudio](https://developer.android.com/ndk/guides/audio/aaudio)；[Oboe 低延迟指南](https://developer.android.com/games/sdk/oboe/low-latency-audio) |

对这类需求，**UI 流畅的关键是异步准备、不要在主线程做同步解码/准备工作**，而不是为了低延迟换原生 API。

## 3. 提前准备与“从头播放”

- 在主页创建或由应用级音乐控制器持有播放器；尽早设置数据源、音频属性和 `setLooping(true)`，调用 `prepareAsync()`。准备完成后记录 `prepared = true`。官方明确提醒 `prepare()` 可能耗时，不应在 UI 线程调用。[MediaPlayer 入门](https://developer.android.com/media/platform/mediaplayer/basics)
- `res/raw` 适合有资源 ID 的文件；`assets` 适合保留路径结构或按文件名访问。若用 `Resources.openRawResourceFd()`，文件必须在 APK 中未压缩，否则会返回 `null`。[Resources API](https://developer.android.com/reference/android/content/res/Resources#openRawResourceFd(int)) AGP 的 `noCompress` 可配置不压缩扩展名，但我没有找到当前官方文档列出“AGP 默认不压缩哪些音频扩展名”的可靠完整清单，因此不要依赖某个默认值；检查构建产物，或显式配置 `.ogg` / `.mp3`。用 `openRawResource()` 的流式重载则不要求资源未压缩。
- 用户点“开始游戏”时，若已准备好，调用 API 26 可用的 `seekTo(0, MediaPlayer.SEEK_CLOSEST)` 再播放；若重点是精确回到时间零，`SEEK_CLOSEST` 是合理选择。`seekTo(0)` 是旧接口，语义相对不明确。**不要假定 seek 后紧接着 `start()` 必然等 seek 完成**：API 提供 `OnSeekCompleteListener`，应在回调里 `start()`，这样可避免 seek 与播放竞态。[`seekTo(long, int)` API](https://developer.android.com/reference/android/media/MediaPlayer#seekTo(long,int))
- 准备尚未完成就点击时，只记录 `pendingPlayFromStart = true`；收到 `onPrepared()` 后再执行 seek，收到 seek 完成回调后 start。重复点击时更新为最新一次请求，并确保旧 seek 回调不会触发过期播放意图。也可在游戏页切换前显示短暂加载状态，产品上更容易解释启动延迟。

## 4. 音频属性与焦点

背景音乐建议配置 `USAGE_GAME` + `CONTENT_TYPE_MUSIC`。Android 官方音频焦点示例也使用这组属性。[AudioAttributes](https://developer.android.com/reference/android/media/AudioAttributes)；[管理音频焦点](https://developer.android.com/media/optimize/audio-focus)

应用主动开始音乐时应请求音频焦点，并根据结果决定是否播放；失焦时暂停或按策略降低音量，焦点恢复后只在此前确实处于播放意图时恢复。游戏常见做法是永久失焦就暂停，短暂 duck 请求则由系统 duck 或由应用降音，具体取决于产品体验。

Android 12（API 31）起，满足条件时系统会在另一应用请求 `AUDIOFOCUS_GAIN` 后淡出当前已获焦点的媒体/游戏音频；来电时也会静音符合条件的游戏音频。Android 8–11 的系统自动 duck 等行为也有版本差异。应用仍应处理焦点回调，不能把系统淡出当作唯一管理方式。[管理音频焦点](https://developer.android.com/media/optimize/audio-focus)

注意：targetSdk 36 高于 35。Android 15 起，应用只有在前台或运行前台服务时才能请求焦点；因此应在用户点“开始游戏”、Activity 在前台时请求焦点，不要在后台预请求。[管理音频焦点](https://developer.android.com/media/optimize/audio-focus)

## 5. 生命周期与播放器所有权

如果产品规则是切后台或锁屏即停音乐，在 `onPause()` 或适合的前后台状态回调中暂停，回前台时仅在游戏仍应继续、且此前正在播放的情况下恢复。不要无条件在 `onResume()` start，否则用户手动暂停或刚失去焦点后可能被意外恢复。Activity 的暂停状态可能由切换 Activity、来电或屏幕关闭触发。[Activity 生命周期](https://developer.android.com/guide/components/activities/activity-lifecycle)

播放器不要由每次重建的 Activity 重复创建。可以由应用级控制器持有，或在配置变更中保留同一个控制器；Activity 销毁时解除监听引用，最终不再需要时显式 `release()`。Android 文档也建议显式清理播放器资源。[后台播放指南](https://developer.android.com/media/platform/mediaplayer/background)

## 6. 音量与余量

Android 官方没有为游戏背景音乐规定 LUFS 目标。**不存在一个适用于所有游戏的标准值**；响度要结合音效、语音、设备、音乐动态和游戏内混音试听。建议先保留混音余量：降低音乐通道增益，让音效/语音可在其上方清晰出现，并在游戏内提供独立音乐音量控制。

如果团队需要制作起点，可以暂以 **约 −20 至 −16 LUFS-I** 作为一首普通 BGM 的内部参考范围，而不是平台标准；同时把 true peak 留在 0 dBTP 以下并在叠加音效后检查总线峰值。这个范围是制作建议，依据项目听测调整，不能从 Android 文档推出。

## 推荐实现要点

1. 选择实际测试过首尾衔接的 Ogg Vorbis 资源；API 26–28 不使用平台 Opus。
2. 用应用级控制器持有唯一 `MediaPlayer`，在主页早期设置 `AudioAttributes`、数据源和 looping，然后 `prepareAsync()`。
3. 将准备状态与播放意图分开管理：未准备时点击只记下请求；`onPrepared()` 后从头 seek，`onSeekComplete()` 再 start。
4. 每次点击“开始游戏”都生成新的请求序号/播放意图，避免异步回调把旧请求播放出来。
5. 点击时在前台申请 `AudioFocusRequest`；失焦暂停或 duck，焦点恢复时按先前播放意图处理。
6. 依据游戏规则在进入后台/锁屏时暂停，回前台只恢复符合条件的播放；Activity 重建不能重复创建播放器。
7. 显式处理错误并释放播放器；不要在主线程调用同步 `prepare()`。
8. 实机反复试听循环边界，特别检查不同 Android 版本和耳机输出。`setLooping(true)` 本身不构成无缝保证。
