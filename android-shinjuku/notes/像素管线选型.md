# 像素画面的技术选型（Sol）

最后选了 D（GLES2 低分辨率帧缓冲 + GL_NEAREST 放大）。场景代码只写一份，下面接两个后端：GlTarget（游戏里用）和 CanvasTarget（截图测试、GL 起不来时兜底）；GL 后端用桌面 Mesa 跑对照测试（GlParityTest）。

**推荐 D：GLES2 在低分辨率 FBO 内绘制整个战场，再用 `GL_NEAREST` 放大到原生尺寸 Surface，最后绘制高清 HUD。**它最符合“所有战斗元素共用一个像素网格”，也更适合长期追求中低端机 120Hz。纯 Java 可以直接使用 GLES20，无须引入 C++。

**A 可作为开发成本较低的过渡方案，60Hz 有可行性；不能仅凭分辨率承诺 120Hz。**尤其是 Android 8.0 的过滤限制，以及项目现有 Surface 缩放，需要先解决。

**1．A 的性能与上传风险**

640×295～360 的 ARGB_8888 是 **0.755～0.922 MB/帧**；60Hz 约 45～55 MB/s，120Hz 约 91～111 MB/s。计算正确，但只是上传有效载荷。

- **软件绘制：**约 19～23 万像素本身不大。少量矩形、背景拷贝很便宜；旋转透明部件、半透明叠加、ADD、大面积多层光晕才决定成本。初步预算可按 **1～5ms/帧**考虑；复杂特效叠加或弱核、降频状态可能超过 **5～10ms**。这是预算范围，不能按“骁龙 6/7 系”统一推断。
- **纹理上传：**这一级数据量通常不是带宽瓶颈；无明显争用时，可先按**数百微秒至约 1ms 级的增量成本**预留，但驱动、复制、排队可能产生数毫秒尖峰。它不是可保证的上限。
- **同一 Bitmap 改写：**复用 Java 对象不会避免上传。官方明确说明，位图内容变化后，下次 GPU 绘制会再次上传。旧 HWUI 的缓存代码直接比较 generationId 并重新上传；Skia 路径也将像素 generationId 纳入缓存键。**应按整图更新预算，不要期待自动识别局部脏矩形。**具体是重用纹理存储还是创建新资源，随后端而异，不能把旧实现套到 Android 8～16 全部版本。[官方说明](https://developer.android.com/develop/ui/views/graphics/hardware-accel#tips)、[HWUI 缓存源码](https://android.googlesource.com/platform/frameworks/base/+/3bba35111e844fbc906255e2dead386a96520ae4/libs/hwui/TextureCache.cpp)、[Skia 缓存键源码](https://skia.googlesource.com/skia/+/df65b83ef758094f198a27fb179c1548dfa7dfc3/src/gpu/GrBitmapTextureMaker.cpp)
- **同步与卡顿：**有风险，但不是“每次改写必然等待 GPU”。驱动可能通过复制、资源替换、排队避免等待，也可能因资源争用、缓冲区背压而阻塞。不要并发修改正在被绘制的 Bitmap；双缓冲也不会消除上传成本。
- **发热：**约 100 MB/s 不能单独称为“大带宽”。实际还有 CPU 光栅化的读写、透明混合、上传暂存、全屏输出及合成。更值得关注的是持续 CPU 工作和 120Hz 全链路成本，而非单独这张小图。

120Hz 每帧只有 **8.33ms**，且你当前逻辑、软件绘制和提交共享战斗线程，尾延迟比平均值更重要。

**2．关闭 FILTER 是否保证最近邻**

对普通 `drawBitmap` 放大，官方契约如下：

| Android | 行为 |
|---|---|
| 8.0，API 26 | 硬件绘制缩放位图始终使用双线性，关闭过滤无效 |
| 8.1，API 27 | 不在上述强制范围内，可按关闭过滤的最近邻行为使用 |
| 9～16，API 28～36 | 关闭过滤表示最近邻；Android 10 起新 Paint 默认开启过滤，必须显式关闭 |

建议创建 Paint 后明确调用 `setFilterBitmap(false)`，不要仅依赖构造参数。抗锯齿与位图过滤是两个独立设置。[Paint 官方文档](https://developer.android.com/reference/android/graphics/Paint#FILTER_BITMAP_FLAG)

不过，这只控制**该次位图绘制**，不能控制后续 Surface 合成缩放，也无法撤销资源解码时已经发生的密度缩放。

**3.66 倍最近邻不会变糊，但像素宽度会交替成为 3 或 4 个屏幕像素**；移动时容易出现粗细跳动和视觉抖动。优先整数倍缩放并留边，或调整虚拟分辨率/可见范围。必须铺满时，接受不等宽像素，固定缩放原点，避免逐帧改变目标矩形。

**3．四种方案比较**

| 方案 | 性能特点 | 实现成本 | 同一像素网格 |
|---|---|---|---|
| **A：软件 Bitmap → HWUI** | CPU 光栅化＋每帧上传；低分辨率有利，120Hz 尾延迟风险较高 | 低～中 | 强；但 API 26 最终放大会模糊 |
| **B：直接硬件 Canvas** | 静态素材可缓存，省整帧上传；全屏像素填充、透明过绘仍有成本 | 中 | **一般**；任意角度旋转会在屏幕分辨率上光栅化 |
| **C：低分辨率软件 Surface** | 省去显式 Bitmap→HWUI 绘制步骤，仍有 CPU 绘制、缓冲同步和合成成本 | 低 | 低分辨率内容一致，但最终清晰度不可保证 |
| **D：GLES2 低分辨率 FBO** | 静态纹理常驻 GPU；低分辨率绘制＋一次全屏放大，避免整帧 CPU 上传 | 高 | **最强，采样可明确控制** |

**B 的关键限制：**只对齐部件位置不够。把一个部件旋转后直接画到高清 Canvas，其阶梯边缘会按屏幕像素生成，而不是按虚拟像素生成。除非限制旋转，或预烘焙离散角度，否则不等价于低分辨率整场景渲染。

**C 的关键限制：**`setFixedSize()` 只决定缓冲区大小，不提供合成采样模式的公开控制；放大可能经过 SurfaceFlinger GPU 合成或厂商 HWC 缩放，不能保证最近邻，应视为有模糊风险。[SurfaceHolder 文档](https://developer.android.com/reference/android/view/SurfaceHolder#setFixedSize(int,int))、[AOSP SurfaceView 架构](https://source.android.com/docs/core/graphics/arch-sv-glsv)

D 的最近邻由 GLES 纹理采样明确控制，但最终 Surface 仍应保持原生尺寸，避免合成器再次缩放。[Khronos GLES2 规范入口](https://registry.khronos.org/OpenGL/index_es.php#specs2)

**4．实现必须注意的点**

- **先处理已有二次缩放。**[BattleView.java](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/BattleView.java:77) 已按像素预算调用 `setFixedSize()`；严格像素输出时，应让最终 Surface 与显示区域尺寸一致，再在内部控制战场分辨率。
- **逻辑保持浮点，最终绘制才量化。**先完成插值、相机变换和震屏，再统一对齐虚拟网格；不要把量化误差反馈到物理模拟。相机与角色使用一致规则。
- **旋转在低分辨率目标内完成。**最近邻只能防止混色，不能消除旋转时的轮廓跳变；重要姿势可用离散角度或手工帧改善。
- **D：**FBO、纹理、顶点缓冲复用；素材与 FBO 纹理设置 `MIN/MAG=GL_NEAREST`，非二次幂纹理使用 `CLAMP_TO_EDGE`、不用 mipmap；关闭场景 MSAA，统一预乘 Alpha 和混合规则。处理 EGL 上下文重建。
- **A 若保留：**复用 Bitmap、Canvas、Paint、Rect 和数组；背景每帧完整覆盖或正确清屏，避免透明残影。软件 Canvas 输入素材不能使用 `Bitmap.Config.HARDWARE`；当前 renderer 的硬件位图加载分支需要区别处理。资源使用 `drawable-nodpi` 或关闭密度缩放。
- **文字：**战斗伤害数字若也要求共网格，就在低分辨率层绘制；HUD 可在放大后高清绘制。D 可用字形图集或普通 View 叠层，避免每帧把文字重新栅格化成上传位图。
- **验证：**当前 [BattleLoop.java](/home/user/codex-remotion-project/android-shinjuku/app/src/main/java/com/shinjuku/showdown/BattleLoop.java:113) 的 `drawMsAvg` 是调用侧平滑耗时，不能代表 GPU 完成或实际呈现。用 Perfetto 看线程、RenderThread、GPU 与缓冲等待，并在最重特效下持续运行，统计 P95/P99 和降频后的掉帧；60Hz、120Hz 分别验收。
