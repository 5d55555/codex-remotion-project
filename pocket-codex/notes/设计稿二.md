# Astra 设计稿 第二轮：逐屏规格、文案、卡片、会话状态模型、通知、应用名，以及对 core 的审阅

## 1. 首次使用流程

本轮确定：**默认私有工作区，另提供直接访问手机存储的工作区；默认“每步确认”，可切换“完全自动”；不提供只读执行模式。** 首版只支持修改文件和运行 Android 自带命令，不安装 Git、Node、Python、rg。

以下以你提供的实测、现有 core 和本地 schema 为实现基线。尺寸为默认字号下的建议值；文字容器、按钮高度允许随系统字体放大。没有修改文件，也没有重新运行测试。

首次使用顶栏下显示步骤文字：

> 安装 → 登录 → 工作区

当前步骤用 `primary`，已完成步骤用勾选图标。欢迎页不显示步骤条。

进度计算：

- MB 按十进制计算；若沿用二进制计算，单位必须写 MiB。
- 下载速度使用最近 5 秒字节增量，每 500ms 刷新；恢复下载时重建速度窗口。
- 下载总大小未知：显示“已下载 82.4 MB”，不显示百分比或剩余时间。
- 校验进度可以按字节计算。
- **当前解压回调是压缩流读取进度，不是两个文件的安装完成比例。** 首版解压阶段使用不确定进度条，显示“正在解压运行组件”。
- “下载 100%”不能变成“安装完成”；必须等校验、解压和启动检查。
- 暂停/取消需要 core 主动关闭连接；不能点击后仍显示“已暂停”，实际又下载 30 秒。

启动检查至少包含 `codex --version` 和 `app-server initialize`。失败时保留诊断结果；升级场景必须保留原可用版本。

布局树：

```text
顶栏：“连接账号”
步骤条：“第 2 步，共 3 步”
可滚动正文〔16dp〕

├─ 说明〔14sp〕“在浏览器完成授权后，回到这里即可。”
├─ 间距 24dp
├─ 授权卡片〔surface，内边距 20dp〕
│  ├─ 水平行
│  │  ├─ “一次性登录代码”〔14sp〕
│  │  └─ 倒计时环〔40×40dp，线宽 3dp〕
│  ├─ 代码〔32sp，等宽，居中，可选择，最小高 64dp〕
│  ├─ “预计 {14:32} 后过期”〔14sp，居中〕
│  ├─ 主按钮“复制代码并打开浏览器”
│  ├─ 水平按钮：“仅复制代码”“换一个代码”
│  └─ “即将过期时会自动换码，请使用页面上最新的代码。”〔12sp〕
├─ 状态或错误卡片
├─ 可展开行“登录遇到问题”〔最小高 48dp〕
└─ 文字按钮“改用 API 密钥登录”
底部辅助文字〔12sp〕
“请只在官方授权页面输入代码，不要把代码发给其他人。”
```

倒计时和换码：

- 环显示剩余有效期比例；最后 60 秒改为 `warning`。
- 保留你当前“提前 20 秒换码”的策略，但必须称为**提前换码**，不能把尚未过期写成“已过期”。
- 最后 60 秒补充“即将自动换码，请留意最新代码”。
- 换码后显示持续提示：“登录代码已更新，请重新复制。”
- 自动换码不自动打开浏览器，不自动写剪贴板。
- 倒计时使用单调时钟；进程结束、授权成功等实际证据优先。
- 切换 API 密钥登录之前，先停止设备码登录并确认旧进程结束。

| 启动 | “正在连接登录服务…” | “取消登录” |
| 等待代码 | “正在获取一次性代码…” | 超过 10 秒显示“查看网络设置” |
| 等待授权 | “等待你在浏览器完成授权” | 复制、打开、换码 |

| 网络重试 | “暂时无法连接登录服务”＋“{秒数} 秒后重试” | “立即重试”“网络设置”“查看详情” |

网络重试时，如果旧 CLI 已结束，就不要继续展示可操作的旧代码。仅当原登录进程仍活着、代码仍有效时，才保留复制入口。

设备码未开启卡片：

> **需要开启设备码授权**  
> 在 ChatGPT 网页版打开“设置 → 安全”，查找 Codex 设备码授权选项并开启。组织账号可能需要管理员允许。页面名称可能因账号而不同。

按钮：

- “打开 ChatGPT”：打开固定官方站点。
- “已开启，重试”：启动新尝试。
- “改用 API 密钥”：进入备用登录。
- “查看详情”：显示脱敏错误。

不要把任意包含 `device` 的 URL 交给浏览器。固定版设备登录 URL 应验证 HTTPS、精确主机名和允许的路径。

应用内工作区：

- 输入框“工作区名称”，默认“我的工作区”，显示名最多 40 个字符。
- 目录使用 UUID，避免直接把名称拼进路径。
- 可以显示已创建工作区列表，提供“新建工作区”。
- 名称为空：“请输入工作区名称”。
- 创建失败：“无法创建工作区，请检查可用存储空间”。

#### 手机存储的判断与交互

**同意采用直接 POSIX 路径方案。** target 28 的旧版存储兼容路径有依据，但权限成功不代表每个目录都可访问；必须以设备实际读写结果为准。Android 官方资料也明确区分旧版存储与分区存储，并保留目录访问限制。[Android 10 存储变更](https://developer.android.com/about/versions/10/privacy/changes)、[Android 11 存储变更](https://developer.android.com/about/versions/11/privacy/storage)

点击该卡片后，先显示说明：

> **允许访问手机存储**  
> 授权后，助手可以读取和修改系统允许本应用访问的共享存储，包括所选文件夹之外的文件。  
> 选择工作区只设置默认操作位置，不会把助手限制在这个文件夹内。改动会直接写入原文件。

按钮：“继续授权”“使用应用内工作区”。

权限时机：

1. 用户点击“继续授权”后才请求存储权限。
2. 首次启动、安装、登录都不请求。
3. 已授权则进入目录选择器，但首次启用说明仍需展示。
4. 拒绝：“未获得存储权限，仍可使用应用内工作区。”
5. 永久拒绝：“请在系统设置中允许文件访问。”按钮“打开应用设置”。
6. manifest 不要把相关旧版存储权限限到 `maxSdkVersion=28`，否则新系统上的兼容访问路径可能拿不到权限。
7. 不额外申请“所有文件访问”特殊权限来掩盖兼容问题。

目录选择器使用**应用自己的原生目录浏览页**，不使用 SAF，也不尝试把 `content://` 转成本地路径。

```text
顶栏〔56dp〕：“选择文件夹”＋“新建文件夹”
路径面包屑〔最小高 48dp，可横向滚动〕
说明条〔14sp〕：“选择后会直接修改这里的文件”
目录列表〔每项 56dp〕
├─ 文件夹图标 24dp
├─ 名称 16sp
└─ 进入箭头
底部当前路径〔12sp，可展开完整路径〕
主按钮：“使用此文件夹”
```

规则：

- 初始位置从系统获取主要共享存储根目录，不写死 `/storage/emulated/0`。
- 推荐创建“口袋工坊/项目名”，但不在用户点击前自动创建。
- 首版不将共享存储根目录作为工作区；提示“请选择或新建一个项目文件夹”。
- 不宣称支持其他应用的私有数据目录、所有 SD 卡或 USB 目录。
- 显示隐藏目录开关位于更多菜单。
- 不跟随越出允许浏览根目录的符号链接；这是浏览器约束，不是 Agent 隔离。
- “使用此文件夹”后创建随机命名的小型探测文件，写入、读回、删除；成功才保存工作区。
- 测试失败：“这个文件夹无法读写，请选择其他位置。”
- 探测文件删除失败必须报告，不静默遗留。

最后的工作区摘要：

> **{工作区名}**  
> 手机存储 · {路径}  
> 运行模式：每步确认  
> 改动会直接保存到原文件。

**特别补充：授权是应用级的。用户回到私有工作区后，共享存储权限仍然存在。** 设置页提供“管理系统存储权限”；“移除工作区”仅移除记录，不撤销权限、不删除文件。

## 2. 主界面

### 2.1 导航结构

底部导航高 64dp，三个入口：

- “会话”：对话图标。
- “文件”：文件夹图标。
- “设置”：齿轮图标。

图标 24dp，文字 12sp；选中使用 `primary`。对话页、文本查看页、诊断详情页隐藏底部导航。

首版全局仅运行一个用户任务。其他会话可以浏览和编辑草稿，不能悄悄排队执行。

> “另一个会话正在运行，结束后可以发送。”  
> 操作：“查看运行中的会话”。

**状态与输入：**

| 状态 | 状态文字 | 输入区行为 |
|---|---|---|
| 空闲 | “准备就绪” | 主按钮“发送” |
| 启动中 | “正在启动 Codex…” | 保留草稿，发送禁用 |
| 已提交待确认 | “正在提交…” | 防重复点击 |
| 运行中 | “正在处理”或具体工具动作 | “停止”；有输入时另显示“追加指令” |
| 等待审批 | “等待你的确认” | 停止可用，审批入口常驻 |
| 网络自动重试 | “连接中断，正在重试” | 停止可用；追加可能不可用时保留草稿 |
| 停止请求中 | “正在停止…” | 停止按钮禁用，防重复请求 |
| 正常结束 | “已完成” | 恢复“发送” |
| 用户停止 | “已停止” | 提示“已发生的文件改动会保留” |
| 进程失联 | “连接已中断” | “重新连接”；不能自动重发任务 |
| 失败 | “本轮未完成” | “查看详情”；用户可编辑后再发 |

追加使用 `turn/steer`，带当前 `expectedTurnId`。若 turn 已结束：

> “本轮已结束，追加内容已保留。点击发送可开始下一轮。”

**不自动把失败的追加转换成新任务。**

模型选择弹窗：

- 标题“选择模型”，列表来自 `model/list`，隐藏模型不显示。
- 显示服务端名称、说明、默认标识；不硬编码套餐能力。
- 空：“当前没有可用模型”，按钮“刷新”“检查账号”。
- 错误：“无法获取模型列表”，保留已有有效选择。
- 推理强度来自该模型支持列表；没有可选项时显示“由模型决定”。
- 当前任务运行时可修改下轮配置，标注“下一轮生效”。
- 已发送任务旁记录当时使用的模型和强度，不用当前设置覆盖历史。

计划条：

- 点击展开步骤列表，状态文字：“待开始”“进行中”“已完成”。
- 不把步骤比例称为“任务完成百分比”。
- 无计划就完全隐藏。
- 任务结束但步骤未全完成：显示“本轮已结束，部分步骤未完成”，不自动全打勾。

用量弹窗：

```text
标题：“用量”
“本会话累计：{total.totalTokens} 个令牌”
“最近一次模型调用：{last.totalTokens} 个令牌”
可展开细分：输入、缓存输入、输出、推理输出
分隔线
“账号额度”
按实际窗口显示：“{窗口名称} · 已用 {usedPercent}%”
“预计 {本地时间} 重置”
更新时间
```

- 不把 `last` 命名为“本轮总量”。
- 不用会话累计令牌除以上下文窗口，伪造上下文占用百分比。
- 输出令牌与推理令牌可能存在包含关系，不自行相加。
- 额度缺失：“服务未提供额度信息”；不是“无限额度”。
- 达到限制时在输入区上方显示“当前额度已用尽”，提供实际重置时间；不显示猜测金额。
- 常态用量藏在弹层；接近或达到限制才出现行内提示。

空对话：

> “想先改点什么？”  
> “可以创建文本、整理内容，或修改已有文件。”

示例按钮只填入输入框，不自动执行：

- “创建一份待办清单”
- “看看这个文件夹里有什么”
- “帮我整理这份文档”

### 2.4 审批底部弹窗

首版**只提供一次性决定**，不提供会话记忆、永久规则或“全部允许”。这样“每步确认”与实际交互一致。

```text
底部弹窗〔surface，顶部圆角 24dp，最大高 85% 屏幕〕
├─ 拖动条〔32×4dp〕
├─ 标题行〔图标 24dp＋20sp 标题〕
├─ “{会话名} · 第 1 项，共 2 项”〔12sp〕
├─ 可滚动详情
│  ├─ 操作内容
│  ├─ 工作目录
│  ├─ 请求原因〔存在才显示〕
│  ├─ 额外权限说明〔存在才显示〕
│  └─ “展开完整内容”
└─ 固定操作区
   ├─ 主按钮：“允许这一次”
   ├─ 次按钮：“拒绝此操作”
   └─ 文字按钮：“拒绝并停止本轮”
```

命令审批：

- 标题“允许运行这条命令？”
- 完整命令用 13sp 等宽，长行横向滚动。
- 工作目录显示绝对路径。
- `kind=writeStdin` 时改为“允许向运行中的命令发送输入？”，不能伪装成启动新命令。
- `commandActions` 仅用于辅助摘要，原始命令始终可见。

文件审批：

- 标题“允许修改这些文件？”
- 从关联 `fileChange` item 的 `changes` 读取文件列表和 diff。
- 列出新增、修改、删除、移动，默认展开前 3 个文件名。
- 找不到 item：“正在获取改动详情…”，暂时禁用允许按钮。
- 拉取失败：“无法取得改动详情”，允许“重试”“拒绝此操作”“拒绝并停止本轮”。
- `grantRoot` 仅显示“请求涉及的目录：{路径}”；本地 schema 已标注其语义不稳定，不能写成可靠的目录授权或隔离范围。

按钮映射：

```text
允许这一次       → {"decision":"accept"}
拒绝此操作       → {"decision":"decline"}
拒绝并停止本轮   → {"decision":"cancel"}
```

交互规则：

- 关闭 sheet、按返回、点遮罩都只是收起，审批仍待处理。
- 点击决定后显示“正在提交决定…”，禁用全部决定按钮。
- 收到 `serverRequest/resolved` 后关闭；不能因为本地写入 stdin 成功就宣称执行成功。
- 后台只通知，不强行弹出 Activity。
- 多个请求按到达顺序展示，按请求 ID 区分，不能按 item ID 合并。
- 命令可能修改文件但没有结构化 diff，审批中写“这条命令可能修改文件，未提供改动预览”，不伪造预览。

文本查看：

```text
顶栏〔64dp〕：返回＋文件名＋更多
```

- 默认原文查看，Markdown 文件可切“预览”。
- 1 MiB 以上分页读取，单页约 64 KiB，显示“正在分段查看”。
- 不认识的编码：“无法按 UTF-8 解码”，提供明确的有限编码选项或“复制路径”，不静默用替换字符伪装正常。
- 二进制：“暂不支持预览此类文件”，显示名称和大小。
- 文件外部更新：“文件已变化”，按钮“重新加载”；不打断正在选字。
- 文件删除：“文件已不存在”，按钮“返回目录”。

完全自动启用弹窗：

> **开启完全自动？**  
> 助手将直接运行命令和修改文件，不再逐项确认。它能访问本应用有权限访问的位置；工作区不是独立隔离区。  
> 你仍可随时停止，但已经发生的改动不会自动撤销。

按钮“开启完全自动”“保持每步确认”。

运行中切换模式：

> “当前任务继续使用原模式，新模式从下一轮生效。”

“直连”指 **Java LocalProxy 直连上游**，不是移除 Codex 的 loopback 代理；否则 musl DNS 问题会回来。

设置加载失败保留上次保存值，标注“状态暂未刷新”。任何保存失败都显示“设置未保存”，不能先改 UI 再静默失败。

### 2.7 诊断页

诊断是首版必要功能，应从欢迎、安装失败、设置和运行失败页进入。

```text
顶栏：“自检与诊断”
设备摘要卡片〔14sp〕
“{品牌 型号} · Android {版本} · {ABI}”
“应用 {版本} · Codex {版本}”
说明〔14sp〕
“检查本机运行环境和网络连接，不读取你的项目内容。”
主按钮：“开始自检”
检查列表〔每项最小高 72dp〕
├─ 状态图标〔24dp〕
├─ 检查名称〔16sp〕
├─ 结果摘要〔14sp〕
├─ 耗时〔12sp〕
└─ 展开详情
结果摘要卡片
底部：“复制诊断结果”＋“重新检查”
```

建议检查顺序：

| 检查 | 实现与通过条件 | 默认超时 |
|---|---|---|
| 运行组件 | 文件存在、ABI、可执行权限、剩余空间 | 5 秒 |
| Codex 版本 | 同一运行环境启动 `codex --version`，退出 0 | 10 秒 |
| 协议初始化 | 临时 app-server 完成 `initialize`，再发 `initialized`；记录耗时 | 20 秒 |
| 执行命令 | 通过 `command/exec` 执行 `/system/bin/sh -c 'echo pocket-codex-ok'`，退出 0且输出符合预期 | 10 秒 |
| Shell 兼容 | 通过 `command/exec` 执行私有 `bash -lc`，打印固定标记并检查 PATH、toybox 可见性 | 10 秒 |
| 本地代理 | 缺失认证得到 407；合法认证可建立预期连接 | 10 秒 |
| 外网与证书 | 专用 Java 探针经 LocalProxy 建立 CONNECT，再用与应用一致的 CA 策略完成 TLS，访问 `https://chatgpt.com` | 20 秒 |
| 账号状态 | 已登录时 `account/read`，否则标记跳过 | 15 秒 |
| 端到端对话 | 单独按钮“测试真实对话”，由真实 Codex 请求固定短回复 | 60 秒 |

关键区分：

- `command/exec` 是应用主动发起的诊断命令，不代表模型 turn 的审批路径已经通过。
- Java HTTPS 探针通过，不代表 Codex 的 TLS/WebSocket 已通过。
- “测试真实对话”显示“会使用少量账号额度”，由用户点击，使用专用诊断工作区。
- 没有确切传输证据时，不显示“WebSocket 已通过”；可以显示“真实模型请求通过，传输方式未确认”。
- `chatgpt.com` 返回 403：显示“已连接，但网站返回 HTTP 403”，网络层通过、访问检查警告，不能误报 DNS 失败。
- 无登录、无二进制等依赖缺失用“已跳过”，不连续报一排失败。
- 正在执行用户任务时：“任务运行中，自检将在停止后可用”，首版不额外启动第二个运行时。
- 本地执行测试失败后仍可继续独立的 Java 网络检查。
- “取消自检”关闭探针连接和诊断进程，保留已完成结果。

状态文案统一：

- “等待检查”
- “正在检查…”
- “通过 · {耗时}”
- “需要留意 · {原因}”
- “失败 · {简短原因}”
- “已跳过 · {依赖原因}”
- “已取消”

复制内容包含：

```text
应用版本、Codex 版本、Android API、ABI、设备型号
页大小（能取得时）、存储可用空间、通知/存储权限状态
下载来源、代理模式、证书模式
每项检查的开始时间、耗时、退出码或 HTTP 状态
initialize 耗时
有限长度的脱敏错误尾部
```

不包含登录代码、API 密钥、令牌、完整代理认证 URL、账号邮箱、项目内容。路径使用 `<应用目录>`、`<工作区>` 替代。

复制前提示：

> “诊断结果已隐藏凭据和项目路径。你可以先查看，再发给开发者。”

单凭退出码不能断言 SIGSYS；文案应为“进程异常退出，原因待确认”，有系统崩溃证据才显示具体信号。

## 3. 对话 item 的视觉规格

### 3.1 共用卡片

工具卡片统一：

```text
卡片〔surface，outline 1dp，圆角 12dp，内边距 12dp〕
├─ 标题行〔最小高 32dp〕
│  ├─ 类型图标〔20dp〕
│  ├─ 标题〔14sp，中等字重〕
│  ├─ 状态〔12sp〕
│  └─ 展开箭头〔点击区域 48dp〕
├─ 摘要〔14sp，textSecondary〕
├─ 内容区〔surfaceAlt，圆角 8dp〕
└─ 操作行〔存在才显示，最小高 40dp〕
```

卡片之间 8dp；用户消息与 Agent 回答之间 16dp。颜色只用于图标、状态和局部背景，不给整张运行卡片铺强色。

### 3.2 各类 item

| 类型 | 结构和文案 | 折叠规则 |
|---|---|---|
| `userMessage` | 右对齐浅底气泡，最大宽度 92%，正文 16sp；附件或路径独立显示 | 超过 12 行显示“展开消息”；复制和重新编辑放长按菜单 |
| `agentMessage` 正式回答 | 左对齐，无厚重外框，正文 16sp，Markdown | 默认展开；不因完成而收起 |
| `agentMessage` commentary | 进度小图标＋“执行说明”，正文 14sp、次文字色 | 运行时展开；完成后可归入“执行过程”，不丢内容 |
| `agentMessage` phase 未知 | 普通 Agent 消息 | 不猜测是最终回答，也不触发任务完成 |
| `agentMessage` questions | 消息下附问题卡片、建议选项和输入入口 | 不预选即提交；异步问题不冒充阻塞 RPC 审批 |
| `reasoning` | 小灯泡图标＋“推理摘要”；展示服务端 summary | 默认折叠；没有摘要时写“未提供摘要”，不虚构内容 |
| `plan` | 清单图标＋“方案”，正文 Markdown | 预览 6 行；与 turn 的步骤进度分开 |
| `commandExecution` | 终端图标＋状态＋命令、cwd、输出、耗时 | 见下一节 |
| `fileChange` | 文件差异图标＋“修改 {N} 个文件”＋状态 | 默认文件摘要，点开 diff |
| `webSearch` | 搜索图标＋“搜索网页”，查询、结果链接 | 运行时展开；完成后默认折叠 |
| `imageView` | 图片图标＋“查看图片”＋路径 | 可读且解码受限时显示缩略图，否则仅路径 |
| `functionCallOutput` | 工具图标＋工具名＋输出摘要 | 默认折叠，文本最多 6 行 |
| `mcpToolCall` / `dynamicToolCall` | 工具图标＋工具名＋状态；参数、结果分区 | 首版兼容显示，不提供安装或执行入口；远端 HTML 不嵌入 |
| `collabAgentToolCall` | 分支图标＋“协作任务”＋工具动作、状态 | 默认折叠；首版不主动启用多 Agent |
| `subAgentActivity` | 紧凑事件行：“子任务已开始 / 已完成 / 已中断” | 默认折叠到执行过程 |
| `sleep` | 时钟图标＋“等待”＋服务端给定时长 | 单行；不能仅由时长推断 turn 已结束 |
| `contextCompaction` | 单行“已整理会话上下文” | 无正文 |
| 进入/退出 review | 单行“进入审查 / 结束审查”，附服务端文本 | 长正文折叠 |
| `hookPrompt` | “运行环境提示”＋片段摘要 | 默认折叠，不作为用户消息 |
| `imageGeneration` | “生成图片”＋状态 | 首版显示已保存路径或受限预览；未知格式不解码 |
| 未知类型 | “暂不支持显示此记录”＋“查看详情” | 保存原始类型和受限数据，不崩溃、不自动执行 |

### 3.3 `commandExecution` 四态

| 状态 | 图标、颜色 | 标题与内容 |
|---|---|---|
| `inProgress` | 小进度图标，`primary` | “正在运行命令”；命令默认最多 3 行，输出显示最近 8 行 |
| `completed` | 勾选，`success` | “命令已完成”；已知时显示“退出码 0 · 1.2 秒” |
| `failed` | 感叹号，`error` | “命令执行失败”；显示真实退出码和最后 8 行输出 |
| `declined` | 禁止图标，`textSecondary` | “已拒绝此操作”；不显示伪造退出码和运行耗时 |

补充规则：

- `completed` 且退出码缺失：写“已完成，未提供退出码”，不用“执行成功”。
- 状态与非零退出码矛盾：显示“已结束 · 退出码 {值}”，保留异常诊断。
- 审批期间覆盖展示“等待确认”，但不要覆盖底层服务端状态。
- 已允许后显示“已允许，等待执行”，不能提前打绿勾。
- 进程失联是本地附加状态：“执行状态待确认”，不要伪装成服务端 `failed`。
- 输出为空：“尚无输出”或“未产生输出”。
- 成功卡片默认折叠；失败卡片默认展开最后 8 行。
- 输出含 ANSI 时移除控制序列；不把终端输出当 HTML。
- `aggregatedOutput` 是合并输出，不伪造 stdout/stderr 两个通道。

### 3.4 `fileChange` 与 diff

标题状态：

- 运行中：“正在修改文件”
- 等待审批：“等待确认文件改动”
- 完成：“文件改动已应用”
- 失败：“文件改动未完成”
- 拒绝：“已拒绝文件改动”

失败不代表没有任何文件被改动，应补充：

> “部分改动可能已经写入，请查看文件。”

文件行：

```text
[新增/修改/删除/移动图标] 相对路径
+12  -4
```

工作区外路径显示绝对路径和“工作区外”标识。这个标识是事实提示，不是安全拦截。

diff 采用单栏 unified 展示：

- 13sp 等宽，行高 20sp。
- 两列行号：旧行号、新行号，各最小宽 32dp，允许随位数扩展。
- 保留 `+`、`-` 和空格前缀。
- 新增行 `addBg`，删除行 `errorBg`；文字仍用可读高对比色。
- hunk 头使用 `surfaceAlt/textSecondary`。
- 只有标准 hunk 信息完整时才计算行号；无法解析就展示原始 diff，不猜行号。
- 卡片内每文件预览最多 12 行；超过显示“查看完整差异”。
- 全屏差异页以 200 行为一批加载，保留全部可获取内容。
- 超过 3 个文件时折叠文件列表，显示“另有 {N} 个文件”。
- 非文本或无 diff：“未提供文本差异”。
- 移动显示“{旧路径} → {新路径}”，兼容 schema 的 `move_path` 字段。
- 不把各个历史补丁的增删数简单相加当成净改动。
- `turn/diff/updated` 用于“本轮改动”独立入口，始终替换同一份汇总。

首版没有 Git，不提供“回滚本轮”或“全部撤销”。文件查看器打开的是**当前文件**，diff 是**当时的改动记录**，两者要区分。

### 3.5 Markdown 范围

支持：

- 段落、换行、标题、粗体、斜体、删除线。
- 有序和无序列表、任务列表、引用、分隔线。
- 行内代码、代码块。
- 普通链接、横向滚动表格。

不支持自动执行或加载：

- 任意 HTML、JavaScript、iframe。
- Mermaid、公式的首版专用渲染。
- 自动获取远程图片。
- 未验证的应用深链、`intent:`、任意 `file:`。

代码块有“复制代码”，超过 20 行折叠预览，提供“查看全部”。本地文件链接走自己的路径校验和查看器；点击失败显示“文件不存在或无法访问”。

流式阶段最多每秒 4 次 Markdown 更新；完成立即渲染最终文本。用户正在选字或浏览历史时不抢滚动。

## 4. 会话状态模型与 reducer

### 4.1 数据结构

不要用一个 `isRunning` 包办所有状态。至少分成运行时、thread、turn、item、待回复请求五层。

```text
AppState
  runtime
    generation                 // 每次启动 app-server 递增
    connectionState            // stopped/starting/ready/disconnected
    initializeDurationMs
    activeThreadId
    activeTurnId
  threads: Map<threadId, ThreadState>
  pendingRequests: Map<RequestKey, PendingRequest>
  account
  rateLimitsById
  outbox: Map<clientMessageId, OutboxEntry>

ThreadState
  id, workspaceId, cwd, title
  serverStatus                 // 保存原始 ThreadStatus
  effectiveApprovalPolicy
  effectiveModel, effectiveEffort
  turnOrder
  turns: Map<turnId, TurnState>
  historyPaging
  draft
  lastSeenAt

TurnState
  id
  serverStatus                 // inProgress/completed/interrupted/failed
  localStatus                  // submitting/reconnecting/unknown 等
  startedAt, completedAt, durationMs
  itemsView
  itemOrder
  items: Map<itemId, ItemState>
  plan: {explanation, steps[]}
  latestDiff
  error
  retryState
  usage
  hydrationState

ItemState
  id, type
  canonicalPayload
  lifecycle                    // placeholder/started/completed
  startedAtMs, completedAtMs
  streamedText
  reasoningSummaryByIndex
  reasoningContentByIndex
  outputBufferRef
  fileChangeOutputRef
  pendingRequestKeys[]
  lastLiveRevision
  presentationState            // 展开、选字等本地状态

RequestKey
  generation
  rpcIdType                    // string 或 number
  rpcIdValue

PendingRequest
  key, method
  threadId, turnId, itemId
  approvalId
  rawParams
  state                        // waiting/responding/resolved/stale
  chosenDecision
  resolutionReason             // 已知时记录

OutboxEntry
  clientMessageId
  threadId
  expectedTurnId
  kind                         // start 或 steer
  text
  state                        // draft/sending/accepted/unknown/failed
```

准则：

- 所有 reducer 更新串行执行，Activity 仅订阅快照。
- 协议读取线程只解码、投递，不做数据库同步写入或调用同步 RPC。
- 服务端时间戳按字段单位处理：turn 的 `startedAt` 是秒，item 的 `startedAtMs` 是毫秒。
- 展示耗时用单调时钟估算，服务端最终 `durationMs` 优先。
- 原始 payload 保留未知字段；UI 不依赖所有字段必填。
- item 顺序使用服务端返回顺序和直播到达顺序，不按 ID 字典序排序。

### 4.2 通知与请求归并

| 事件 | reducer 行为 |
|---|---|
| `turn/started` | 按 turn ID upsert；记录服务端状态、时间；设置活动 turn。只初始化新 turn 的计划和临时数据，不清空旧历史 |
| `item/started` | 按三元键 upsert；写初始完整 item。已有占位和早到 delta 时补齐元数据，不重复插入 |
| `item/agentMessage/delta` | 按 item ID追加 `delta`；缺 item 时建占位；收到正式 item 后校准类型 |
| `item/plan/delta` | 更新 plan item 的临时文本；不直接修改结构化步骤进度 |
| `item/reasoning/summaryPartAdded` | 确保 `summaryIndex` 对应段存在，不重复增加段 |
| `item/reasoning/summaryTextDelta` | 追加到指定 `summaryIndex`，不能全部拼到第 0 段 |
| `item/reasoning/textDelta` | 追加到指定 `contentIndex`，与 summary 分开存储 |
| `item/commandExecution/outputDelta` | 追加到命令输出缓冲；只刷新可见尾部 |
| `item/fileChange/outputDelta` | 追加补丁工具输出日志，不当作 diff，也不改写 `changes` |
| `item/commandExecution/terminalInteraction` | 记录终端交互信息；不能据此推断命令成功或结束 |
| `item/completed` | 完整 item 是最终权威内容；替换临时文本和完整字段，不再追加一遍。记录完成时间 |
| `turn/plan/updated` | 整体替换 explanation 和 steps；步骤可增加、重排，不能假设进度单调增长 |
| `turn/diff/updated` | 替换 `latestDiff`；不追加旧 diff |
| `error` 且 `willRetry=true` | 保存最近错误，设置重试提示；保持 turn 活跃，不发送最终失败通知，不自动重启进程 |
| `error` 且 `willRetry=false` | 显示不可自动重试错误；以最终 turn 状态收束。未收到终态时安排状态对账，不无限转圈 |
| `turn/completed` | 保存最终状态和 error；合并携带的 items，遵守 `itemsView`；释放活动 turn，结束重试提示 |
| `thread/status/changed` | 保存 status；`waitingOnApproval`、`waitingOnUserInput` 用于展示。没有对应本地请求时显示“正在同步待处理事项”，不编造审批内容 |
| `thread/tokenUsage/updated` | 替换对应 thread 的服务端累计快照，保存该 turn 的最新观察值；绝不能对 total 再累加 |
| `account/rateLimits/updated` | 按 `limitId` 合并可用字段；缺失或 null 通常不清除旧元数据；保留更新时间 |
| `serverRequest/resolved` | 按当前 generation、原始 request ID 找请求，标记 resolved；关闭对应弹窗，推进下一请求；不推断是允许还是拒绝 |
| 审批请求 | 保存原始 RPC ID 和参数；关联 item；进入待处理队列，立即刷新 UI 和通知 |
| 进程退出 | 当前 generation 的请求全部 stale；活跃任务标记“状态待确认”；outbox 的已发送未确认项保持 unknown；禁止自动重发 |
| 未知通知 | 有界记录，忽略其未知 UI 含义，不停止整个会话 |
| 未知服务端请求 | 回复明确的“不支持该方法”协议错误，并记录不兼容提示；不自动批准 |

`item/completed` 之后，迟到 delta 不得把 item 改回运行中。若发生内容冲突，记录异常并获取快照。

命令输出处理稍作区分：

- 最终 `aggregatedOutput` 非 null：它是最终显示内容来源。
- 最终字段缺失或 null：保留已收到的输出，不能无条件清空。
- 显示缓冲受限，原始流继续消费；截断时标注“较早输出未保留”。

计划完成不代表 turn 完成，Agent 最终回答也不代替 `turn/completed`。

### 4.3 审批的特殊规则

本地 schema 的审批请求通常还有 `threadId`、`turnId`、`startedAtMs`。你实测强调的 `itemId/reason/grantRoot` 是文件审批的业务内容，解析器仍应容忍不同 payload 的字段缺失。

- 请求身份用 RPC ID，不是 item ID。
- 同一 item 可能产生多个审批回调，`approvalId` 需要保存。
- 同 ID、同参数重复请求：不重复弹窗。
- 同 ID、不同参数：视为协议异常，不能沿用旧决定。
- 缺 thread/turn 但 item 唯一可定位时允许关联；无法唯一关联时保留待处理错误，不向任意会话回复。
- 文件改动缺详情时，使用 `thread/items/list` 查关联 item；找不到就禁止“允许”。
- 首版不发 `acceptForSession`，不写 execpolicy amendment。
- 回复仍在原 JSON-RPC 连接上，使用原始 ID 类型。
- `respond()` 需要返回写入结果；当前 `void` 不能让 UI判断“未写入”和“已写入待确认”。

`serverRequest/resolved` 仅说明服务端不再等待该请求，**不是审批接受回执，更不是文件写入成功回执**。

任务终止后，剩余审批从可操作队列移除并保留记录“本轮已结束”。不得拿旧请求 ID在新 app-server 连接上继续回复。

### 4.4 用户消息与重试

发送前：

1. 生成 `clientUserMessageId`。
2. 持久化 outbox 和草稿。
3. UI 插入“正在发送”的本地消息。
4. 调用 `turn/start` 或 `turn/steer`。

服务端 `userMessage.clientId` 匹配后，用真实 item 替换本地消息，不重复显示。

请求超时：

- “发送结果待确认”，保留消息。
- 查询历史寻找 `clientId`。
- 找到则归并成功。
- 没找到且没有可靠结论时不自动重发。
- `clientUserMessageId` 用于关联，不把它当作服务端承诺的幂等键。

### 4.5 历史恢复与分页

官方文档支持分页读取历史而不必先恢复执行；具体参数以本地 schema 为准。[Codex App Server 文档](https://learn.chatgpt.com/docs/app-server)

**仅浏览历史：**

- 可以直接 `thread/turns/list`、`thread/items/list`。
- 不因为用户点开旧会话就重新执行任务。
- app-server 不可用时展示本地缓存，明确“历史尚未完整加载”。

**准备继续对话：**

```json
{
  "method": "thread/resume",
  "params": {
    "threadId": "已有会话标识",
    "excludeTurns": true,
    "cwd": "已校验的工作区绝对路径",
    "sandbox": "danger-full-access",
    "approvalPolicy": "untrusted",
    "approvalsReviewer": "user"
  }
}
```

- 不传 `path/history` 来替代 ID。
- 根据用户模式切换 `untrusted/never`。
- 返回后读取实际 `approvalPolicy/cwd/model/reasoningEffort`；若与 UI 选择冲突，禁止在错误模式下悄悄发送。
- `thread.turns=[]` 配合 `excludeTurns=true` 不等于历史为空。

turn 分页：

```json
{
  "method": "thread/turns/list",
  "params": {
    "threadId": "已有会话标识",
    "sortDirection": "desc",
    "limit": 20,
    "itemsView": "summary"
  }
}
```

如果 resume 返回 `turnsBackwardsCursor`，作为这次倒序请求的 cursor。它的首批结果**包含锚点 turn**，按 ID upsert。

- 倒序数据放入时间线时转换为时间正序。
- 继续向旧历史加载使用响应 `nextCursor`。
- `backwardsCursor` 用于反转读取方向，不与 `nextCursor` 混用。
- `summary` 只有显示摘要；`notLoaded` 的空 items 是未加载；都不能标记“这个 turn 没有工具记录”。

item 分页：

```json
{
  "method": "thread/items/list",
  "params": {
    "threadId": "已有会话标识",
    "turnId": "目标轮次标识",
    "sortDirection": "asc",
    "limit": 50
  }
}
```

- `data` 元素是 `ThreadItemEntry`：包含 `turnId`、`item` 和可选时间戳，不是裸 item。
- 继续加载使用 `nextCursor`。
- 不传 turnId 可跨整个 thread 读取。
- resume 的 `itemsBackwardsCursor` 按其说明配合 `sortDirection:"desc"`，用于跨 thread 的倒序回填；不要混入另一个 turn 的局部分页。
- 普通 item anchor 是**排他锚点**，要求非空 turnId；与 resume 返回的包含锚点游标不是同一种语义。
- 游标是不透明值，不解析、不自己构造。

**直播与历史并发：**

- 发起历史请求时记录本地 revision。
- 历史响应补充缺失 item 和顺序；不覆盖请求发出后更新的活跃 item。
- 对恢复时仍在运行的 item，展示“同步中”，不要把旧快照文本和新连接 delta 盲目拼接。
- 本地 schema 没有可普遍依赖的事件序号/文本偏移，因此无法靠“相同 delta 字符串去重”实现正确恢复；重复文字本来就可能合法。
- 最终 `item/completed` 校准文本；缺终态时再获取完整 item。
- 分页失败保留已读内容，显示“较早记录加载失败，点击重试”。

**重连后的审批：**

- 原进程仍活着、只是 Activity 重建：直接订阅 Service 中的现存待处理请求。
- app-server 已重启：旧请求全部失效，仅响应新连接实际收到的请求。
- `thread/resume` 返回活跃状态，并不等于它列出了所有审批。没有重新收到请求时不能恢复一个可点击的旧审批弹窗。

### 4.6 建议补的 reducer 回放用例

优先补实际行为测试：

- delta → completed，最终文本不重复。
- delta 先于 started。
- 同 item 多个审批请求。
- 文件审批先到、changes 后到。
- resolved 先于本地点击。
- turn 已结束时 steer 返回错误，草稿仍在。
- 历史摘要不能覆盖完整工具记录。
- 活跃 delta 与旧历史响应交错。
- 额度稀疏更新、`false/0` 不被误当缺失。
- app-server 重启后旧审批不可回复。
- turn/start 超时后按 clientId 对账，不重复执行。
- 长输出和最终完整 payload 都受内存限制。

## 7. 第一轮需要修改的结论，以及 core 审阅意见

### 7.1 设计结论修改

| 第一轮 | 本轮调整 |
|---|---|
| 共享文件采用 SAF 导入导出 | 改为可选的共享存储直接路径工作区，SAF 后置 |
| 默认“谨慎执行”，不能称每步确认 | 依据固定版实测，改为“每步确认”；仅对已验证的命令执行与文件修改范围作承诺 |
| 审批可记住会话授权 | 首版去掉，避免破坏“每步确认”的语义 |
| 严格只读作为潜在档位 | 首版 UI 完全不显示，不自动降级 |
| 还需优先进程组方案 | 首版不另做，采用正常 interrupt 和应用生命周期处理；仍需正确处理子进程异常退出 |
| shell 兼容方案待验证 | 接受私有 bash 链接＋mksh 家族兼容方案；开发指令明确“不是完整 Bash” |
| helper 可执行路径待验证 | 接受 chroot 验证结果，真机诊断继续覆盖 |
| DNS 可能需要 rootfs/proot | 不引入；Codex 经数字 loopback 代理，Java 处理目标解析 |
| SSE、WSS 代理支持待确认 | 上游代理路径已有你的实测；Java LocalProxy 的真实 Codex 集成仍单列待验证 |
| 镜像 integrity、Range 未确认 | 接受你提供的已验证结果，保留每次安装校验 |
| 兼容范围可写 Android 8–16 | 改写为“设计面向 minSdk 26 的 64 位设备，具体兼容性以设备自检为准” |
| 内存与启动目标较确定 | 作为性能目标，不作为已测事实；诊断展示 initialize 耗时 |
| 工具可逐步扩展 | 首版明确不装 Git、Node、Python、rg |
| code-mode-host 倾向统一开启或关闭 | 不因 Luna 对滚动源码的推断改动已验证配置；保留配套二进制，按固定版实际默认及测试结果运行 |

两点要纠正得更明确：

1. **每步确认不是项目隔离，也不是所有网络请求都需确认。** 它对应你已测过的命令和补丁审批，不能扩大成“所有读取、模型请求都经用户批准”。
2. **私有工作区也不能隔离同应用 UID 下的运行组件和凭据。** 给目录设 0700、给凭据设 0600，不能挡住同 UID 的 Agent 子进程。

### 7.2 core 中应优先修改的问题

下面是对源码的静态审阅，不把“23 个 JVM 测试通过”扩大成 Android 行为已经验证。

#### A. `CodexRuntime`：默认审批与产品设计冲突

当前 `writeConfig()` 固定写：

```toml
approval_policy = "never"
```

而 `Config` 没有审批模式字段。

应改为：

- `Config` 增加审批模式，默认 `untrusted`。
- `thread/start`、`thread/resume` 和需要覆盖的 `turn/start` 使用同一份有效设置。
- 读取服务端返回值核对。
- 确保恢复旧会话不会继承一个 UI 没显示的自动模式。

`hasAuth()` 只能表示“存在凭据文件”，不能表示“已登录”。建议重命名为类似 `hasStoredCredentials()`，登录状态由账号检查维护。

#### B. `DeviceLogin`：计时、失败计数和成功状态需要拆开

具体问题：

- 期限和退避使用 `System.currentTimeMillis()`，系统时间变化会提前换码或延迟重试。
- 每次拿到代码就把 `failures=0`，如果服务反复“发码后马上失败”，可能永远到不了六次失败上限。
- 登录日志超过读取上限后 `readFile()` 返回空串，但文件本身仍可能继续增长。
- `start()` 可重启同一个实例，但应同时考虑实例复用、旧状态清理和 attempt 标识。
- CLI 退出 0＋非空 auth 文件就发 `SUCCESS`；UI还需要区分“凭据已保存”和“账号已确认”。
- 提前换码前需要再次检查进程是否刚好成功，避免在凭据交换阶段直接终止。
- `kill()` 超时后若仍未证实旧进程退出，不应立刻启动新的登录进程。

建议：

- 注入 `Clock`，Android 实现用 `elapsedRealtime()`。
- 增加连续失败窗口、后台登录最长等待时间。
- 每次尝试使用独立 ID和日志文件。
- 日志有限增长，超限明确报错。
- 明确取消/拒绝授权后暂停，让用户决定重试，避免不断弹回登录循环。
- 退出码 0 后交给账号验证阶段，不立即展示“已连接账号”。

#### C. `DeviceAuth`：已修过期误判，但分类仍偏宽

当前 `classify()` 把任何 `timeout/timed out` 优先判为过期，因此“网络请求超时”仍可能落到 EXPIRED。

应改为：

- 只有明确设备授权到期上下文判 EXPIRED。
- 连接/TLS/代理超时判 NETWORK。
- 模糊超时判未知失败，不猜成代码过期。
- `parse()` 的 URL 当前允许任意 HTTPS 链接，应做官方主机和路径校验。
- 有效期数字用有界解析，防超长数字导致 `Integer.parseInt` 异常。
- 代码候选应限定在设备码说明附近，避免把帮助文本中的大写标识识别为登录码。

你已修复的 `(expires in 15 minutes)` 必须保留为明确回归样本。

#### D. `LocalProxy`：关闭和资源释放是当前最实在的问题

源码中 `close()` 关闭监听 socket 并 `shutdownNow()`，**不会可靠关闭已经在阻塞 socket 读取中的连接**。

另外：

- `open()` 创建 socket 后，如果 connect、上游头读取等抛异常，部分路径没有关闭该 socket。
- 池上限 256，每条隧道还创建一个上行线程，手机上并发预算过大。
- `SYSTEM` 选择代理失败或没有 HTTP 结果时会直连；这可能绕开用户原本的代理意图。
- 系统代理选择 URI 固定为 HTTPS，普通 HTTP 的 PAC/代理决策可能不同。
- 普通 HTTP 也对上游执行 CONNECT，很多上游代理不允许 CONNECT 到 80 端口。
- `readHead()` 遇到 EOF 时可能返回不完整头部，调用方仍继续解析。
- 只有 socket 读超时不能限制缓慢逐字节发送的总头部时间。
- 本地 Basic 认证和上游代理认证是两件事；目前代码实现的是前者。
- `start()` 在 close 后不能可靠复用，不应把旧实例当可重启对象。

建议首版修正：

- 跟踪所有活跃 client/remote socket，close 时逐个关闭。
- `open()` 异常路径统一 finally 关闭未移交 socket。
- 并发隧道先限制为 16或32，满额返回明确状态。
- 系统返回不支持的代理、代理选择异常时明确报错，不静默直连。
- 普通 HTTP 经上游使用适当的正向代理请求；若暂不支持，清楚标注。
- HTTP 请求头完整性、大小和总耗时都有界。
- 添加“长连接空闲后仍可用”“代理关闭后无残留 socket”“真实 Codex Basic CONNECT”集成验证。

#### E. `Installer`：目前不是“验证成功后安全升级”

当前流程在切换 current 后删除所有旧版本，但还没有实际启动新二进制。这会导致：

> 下载和解压成功，新版本无法运行，旧版本却已删除。

应拆成：

```text
下载 → 校验 → 解压候选目录 → 启动候选检查 → 切换 current → 保留上一版本
```

其他具体问题：

- 206 未校验 `Content-Range` 的起始位置。
- 没有 ETag/If-Range 身份约束，续传拼接错误只能最后靠 SHA-512 发现。
- 416 直接结束下载，应该检查远端总长度与本地长度；不一致则重新下载。
- 206 的 Content-Length 未知时，`have + (-1)` 会得到错误 total。
- `Package.size` 实际来自 `unpackedSize`，不能拿来当压缩包下载体积。
- 空间估算固定为约 604 MiB，没有随版本、升级保留策略变化。
- 解压写入遇到空间不足统一报 CORRUPT，用户会误以为安装包损坏。
- 元数据获取阶段没有纳入同样的取消和状态回调。
- 当前只验证“该来源提供的 hash 与 tarball 一致”；这不等于独立验证官方来源。固定已测版本可随 App 内置两种 ABI 的官方 SHA-512。
- URL重定向需保持 HTTPS 并设跳转上限。
- 版本号进入目录路径前要校验允许格式。
- 同版本“已安装就返回”会阻止重新校验损坏文件，需要专用重装路径。
- 安装器、app-server、登录进程对版本目录的操作应由同一运行时协调，避免使用中被删除。

#### F. `TarReader`：白名单解包方向正确，解析边界还需收紧

优点是输出路径来自精确的允许列表，常见 tar 路径穿越没有直接落到任意目标路径。

需修：

- PAX 长度是 UTF-8 **字节数**，当前按 Java 字符近似会错位。
- PAX 记录长度、边界、数字溢出要检查。
- GNU 二进制 size 解析可能溢出 long；需要非负和上限检查。
- 重复命中目标 entry 不能重复累计 `found`；使用集合并拒绝重复目标。
- 限制单个条目、累计扫描字节和解压写入字节。
- 跳过巨大无关 entry 时也要能够响应取消。
- 全局 PAX 当前被读走但未解释，应明确支持范围，不能默默接受可能影响后续尺寸的扩展。
- 解压失败区分“压缩包损坏”“磁盘不足”“取消”“文件写入失败”。

#### G. `AppServer`：RPC 已够起步，但还不够驱动可靠 UI

当前值得优先处理：

1. `readLine()` 无长度上限，单条超大事件可造成内存压力。
2. 回调运行在读线程；调用方若在回调里调用同步 `call()`，会阻塞读响应。
3. 异步 `request()` 没有默认超时，pending 可能长期累积。
4. `respond()` 忽略 send 结果，审批 UI无法知道提交失败。
5. `RpcError` 丢弃服务端 error 的 `data`，限制错误分类和诊断。
6. stdout 读取结束后直接 `waitFor()`，若进程仍存活，退出处理可能一直卡住。
7. 退出清理时某个 callback 抛异常，可能阻断后续 pending 清理和 `onExit`。
8. `close()` 的 stdin 关闭与并发写入需要统一协调。
9. 请求注册、进程退出、pending 清空有竞态，应由单一连接生命周期管理。
10. stderr 的有限行数做得对，但仍需统一脱敏后才能展示或复制。

建议：

- 加协议行大小上限和有界事件队列。
- 用串行事件执行器投递回调。
- 区分可重试查询与非幂等操作超时；后者走对账。
- 所有退出清理保证最终执行，逐个捕获回调异常。
- 保存 connection generation，防止旧实例回调污染新状态。
- 初始化成功前禁止普通业务请求；完成 `initialize → initialized` 后才发布 ready。

#### H. `Json`：协议解析不能过度宽容

当前解析器会接受部分非法 JSON：

- 字符串中未转义控制字符。
- 部分非标准数字形式，如前导零或末尾小数点。
- 极大浮点数可能解析为无穷大，序列化时又变成 null。

建议严格校验 JSON 数字语法、控制字符、大小与深度。审批 RPC ID 要保留字符串/整数类型；不能把无法精确表示的大整数悄悄转成浮点数。
