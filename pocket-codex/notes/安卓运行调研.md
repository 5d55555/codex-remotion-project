# Luna：安卓上跑 Codex CLI 的调研（联网）

# 结论摘要

这个方案的主要技术风险不是“Android 不支持静态 Linux 二进制”这一点，而是 **app 进程的执行权限、Android seccomp 策略、缺少常规 Linux 文件系统环境，以及 Android 对后台子进程的管理**。`targetSdkVersion=28` 在 Android 14/15/16 仍高于系统最低可安装门槛，Termux 也用它来保留私有目录中执行文件的能力；但它会触发旧 target 警告，并不适合通过 Google Play 发布。

对于 syscall 白名单，不能从 Linux 内核版本直接推断“Android app 一定能调用”。AOSP 对各架构的 app seccomp filter 有版本和设备差异；遇到过滤器配置为 trap 的调用，确实可能直接以 `SIGSYS` 杀进程。对你列出的 14 个调用，我没有找到一份覆盖 Android 10–16、所有 AOSP 版本和 OEM 的官方逐调用白名单时间表，因此下面会区分“已确认”与“查不到统一结论”。

## 1. W^X、低 target 安装和警告

- Android 10 起，target 29 或以上的应用不能直接 `exec()` 自己 app 数据目录中的普通可执行文件。Termux 的官方 wiki 将这个限制归因于 W^X SELinux 策略；Termux 发行版则说明它用 `targetSdkVersion=28` 保留了执行能力。[Termux 执行环境说明](https://github.com/termux/termux-packages/wiki/Termux-execution-environment) [Termux Play Store 背景说明](https://github.com/termux-play-store)

- **对 target 28：**从 Android 14、15、16 的安装门槛和当前 Termux 资料看，target 28 没有被这些系统最低门槛阻止，且仍在 Android 10 W^X 限制的 target 28 兼容侧。Termux 用户与维护者也明确把 target 28 作为私有目录执行的原因。[Termux 讨论](https://github.com/termux/termux-app/discussions/4564)  
  但我没有找到一份 AOSP 官方测试矩阵，逐项证明你这类静态 `ET_EXEC` 在每个 Android 14、15、16 设备上都必定可执行。OEM SELinux 修改、文件权限、挂载选项等仍可能影响结果。

- 官方文档给出的最低可安装 target 门槛：

  | 系统版本 | 最低 target SDK | target 28 能否通过该门槛 |
  |---|---:|---|
  | Android 14 | 23 | 能 |
  | Android 15 | 24 | 能 |
  | Android 16 | 24（目前查到的当前资料） | 能 |

  Android 14、15 的门槛分别见官方行为变更文档。[Android 14](https://developer.android.com/about/versions/14/behavior-changes-all#minimum-target-api-level) [Android 15](https://developer.android.com/about/versions/15/behavior-changes-all) Android 16 的官方页面未检索到独立的门槛变更说明；当前资料显示仍为 24。[Android 最低 target 门槛汇总](https://bayton.org/android/android-minimum-targetsdk-matrix/)

- **“此应用专为旧版 Android 打造”警告：**Android 的系统对话框按 `targetSdkVersion < Build.VERSION.MIN_SUPPORTED_TARGET_SDK_INT` 判断是否显示，而不是按“低于 Android 版本两级”直接写死。[AOSP `AppWarnings`](https://android.googlesource.com/platform/frameworks/base/+/master/services/core/java/com/android/server/wm/AppWarnings.java) Android 14/15/16 设备各自实际的 `MIN_SUPPORTED_TARGET_SDK_INT` 值，应以设备构建为准；我没有找到官方文档列出这三个版本统一固定的数值。Google Play Protect 的相关旧 target 警告则有另一套说明：当 target 比当前 API 低超过两个版本时可能提示。[Play Protect 警告指南](https://developers.google.com/android/play-protect/warning-dev-guidance)

- **Google Play 与侧载要分开看：**Google Play 对新应用及更新有更高 target 要求，target 28 不符合当前 Play 发布要求；侧载时，Play Protect 可能显示“面向旧版 Android”的警告，但这不等同于 AOSP PackageManager 的最低 target 安装阻断。Play Protect 是否弹窗、是否允许继续，取决于设备与 Play Protect 判定；我没找到 Google 官方资料保证每个 target 28 侧载 APK 都会被拦截或都能“继续安装”。[Google Play target API 要求](https://developer.android.com/google/play/requirements/target-sdk) [Play Protect 警告指南](https://developers.google.com/android/play-protect/warning-dev-guidance)

## 2. app 进程 seccomp 与相关 syscall

### 过滤器行为

Android 对 zygote 派生的 app 进程应用 seccomp filter。AOSP 的 bionic 源码说明 whitelist 用于生成 seccomp policy，并且确实存在按 syscall 白名单工作的策略。[AOSP bionic whitelist 示例](https://android.googlesource.com/platform/bionic/+/android-8.0.0_r4/libc/SECCOMP_WHITELIST.TXT)

未允许的 syscall **可能**导致 `SIGSYS`；但不能把所有设备概括为统一的“未在白名单里就一定 SIGSYS”。具体返回行为由设备上的 BPF policy 决定，可能是 trap、返回错误等。Termux 和 Go 的问题报告中都有实际 `SIGSYS` 案例，包括被拦截的 `faccessat2`、`landlock_create_ruleset`。[Termux Landlock SIGSYS 报告](https://github.com/termux/termux-packages/issues/30082) [Termux Go/faccessat2 报告](https://github.com/termux/termux-packages/issues/29385)

### 你列出的调用：能确认到什么程度

下面列的是“官方资料能否给出跨版本结论”，不是 Linux 内核首次支持版本：

| syscall | 可确认的信息 |
|---|---|
| `getrandom` | AOSP Android 8.0 的 whitelist 示例中已列入；Rust 标准库 Linux 随机源会尝试它，并有回退路径。 [AOSP whitelist](https://android.googlesource.com/platform/bionic/+/android-8.0.0_r4/libc/SECCOMP_WHITELIST.TXT) [Rust std 实现](https://doc.rust-lang.org/src/std/sys/random/linux.rs.html) |
| `memfd_create` | 同一份旧 AOSP whitelist 示例已列入；这证明该 AOSP revision 的策略允许，不足以证明所有 OEM/后续策略。 [AOSP whitelist](https://android.googlesource.com/platform/bionic/+/android-8.0.0_r4/libc/SECCOMP_WHITELIST.TXT) |
| `pidfd_open`、`pidfd_send_signal` | Go 官方源码注释写明 Android 12 之前 pidfd 相关调用不被 seccomp 允许并会触发 `SIGSYS`；这是 Go runtime 对 Android 的说明。不能由此推断所有 Android 12+ OEM 构建都放行。 [Go Android pidfd 检测源码](https://android.googlesource.com/platform/prebuilts/go/darwin-x86/+/3338a834dd07658737237fa1fa87d7ba8b191c93/src/os/pidfd_linux.go) |
| `landlock_create_ruleset` | Termux 2026 issue 有 Android app 进程因该调用被 seccomp 拦截并 `SIGSYS` 的复现；它不能作为 Android 10–16 的逐版本矩阵。 [Termux issue](https://github.com/termux/termux-packages/issues/30082) |
| `faccessat2` | 有 Samsung Android 16 Termux 报告称被设备 seccomp 拦截并 `SIGSYS`。这是 OEM 特定实证，说明不能假设新 Android 必定放行。 [Termux issue](https://github.com/termux/termux-packages/issues/29385) |
| `clone3`、`close_range`、`copy_file_range`、`statx`、`rseq`、`openat2`、`epoll_pwait2`、`membarrier` | 我没有找到可核验的 AOSP 官方资料，逐版本说明这些调用在 Android app seccomp 中何时放行。Linux 内核支持该调用不等于 Android app filter 放行。 |

**结论：**不能仅凭 Android 版本把上述调用逐个标成“从某版起允许”。AOSP filter、内核与 OEM 修改都可能改变结果。你提到的 `SIGSYS` 最有效的定性方式是实机 `strace`/crash log，看 `si_syscall`，再按具体设备固件判断。

### Tokio、Rust std 与 SIGSYS 风险

- Tokio 的 Unix child reaper 在 Linux 上可使用 pidfd；若 `pidfd_open` 不可用或失败，会让 pidfd reaper 不启用并使用常规 SIGCHLD 回收路径。当前 Tokio 源码可从其 Unix process 实现查看：[Tokio `process/unix` 源码目录](https://github.com/tokio-rs/tokio/tree/master/tokio/src/process). 我没找到可引用的官方源码资料，证明你指定的 Codex 0.166.0 构建所用 Tokio feature/版本一定会在实际路径调用 pidfd；因此不能断言 Codex 启动必然调用它。

- Rust std 在 Linux/musl 构建中是否调用某个 syscall，取决于 Rust 版本与功能路径；已确认 Rust std Linux 随机数实现会尝试 `getrandom`，并有 `/dev/urandom` 等回退说明。[Rust std `linux.rs`](https://doc.rust-lang.org/src/std/sys/random/linux.rs.html)

- Termux 有 Android 11 上 `set_robust_list` 导致 SIGSYS 的旧报告，也有近期 Android 16 的 Landlock、`faccessat2` 案例。前者是非 Android 目标的 Linux 用户态程序跑在 Android 上的兼容问题；这些都说明静态 musl 并不会绕开 app seccomp。[Termux glibc SIGSYS 讨论](https://github.com/termux/termux-packages/discussions/8677) [Termux Landlock issue](https://github.com/termux/termux-packages/issues/30082)

## 3. musl 静态程序的 DNS

musl 会读取 `/etc/resolv.conf`。如果文件不存在或没有有效 nameserver，musl resolver 的默认 nameserver 是 `127.0.0.1`，而 Android app 运行环境通常没有在 localhost:53 提供 DNS 的系统解析器，因此域名解析容易失败。[musl `resolvconf.c`](https://chromium.googlesource.com/native_client/nacl-musl/+/f190498d3f81a5e9d5e94b8678e93dbd943fb2b0/src/network/resolvconf.c)

常见办法：

1. 在 App 私有运行目录中提供 `/etc/resolv.conf` 所需路径——但静态程序默认读取的是进程可见的绝对 `/etc/resolv.conf`，不能只在 `CODEX_HOME` 下放文件。
2. 让启动环境具备可控的 `/etc` 视图，例如使用受控 rootfs/proot；代价是复杂度与 syscall 兼容性上升。
3. 让程序改用应用层 DNS/HTTP 代理或其他可配置解析器。对 Codex 来说，代理可以解决部分外网请求路由，但 `HTTPS_PROXY` 本身不会自动改变 musl 的 DNS resolver 行为。

我没有找到 Codex 0.166.0 官方文档称其可配置 musl resolver 的 `resolv.conf` 路径。

## 4. Codex CLI / codex-rs

以下 GitHub `main` 源码链接是当前可浏览源码；除非指向 release/tag 固定链接，否则不能保证内容与 0.166.0 完全一致。0.166.0 的 npm 版本确实存在。[npm 版本页](https://www.npmjs.com/package/%40openai/codex?activeTab=versions)

### a. `codex login --device-auth`

- 登录使用 ChatGPT 设备码授权。当前官方 Codex 登录说明与 issue 资料显示需要在个人 ChatGPT 安全设置中启用，或由组织管理员在 workspace 权限中允许；不是只要 CLI 传 `--device-auth` 就必定可用。[Codex device auth 源码](https://github.com/openai/codex/blob/main/codex-rs/login/src/device_code_auth.rs) [Codex issue：启用设备码授权](https://github.com/openai/codex/issues/34817) [Codex issue：workspace 管理员设置](https://github.com/openai/codex/issues/9253)

- CLI 显示一次性码有效期 **15 分钟**，轮询也最多等待 15 分钟；HTTP 403/404 表示授权尚未完成，超过等待时间返回 `device auth timed out after 15 minutes`。[device code 源码](https://github.com/openai/codex/blob/main/codex-rs/login/src/device_code_auth.rs)

- 成功时源码交换 OAuth token 并调用 token 持久化函数；默认凭据存储模式可配置为 `file`、`keyring`、`auto` 或 `ephemeral`。`file` 写入 `CODEX_HOME/auth.json`；`ephemeral` 仅当前进程保存。[凭据存储配置定义](https://github.com/openai/codex/blob/main/codex-rs/core/config.schema.json) [凭据存储实现](https://github.com/openai/codex/blob/main/codex-rs/login/src/auth/storage.rs)

- CLI `login --device-auth` 成功路径退出码为 0；错误路径会输出错误并以非零退出。`--device-auth` 路径的代码通过 `run_interactive_login` 结束，确切各类错误码需以固定的 0.166.0 tag 逐条核对；我没有找到官方文档承诺所有失败类型使用同一数值。[CLI login 实现](https://github.com/openai/codex/blob/main/codex-rs/cli/src/login.rs)

- workspace 成员能否登录还受其 Codex 使用权限和组织策略影响。公开资料支持“个人设置 / workspace 管理员开关”这一差别；我没有找到一份官方表格完整比较 Free、Plus、Team/Business、Enterprise 每种套餐的设备码权限，因此不应推断某类账号必然可用或必然不可用。

- 配置项源码名称为 `cli_auth_credentials_store`，支持 `file`、`keyring`、`auto`、`ephemeral`。在无 Android keyring 服务的环境，建议明确设成 `file`，避免 `keyring` 模式因不可用失败。[配置 schema](https://github.com/openai/codex/blob/main/codex-rs/core/config.schema.json)

### b. Linux shell 选择

Codex shell 检测源码路径是 [`codex-rs/shell-command/src/shell_detect.rs`](https://github.com/openai/codex/blob/main/codex-rs/shell-command/src/shell_detect.rs)。

Linux/Unix 大致顺序是：

1. 读取当前 uid 的 passwd 记录中的 `pw_shell`，仅当识别为支持类型且路径存在时使用；
2. 在 `PATH` 中按 shell 名称查找（例如 bash）；
3. 检查硬编码候选路径（bash 是 `/bin/bash`、`/usr/bin/bash`；zsh 是 `/bin/zsh`）；
4. 最终 fallback 是 `/bin/sh`。

源码明确使用 `getpwuid_r` 风格接口读取 passwd 字段，而非直接 `getpwuid`。因此，在没有 `/etc/passwd`、没有 `/bin`，但 `PATH` 中没有 `sh` 的 Android 环境，最后的 `/bin/sh` fallback 也会失败。Android 系统 shell 通常是 `/system/bin/sh`，但 Codex 默认候选路径里没有它。

实用做法：提供一个包装器，在 App 启动时把 `/system/bin/sh` 的目录加入 `PATH`，并确保 `sh` 名称可找到；或者在私有兼容目录构造 `bin/sh` 指向系统 shell。仅设置 `$SHELL=/system/bin/sh` 不一定够，因为源码通过 passwd shell 和类型探测/文件存在性选择，并不是简单无条件采用 `$SHELL`。

### c. 网络代理和 TLS 根证书

- Codex 的 HTTP 请求统一经共享 `codex-http-client`。默认代理行为取决于有效代理策略和配置；Codex 文档描述了 `RespectSystemProxy` 模式会考虑系统设置、PAC/WPAD、环境代理，再考虑直连。不能笼统说所有请求在所有配置下都遵守 `HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY`。[HTTP client README](https://github.com/openai/codex/blob/main/codex-rs/http-client/README.md)

- WebSocket 有独立的代理连接代码；当前源码的 secure WebSocket 环境变量处理包括 `HTTPS_PROXY`，Codex 网络层 README 也列有 HTTP/HTTPS/WS/WSS 与 SOCKS 变量。[代理实现](https://github.com/openai/codex/blob/main/codex-rs/http-client/src/outbound_proxy.rs) [WebSocket dialer](https://github.com/openai/codex/blob/main/codex-rs/websocket-client/src/dialer.rs) [网络代理 README](https://github.com/openai/codex/blob/main/codex-rs/network-proxy/README.md)

- Codex 自定义 CA 处理读取 `CODEX_CA_CERTIFICATE`，回退到 `SSL_CERT_FILE`；当前源码注释描述的是 native roots 加自定义 CA bundle。[Codex custom CA 源码](https://github.com/openai/codex/blob/main/codex-rs/http-client/src/custom_ca.rs) 我没有找到当前实现承诺使用 `SSL_CERT_DIR` 的证据。Android 没有典型 Linux CA 文件布局时，应显式提供适用于该二进制实现的 CA bundle，并实测 HTTP 和 WebSocket 两类连接。

### d. `codex-code-mode-host`

它是 Codex JavaScript code mode 的独立 host 进程。Codex feature 列表中有 `CodeModeHost`、`CodeModeHostGrpc` 等 feature；这些开关用于启用独立 host / stdio gRPC 等路径。[Codex features 源码](https://github.com/openai/codex/blob/main/codex-rs/features/src/lib.rs)

它不是启动 `codex app-server` 和一般 shell 工具的基础必需品；如果 app-server 会启用并使用 JavaScript code mode，host 才可能需要。npm 包确实会包含这个二进制，但我没有找到 0.166.0 官方说明称它在所有配置下必需。保守做法是保留与发布包匹配的 host，同时在 Android 上关闭相关 code-mode feature，避免意外拉起额外进程。

### e. Linux sandbox 与 app-server

Codex 当前 Linux sandbox 默认使用 bubblewrap 建立文件系统视图并应用 seccomp；Landlock 是 legacy/备选路径。Android app 环境通常既没有可用的 bubblewrap mount/user namespace 环境，也不能假定 Landlock syscall 可用。[Codex sandbox helper](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/src/linux_run_main.rs) [Landlock 相关源码](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/src/landlock.rs)

若 Codex 在 Android 上执行命令，配置 `sandbox_mode = "danger-full-access"` 可以跳过 Codex 自身的 Linux 命令 sandbox；这会让子命令直接继承 App 权限边界，不能视为安全隔离。Codex 配置文档说明该模式适用于外部环境已经负责隔离、或原生 sandbox 不支持的环境。[Codex 配置说明](https://github.com/openai/codex/blob/main/docs/config.md)

app-server 官方协议文档：[codex-rs/app-server/README.md](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md)。由 App 用 stdio JSON-RPC 驱动时，重点看该协议 README 和协议 schema；当前 README 是滚动文档，集成应固定到 0.166.0 对应 tag/commit。

## 6. PhantomProcessKiller 与前台服务

- Android 12 引入 phantom process 管理。AOSP 维护者资料指出默认 `max_phantom_processes=32`；超出后系统可清理 phantom 子进程。父 App 用 `ProcessBuilder` 启动的 Codex，以及 Codex 再启动的 shell/工具进程，都属于需要考虑的子进程树；是否被杀取决于进程状态、数量、资源和设备实现。[Phantom process 机制与 AOSP 源码说明](https://github.com/agnostic-apollo/Android-Docs/blob/master/en/docs/apps/processes/phantom-cached-and-empty-processes.md)

- Android 12+ 也有针对子进程过量 CPU 使用的清理逻辑。AOSP `ActivityManagerService` 代码中可以看到对 phantom process CPU 使用量的检查和杀进程调用。[AOSP AMS phantom CPU 处理](https://android.googlesource.com/platform/frameworks/base/+/5f00e89989392c9ae00b360e1388d0179dfb36d7/services/core/java/com/android/server/am/ActivityManagerService.java)

- 前台服务提升的是承载服务的 App 进程重要性；不能据此推断整个子进程组必然豁免 phantom process 限制。官方生命周期文档说 FGS 被视作用户可见、重要的进程；我没有找到 Android 官方承诺“前台服务完全豁免 phantom process 的数量和 CPU 管理”。[Android 进程生命周期](https://developer.android.com/guide/components/activities/process-lifecycle)

- Android 14 开发者选项有 **Disable child process restrictions** 开关。非官方但有源码引用的操作资料给出 adb 写法：`adb shell settings put global settings_enable_monitor_phantom_procs false`；该值是否有效、是否被 Google Play services 或 OEM 重置，应在具体设备验证。[设置项说明与 adb 方法](https://github.com/agnostic-apollo/Android-Docs/blob/master/en/docs/apps/processes/phantom-cached-and-empty-processes.md)

- target 28 的长任务可从前台 Activity 启动前台服务，服务立即调用 `startForeground()` 并持续显示通知；Android 9 起需 `FOREGROUND_SERVICE` 权限。Android 14 的强制 service type/对应权限要求只对 target 34+ 生效，Android 15 的 `dataSync` 六小时限制只对 target 35+ 生效。[前台服务规则变化](https://developer.android.com/develop/background-work/services/fgs/changes) [Android 14 FGS types](https://developer.android.com/about/versions/14/changes/fgs-types-required)  
  这提高进程存活优先级，但不能保证 OEM 永不杀进程，也不能替代持久化状态、重启恢复和用户可见取消控制。

## 风险清单与对策（按严重度）

1. **严重：目标二进制被 Android app seccomp `SIGSYS` 杀掉。**  
   不要依据 Android 大版本或 Linux syscall 支持表推定兼容。先在 Android 14/15/16 的目标设备上启动 Codex，覆盖认证、创建子进程、运行 shell、DNS、文件扫描等路径，并收集 `SIGSYS si_syscall`。如果是 Codex/Rust/Tokio 路径触发，优先寻找关闭相应 feature 或替换构建的办法；不同 syscall 的失败回退并不统一。

2. **严重：Codex shell 启动失败。**  
   Android 默认 shell 在 `/system/bin/sh`，Codex Linux 发现逻辑默认走 `/bin` 和 `/usr/bin`。通过包装器与私有兼容路径把可执行 `sh` 暴露在 `PATH` 中，并验证 `pw_shell` 缺失时的最终 fallback。

3. **严重：musl 找不到 DNS。**  
   明确提供 musl 能读取的 resolver 配置，或让运行环境提供有效 `/etc/resolv.conf`。不要假设 Android 的系统 resolver 会自动映射到 musl 的文件式 resolver。

4. **高：低 target 发布/安装警告与分发限制。**  
   target 28 有助于私有目录执行，但 Google Play 发布要求远高于此，侧载可能有 Play Protect 警告。提前确定分发渠道；若必须 target 29+，则需要改成 APK native library / system linker exec 等受支持方案，而不是下载后直接执行普通数据文件。 [Termux 相关说明](https://github.com/termux/termux-app/discussions/4564)

5. **高：后台任务中的子进程被 PhantomProcessKiller 清理。**  
   让长任务由用户明确启动，使用通知型前台服务；让 Codex 命令可中断、可恢复，并持久化会话状态。把 phantom-process adb 开关视作开发/设备侧诊断手段，而不是产品可依赖的用户配置。

6. **高：Android 上 Codex sandbox 不可用。**  
   若采用 `danger-full-access`，App 必须自己限制工作目录、文件权限、命令确认与网络使用；Codex 的 sandbox 不再提供额外隔离。不要把“Android 已有 App sandbox”误解为对子进程的文件系统/API 细粒度沙箱。

7. **中：登录设备码不可用或凭据没落盘。**  
   检查账号安全设置、workspace 管理策略和网络连通性；将 `cli_auth_credentials_store = "file"` 固定下来，确认 `CODEX_HOME/auth.json` 权限仅 App 可读，并把它当作长期凭据保护。

8. **中：代理和 CA 配置对 HTTP / WebSocket 行为不一致。**  
   明确设置适用代理变量与 `CODEX_CA_CERTIFICATE`/`SSL_CERT_FILE`，分别验证普通 HTTPS 和 WSS。不要假设 `ALL_PROXY`、`NO_PROXY` 或 `SSL_CERT_DIR` 在每条网络路径中都生效。

9. **中：镜像同步与大文件下载失败。**  
   对 `0.166.0-linux-arm64` 先查询 registry metadata，再下载 `.tgz` 并校验完整性；镜像失败回退 npm 官方源。分阶段下载、校验、原子替换，避免中断后留下半个二进制。

10. **中：空间与启动耗时。**  
    Codex 包含大型静态二进制，下载和解压前检查可用私有存储空间；先写临时目录、校验成功后原子切换版本。你提供的二进制尺寸尚未由我独立验证，实际包体与解压空间应以目标版本实测为准。
